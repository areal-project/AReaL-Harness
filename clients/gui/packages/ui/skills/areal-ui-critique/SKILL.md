# 审查 @areal/ui 界面

本 skill 只管“怎么审”，唯一真源为 `clients/gui/packages/ui/skills/areal-ui-critique/SKILL.md`（`.agents/skills/areal-ui-critique` 为指向该目录的符号链接）。怎么改见 `areal-ui-guide`；交付要回答的五项见[完成条件](../../../../design-system/governance.md#完成条件)。

## 1. 先取证据

在仓库根运行：

```sh
pnpm --dir clients/gui design:build
pnpm --dir clients/gui test:design
pnpm --dir clients/gui test:design -- --conversation-system
pnpm --dir clients/gui audit:ui
```

`test:design` 最后一行 JSON 的 `scratch` 是本次证据目录：截图、计算样式、`manifest.json`、`accessibility.json` 与 `contrast-matrix.json` 都在里面。`audit:ui` 补充采集多视图亮暗/宽窄/18px 的水平溢出、CLS、Web Animations API 动效时长与 `reduced-motion` 归零情况，并自动合成带编号的 `contact-sheet-overview.png` 供横向视觉比对。改动涉及的场景没有截图时，先补检查用例，再下视觉结论。

业务与 UI/UX 回归优先在 Web（`test:web-journeys` / `audit:ui`）取证；仅原生标题栏、毛玻璃材质、系统菜单/弹窗、Keychain、IME 组合态与 `WebContentsView` 等桌面外壳能力使用隔离 Electron 验证。

## 2. 亮暗分别看

同一状态的亮色和暗色截图各看一次，逐项写下：

- 层级：主阅读内容、次要信息与动作是否一眼可分；单屏主权重按钮是否 ≤ 1。
- 对齐与间距：用留白建立分组，无多余“卡片套卡片”与分割线；与相邻同类组件对比。
- 状态：Empty / Loading / Error / Overflow / Pending 与默认、悬停、焦点、禁用各自可辨，焦点环可见。
- 弹出层：打开后把鼠标移出触发行并悬停各菜单项，位置不变、触发按钮仍可见；以 `test:design -- --popup-anchors` 报告为准。
- 文字：长标签、窄窗口、18px 字号下不截断关键动作；无孤立“确定/取消”、无技术黑话、无“暂无数据”。
- 对比度：以 `contrast-matrix.json` 为准，不靠肉眼判断。

## 3. 失忆 Agent 盲审（独立认知走查 / Cognitive Walkthrough）

写完界面的同一段对话已经染上“知识的诅咒”——自查必然偏乐观。对于**新页面、流程重排或高影响交互改动**，必须启动一个**零历史上下文的独立只读子代理**执行盲审：

- **只传两样东西**：本次 `audit:ui` / `test:design` 实拍截图路径 + 一句真实陌生人目标（例：“假设你第一次打开这个界面，想完成 [具体用户任务]”）。**严禁透露设计意图、按钮含义或源码。**
- **强制回答 4 个冷眼问题**：
  1. **5 秒主焦点（执行鸿沟）**：看图第一眼，这页是干嘛的？你最想点哪个按钮？
  2. **干扰项检测**：有没有长得太像、让你停顿超过 2 秒才敢点的同级按钮或入口？
  3. **文案扫盲**：界面上有没有陌生黑话、模糊确认词（如“确定/取消”）或需要读小字解释才能懂的标签？
  4. **预期踏实度（评估鸿沟）**：凭画面判断，你点完主动作后知不知道会发生什么、错了能不能撤回？

盲审暴露的任何停顿与误解，都作为真实 UX 发现进入问题列表，优先改界面本身，不用“补一行解释小字”掩盖。

## 4. 交互机芯 3 分钟走查

对涉及交互的改动，逐项核验底层机芯（不能只看静态图）：

- **拔鼠标测试**：仅用 `Tab` / `Shift+Tab` / 方向键 / `Enter` / `Esc` 走完核心路径，弹窗与菜单关闭后焦点回到原触发器。
- **贴边测试**：触发器位于视口边缘时，浮层自动避让不裁切，锚点不漂移。
- **反馈节奏**：点击后 100ms 内可见即时状态反馈（评估鸿沟）；加载 >300ms 才出骨架屏，不闪烁；可逆操作优先 Undo。
- **破坏性测试**：注入 50 字长标题、空数据、错误态、窄窗口、18px 字号与暗黑切换，确认无布局崩坏与未跟主题的色块。

## 5. 判断题

CI 不判断下面几项，逐条回答“是 / 否 / 不适用”，回答“否”的写进问题列表：

- 页面只给 `@areal/ui` 组件布局，外观来自 variant 或 slot（基线里的存量不算新问题）。
- 同一个概念没有出现第二套实现，例如另写一个输入框、空状态或审批卡。
- 新增的通知是用户需要知道或能处理的；其余信息在原处说明。
- 高级功能默认收起；默认界面对普通用户没有多余选项；单屏主动作 ≤ 1。
- 文案短、说人话，按钮写“动词 + 结果”，报错含“原因 + 数据安全 + 修复路径”，用词与[术语表](../../../../../../design/content/terminology.md)一致。
- 加载中、未知、已提交等未确认状态没有显示成成功或“没有”。
- 只有桌面端才有的能力，结论注明是否在桌面验证过。
- 改动组件旁合同里带规则 ID 的强制规则逐条对照过。

## 6. 观察与推断分开

每条结论标明来源：

- **观察**：附截图、盲审子代理结论或报告文件名，写明主题、字号、窗口宽度。
- **推断**：只从源码或 diff 得出的结论，句首写“推断：”。自动折叠、等待时长、滚动跟随和焦点移动不能从静态截图得出，只能写成推断或待补证据。

## 7. 输出

按严重程度列出问题，每条包含：位置（文件或组件）、证据（截图、盲审或报告）、违反的规则 ID、建议的最小修改。没有问题时写“未发现问题”，并列出实际看过的主题、字号和窗口。注明证据来自设计预览、源码 Electron 还是安装包；本 skill 默认只覆盖设计预览。

视觉基线由用户确认，审查结论不替代用户验收。
