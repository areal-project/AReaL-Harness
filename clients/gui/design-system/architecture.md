# GUI 设计系统实现与准入

共享知识与平台职责见[设计系统架构](../../../design/architecture.md)，下一轮产品建设见[建设计划](roadmap.md)。整体候选与真实路径迁移仍按各自条件准入，不由文档整理自动通过。

## 目标与质量场景

| 变化 / 条件 | 应发生的结果 | 如何判断 |
| --- | --- | --- |
| 同类设置增加一个字段 | 调用方填标签、值与动作，选择已有控件/设置组合 | 不复制控件 CSS；模式合同覆盖必要状态 |
| 做题暴露共性偏差 | 归因到规则、Token、组件或组合的唯一所有者 | 修改 Base 后原题复验，再用另一题确认没有只适配原题 |

## 分层与所有权

| 层 | 拥有什么 | 输入与输出 | 不拥有什么 |
| --- | --- | --- | --- |
| Product surfaces | 任务内容、业务状态映射、真实动作绑定 | Patterns + 原业务所有者 → 用户页面 | 不重定公共颜色/字号/控件样式，不复制提交和恢复权威 |

`R-ARCH-013` 包内Worktree领域组合位于`packages/ui/src/worktree`，与conversation并列，依赖core控件；core不可反向依赖领域层。五个组合通过原Worktree业务适配接入，状态与操作权威保持原位。短时通知采用core层NotificationToast及原ToastHost通道，等级颜色来自既有语义角色。

`R-ARCH-014` 工作台层位于`packages/ui/src/workbench`，拥有壳层、面板结构、设置导航、任务行及资源范围/空态。面板注册、拖拽身份、关闭守卫、保活与原生资源生命周期归宿主；层级不可反向依赖renderer。

系统级目录 `registry.json` 是上述角色、组件与模式的索引。它只引用数值源和实现，不是新增的数值层，也不承担渲染引擎职责。

## 与现有所有者的映射

当前数值与偏好所有者见[Token 地图](../../../design/foundations/tokens.md#每类值在哪里改)，组件与生产入口见[目录](inventory.md)，生成与检查入口见[自动化](automation.md)。这些索引分别引用实际源码，不在本页复制接线状态表。

`R-ARCH-016` 颜色、字体、间距等的实际优先级继续由现有 CSS cascade、主题适配与外观应用决定。Base 阶段必须以代表控件的 computed style 核对整条链，不能只因为变量存在就宣布统一。尚未观测的跨平台与自定义主题结果保持缺口。

## 数据合同与权威

| 数据 | 可编辑的真源 | 派生物 / 消费者 | 维护规则 |
| --- | --- | --- | --- |
| 页面实现合同 | surfaces 中的数据 | 具体实现与状态验收 | 引用模式、组件、来源、状态和条件；不是执行 DSL |
| `R-ARCH-021` 原始运行证据 | 本地 run manifest、原图与日志 | 对照报告及规范的采纳结论 | 绑定实际版本和条件，保护私有数据；不能自动成为新基线 |

`R-ARCH-023` `schemaVersion` 表示数据格式；未来的 Base 版本表示一套可复验的规则与生产实现。二者不能混用。`schemaVersion: 1` 和目录提交不等于 Base v1 已冻结；当前 Base候选版本在 registry 的 baseCandidate 中维护。

## 结构化数据如何约束实现

任务输入表达意图、内容、状态、条件及所选模式；设计目录把这些选择限制在已有角色和组件中；React 实现仍通过真实组件组合完成。让已有 `SettingsSelect` 决定二值/多值控件，让设置行拥有换行和对齐，比让每页按 JSON 重新生成一套控件更稳定。

## 自动化分工与约束强度

检查范围与静态限制由[自动化](automation.md#增量设计检查)维护；证据能证明的范围由[治理](governance.md#证据分层)维护。

`R-ARCH-026` 截图是反馈传感器，不能成为逐页设计的唯一机制。对确定性结构约束用代码检查；对视觉质量用受控比较；对未决产品语义保留明确决策，避免把审美猜测写成 lint。

## 方案取舍

| 方案 | 收益 | 代价 / 结论 |
| --- | --- | --- |
| 只扩写规范 | 上手快 | 实现可绕过，目录/示例会漂移；不足以单独达成目标 |

`R-ARCH-029` 若未来出现多个独立运行端必须消费同一设计源，再复审 Token 编译与跨端 recipe；不能仅因参考项目采用就提前迁移。

## 阶段及准入

### B：Base 设计系统

在该架构下挑选最小但完整的基础切片：生产字体/色彩/空间/形状角色，常用控件的有限变体，至少一个真实设置组合和一个内容/决策组合。沿现有所有者补齐缺口，不重新绘制全产品。

### C：固定题目与模拟页面

`R-ARCH-032` 先固定题目、内容、初始值、操作后状态、viewport 和评分依据，再用冻结 Base 实现一个新的模拟页面。只复用现有组件与模式，允许的局部差异来自任务内容。模拟页属于开发预览，不能进入生产路由或连接真实业务。

`R-ARCH-033` 实现输入与评判材料分开：要检验 Base 是否足够时，实现者不读取目标效果截图或详细参考实现；评估者按同条件对照。当前同会话已看过的预览不能声称是盲测，新页面的试运行也不能当作整体泛化证据。

## 按用户交互组织

`R-ARCH-036` 基础语言 → [交互模式](interactions.md) → 业务组合 → 验证。八类交互族定义用户意图和响应约束；P-* 保留组合及生产所有者。规则分必须、默认、可探索；具体数值仍归生产 token。registry 只索引交互族、规则与组件，目录生成器校验引用；不生成页面或执行状态。新增分类不扩大 Base 准入。
