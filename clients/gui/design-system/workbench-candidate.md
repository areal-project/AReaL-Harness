# 完整工作台候选

## 打开与体验

从仓库根运行 `pnpm --dir clients/gui design:dev`，打开 `/design-system.html?product-candidate`。现有设计预览也提供候选入口。

打开资源查看内容，再进入设置修改外观。返回时继续查看原资源，关闭资源后回到同一聊天。等待期间可以编辑下一条草稿，资源与设置的切换不提交或清空它。

## 整体表达选择

| 范围 | 候选选择 | 设计理由 |
| --- | --- | --- |
| 工作归属 | 稳定导航与当前任务标题 | 用户在过程、资源和设置间移动时仍能识别原工作 |
| 主要内容 | 中央聊天与底部输入 | 提交、过程、决定和结果在同一阅读路径中连续出现 |
| 设置 | 独立工作区域，偏好即时作用于当前候选 | 外观调整可直接比较，返回后继续原工作 |

精确色值、尺寸、形状和动效继续归[基础表达与 Token 所有者](../../../design/foundations/tokens.md)。本候选不冻结新的全局视觉基线。

## 实现与状态边界

`R-WORKBENCH-009` 候选入口与组合由 [ProductCandidate](../renderer/src/design-system/ProductCandidate.tsx) 维护，复用 Messages、ConversationComposer、ApprovalRequest、工作台布局和设置控件。草稿、路由、外观与模拟执行有明确的本地所有者，不建立 Core 协议模拟服务。

`R-WORKBENCH-010` 审批提交与执行完成是不同事件。后续结果到达前不生成交付物。重新开始使旧事件失效，资源与设置导航不启动另一轮执行。外观仅在当前候选内生效，不写入生产偏好。

## 评价重点

- 审批的信息是否足够作决定，批准、拒绝与后续结果是否连贯。
- 明暗、字号与窄窗下，阅读层级和主要动作是否仍然清晰。
- 失败与结果未知是否容易区分，下一步动作是否符合当前事实。

## 真实 GUI 体验

构建 GUI 后，按 [GUI 体验入口](../README.md#composer)启动隔离窗口。输入普通要求，观察真实过程，选择批准或拒绝，再从文件结果打开正文。它使用既有提交、审批和结果控制器及真实 Core/Runtime，本地确定性模型只负责产生可复现的请求。所有文件限于临时项目。

该入口用于评价本次任务切片的颜色、宽度、间距和文字层级。资源与设置的整体组织仍在本地候选中评价，候选的模拟路由和状态没有迁入生产。

## 验证范围

`pnpm --dir clients/gui test:design --product-candidate` 从真实浏览器操作本地候选，检查连续路径、草稿、返回、状态、外观与响应式布局，保存截图和运行记录。构建使用 `pnpm --dir clients/gui design:build`。
