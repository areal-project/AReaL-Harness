# AReaL Harness GUI

The complete desktop client contains a React renderer, Electron native adapter, and public dependencies. It is a peer of CLI/TUI/Web in the Clients layer. Core owns sessions, history, model loops, and scheduled tasks; Runtime executes tools. Mobile source migration is deferred; desktop pairing remains available.

Engineering checks use the existing Vite+ entry points. `pnpm --dir clients/gui health` checks production source sizes, UI adoption, and recorded debt. `verify:tests` validates the root package test manifest, and `test:unit` runs pure Renderer and UI package behavior tests. `node clients/gui/scripts/run-portable-tests.mjs` selects registered tests for the current platform without Core or native UI prerequisites. A configured Linux CI job does not establish a completed Linux acceptance run.

See the [testing guide](../../docs/development/testing.en.md#gui-test-registry-and-platform-qualification) for registration, area selection, prerequisites, and repeated qualification commands. Register new tests and use `scripts/support/temp.mjs` for temporary directories. `test-manifest.mjs --ci-matrix --base=<commit>` selects existing macOS smoke cases; unknown or shared paths retain the full set. `repeat-tests.mjs` records first attempts for five Linux journeys ten times each and macOS E2E five times each. Linux requires at least 95% without blocks before human review. Unexecuted CI, blocked environments, and unit checks do not establish desktop acceptance.

Production builds emit `renderer/dist/bundle-analysis.json` with actual chunk modules, static dependencies, and hashes. `verify:bundle` checks each HTML entry's full static closure, total JavaScript, and lazy chunk budgets. Initial `bundle-budget.json` limits include 5% byte headroom. `node clients/gui/scripts/bundle-budget.mjs --write` only tightens limits. Health baseline updates also require improvement, and CI compares baseline changes with the base commit. Source findings and limits are recorded in the internal [implementation decisions](specs/implementation-decisions.md).

Web/PWA Remote v2 boundaries are documented in the [architecture](../../docs/design/remote-control.en.md), [API](../../docs/api/remote-control.en.md), [connectivity guide](../../docs/guides/remote-control.en.md), and [acceptance plan](../../docs/development/remote-control-testing.en.md). Source implements default-disabled entry points, browser requests with desktop confirmation, explicit project grants and device revocation, plus work overviews, session details, creation and sending, exact Turn stops, approval and question replies, task pauses and result review. Direct and the standalone Relay share Host authorization and encryption; container scaffolding is available in [Relay deployment](../../services/remote-relay/deploy/README.en.md). Source implementation does not certify real phones, production browser TLS, public networks, system keychain or packaged apps; each layer requires independent evidence.

Update recovery and menu stop share lifecycle observation and stopping. Normal stop still protects paused Queues containing pending input. Explicit cancellation preserves input and schedules and carries the cancel intent through the final public service host. A changed project scope or Core generation requires new confirmation; partial exits and unknown outcomes do not appear as normal operation. `pnpm --dir clients/gui run test:lifecycle` checks Queue retention and safe exit against real Core, plus menu cancellation, attachment to the original service with a different requested config path, and update recovery in isolated Electron. Ordinary reopen shows no recovery dialog. Explicit stop confirmations use fixture responses; no update is downloaded or installed.

Legacy adapters without lifecycle version 2 retain observation; no cross-layer cancellation fallback is attempted. A known legacy Desktop partial-stop record exposes inspection and an explicit recovery action in the backend banner and settings. Inspection checks original Host identities, admission and resource settlement. Exited targets additionally require a clean Host shutdown marker and released instance/Store locks; a missing PID or socket is insufficient. Unknown, draining, busy or replaced targets retain their records and show the blocker. After confirmation, a new safe stop targets only the original generations verified as idle. A lost recovery-stop response is inspected without resubmission. The current backend starts only after all original Hosts confirm cleanup and the old Desktop exits. An unresponsive Desktop manager requires a separate confirmation before ending that manager; Core/Runtime receive no process signals. Configuration, workspaces, history and tool UNKNOWN records remain intact; the original stop record is archived, and interrupted recovery can be checked again. `pnpm --dir clients/gui run test:legacy-recovery` uses an isolated historical Desktop, current GUI/Core and a local model; `AREAL_RECOVERY_SCENARIO=exited` covers a completed Host stop whose response was unknown.

Before creating, changing or reviewing a page, agents follow the internal [design rules v1](design-system/README.md) and [evidence-driven workflow](design-system/structured-flow.md#执行顺序与每步完成条件): fix the contract and reference, use video analysis to nominate candidates, verify them with keyframes and logs, select justified differences, then implement through existing owners, validate and update the canonical rules. Token roles, interaction contracts and previews remain in the [client design system](design-system/README.md).

Run `node clients/gui/scripts/migration-smoke.mjs --conversation-journey` from the repository root after building and verifying Core/Runtime and the renderer. This real Electron scenario covers commands, child agents, images, reading/convergence, paused UNKNOWN inspection and GUI history recovery against a deterministic local SSE model. See the [Electron scenario](design-system/exercises/conversation-flow.md#真实-electron-专项-e1) for evidence and injected boundaries.
The same runner's `--conversation-motion` mode retains original CDP frames plus RAF/input/reading observations and checks disclosure reversal, resource return and reduced motion. See the [E2 scenario](design-system/exercises/conversation-flow.md#真实-electron-连续动效专项-e2) for its boundaries and replay requirements.

Use `--conversation-host` for actual window sizes/125% zoom, child/settings focus return, drafts, shortcuts and a new-content journey. Native Chinese IME requires separately attributable OS interaction. See [E3](design-system/exercises/conversation-flow.md#真实-electron-宿主与新内容专项-e3); [E4](design-system/exercises/conversation-flow.md#原生宿主补充-e4) uses `AREAL_E4_NATIVE=1 AREAL_E4_OPERATOR=0` to replay same-app window reactivation, independent native web interaction/hiding and focus return. Run `pnpm --dir clients/gui test:design --conversation-demo` for this sample. It uses the same isolated Electron/Core/Runtime and deterministic local model. It does not replace the full journey's separate active-quit/background-completion contract or establish installed-package or real-provider acceptance.

## Development

Run from the repository root with Node.js 22.19+ on 22 LTS, 24.11+ on 24 LTS, or 26+, pnpm 11.7.0 and the repository Rust toolchain. Use the same Node.js 24.22.1 LTS version as CI for both packaging and validation:

```sh
make build
make gui-install
make gui
```

`make gui-build` runs `pnpm install --frozen-lockfile` before building the renderer. `make gui` and `make gui-package` share this step, automatically synchronizing dependencies and installation records after branch or version changes. A lockfile mismatch stops the command without updating the lockfile. `pnpm --dir clients/gui typecheck` checks the Renderer, shared desktop contract, and all owned Electron Main sources. Each owned Main CJS or JS file enables `@ts-check`, so imported third-party sources do not enter the same audit. `pnpm --dir clients/gui run verify` checks the public source boundary. `pnpm --dir clients/gui contracts:check` checks generated desktop management contracts without writing files. The generator uses `schemas/areal-core-v1.json` and actual routing tables, with producer references for known source and schema differences. The first command call loads the full validators and validates the request before submission. The initial interface uses lightweight transport error and page message contracts. Before running standalone Node tests, run `pnpm --dir clients/gui build:desktop` to build the browser automation, browser data and interactive content package entry points. CI runs the same prerequisite before tests. This module has its own pnpm lockfile; existing SDKs retain npm. Dependencies use the public npm registry; initial Electron/Core tool installation needs network access.

After installing locked dependencies, Vite+ 1.4.0 supplies local checks and task orchestration without a global `vp` installation. `pnpm --dir clients/gui check` runs Oxlint and Oxfmt on final working-tree changes relative to `HEAD`, plus untracked files. Lint warnings fail the command. The gate checks whole changed files, not only changed lines. After committing, set `AREAL_CHECK_BASE=<base-commit>` to check branch changes. CI requires `AREAL_CHECK_BASE` or the existing `AREAL_DESIGN_BASE`; missing or unavailable baselines fail. Manual GitHub `GUI checks` runs accept an optional `comparison_base` ancestor commit for integration checks; the default remains the previous commit. The command does not stage, stash, or rewrite files. Run `pnpm --dir clients/gui check --fix` to explicitly fix selected files.

`pnpm --dir clients/gui check:all` inventories all owned source. Existing files have not been reformatted in bulk, so this full check can fail. Check specific files with `pnpm --dir clients/gui exec vp check <file-paths>`. The `lint` and `fmt` scripts run Oxlint and Oxfmt separately. Generated directories, build outputs, and third-party static assets are excluded. Formatting also excludes Markdown, the lockfile, and dependency patches. GUI type checks and UI declaration builds use the native TypeScript 7.0.2 `tsc`. The renderer and UI AST tools, `transpileModule` tests, and generators use the `typescript` alias for `@typescript/typescript6@6.0.2`. The current lockfile pins its API and `tsc6` to TypeScript 6.0.3 alongside native `tsc`. The separate SDK npm projects keep their existing compilers.

`pnpm-workspace.yaml` records exact peer metadata compatibility exceptions for the [supported Vite+ alias](https://viteplus.dev/guide/migrate). They accept core 1.4.0 only for React plugin 5.2.0, Tailwind Vite plugin 4.2.2, Vitest 5.0.5, and its mocker 5.0.5. The physical core exports Vite 8.3.5. Typography 0.5.19 separately accepts Tailwind 4.2.2 because its published peer range contains the non-semver `insiders` tag. These entries do not change package versions or disable other peer checks. Revalidate the affected build, HMR, typography output, and test runner before changing either side of an exception.

`build`, `build:desktop`, `design:build`, `verify`, `verify:design`, and `typecheck` use Vite+ tasks in the root `vite.config.mts`. UI, browser automation, browser data, and Gen UI builds explicitly track source, build configuration, and the lockfile. Gen UI also tracks its assets and digest manifests. Cache hits restore each package's `dist`. Production and design renderer builds run every time, writing `renderer/dist` and `dist/design-system` respectively. They consume shared CSS and design images outside the GUI workspace. The current task cache cannot reliably track or explicitly declare those paths, so renderer caching is disabled. The native Swift helper depends on the host Xcode, SDK, and signing environment and builds every time. Git-baseline audits and tests also run every time; replayed success logs are not fresh acceptance evidence. GUI CI saves the local task cache. To verify without caching, run `pnpm exec vp run --no-cache verify-suite` from `clients/gui`. Run `pnpm exec vp cache clean` to clear the cache.

The renderer uses local `vp dev/build` for `dev`, `build`, `design:dev`, and `design:build`, with configuration imported from `vite-plus`. The workspace pins `vite@*` to the matching `@voidzero-dev/vite-plus-core` so plugins share one Vite instance. Browser types reference `vite-plus/client`. Normal and design development modes share the known workspace CommonJS dependency pre-bundling list. Electron continues to load built `renderer/dist` assets; the browser development server does not automatically connect to desktop windows. Desktop builders, `node --test`, signing, and notarization keep their existing entry points.

`make gui-install` explicitly runs the official Electron installer to download the pinned native runtime.

`AREAL_CORE_BIN` selects an absolute trusted Core path; development defaults to `target/debug/areal`. Development data is isolated under `AReaL Harness GUI Dev/<checkout digest>`; installed builds use `AReaL Harness GUI`. Existing desktop installations and data are not imported or replaced. `AREAL_GUI_USER_DATA`, `AREAL_CORE_HOME`, and `AREAL_HARNESS_SERVICE_HOME` explicitly select isolated directories. Model configuration defaults to the CLI's `~/.areal/config.toml`; Core owns parsing, validation, and saving. `AREAL_HARNESS_HOME` changes the Core configuration home, and `AREAL_CORE_CONFIG` explicitly selects another file. Reads do not create configuration; Core creates the default file on first save. Configuration in old GUI isolated directories is not merged automatically.

Explicitly select `AREAL_CORE_SANDBOX_PROFILE=native` before starting the GUI, or `--sandbox-profile native` for `areal service ensure/restart`, to request the native Runtime sandbox. The default remains `full-access`. The profile participates in deployment compatibility; stop active work and explicitly restart when changing it. Legacy read-only Side chat offers read-only access to current workspace files only when Core verifies the native isolation capability. If native isolation is unavailable, startup fails closed; there is no fallback to full access.

The configuration file is selected in this order: `AREAL_CORE_CONFIG`, `AREAL_HARNESS_CONFIG`, then `config.toml` under the Core configuration home. That home uses `AREAL_HARNESS_HOME` first; otherwise it uses `.areal` under `AREAL_CORE_USER_HOME`, or the current user's home when that override is absent. Relative explicit paths resolve against the GUI launch directory. Both the effective configuration path and configuration home participate in a new service's deployment identity. Ordinary reopen compares the requested deployment with the running service. Matching deployments are reused silently. Changed configuration paths or homes retain the running service and expose an explicit update action. The first save of a previously missing default file preserves its identity. Projects within one GUI adapter share this configuration; switching projects does not select another upload configuration.

Both development and installed macOS builds require a working `/usr/bin/python3` to launch Runtime and trusted tool helpers; install Xcode Command Line Tools with `xcode-select --install`. The interpreter is not bundled. Shared-service startup checks availability and returns an actionable error.

The GUI first tries to reconnect to an existing backend. Before starting a new backend, it checks that the selected developer tools contain Python, then runs a bounded system interpreter probe. Missing or stale developer tools prevent execution of the Python stub that can open the OS installer. A dependency failure displays installation guidance and a check-again action before Core or the backend starts. Only clicking the installation button requests `xcode-select --install`. Packaged checks use the existing Core manifest's `prerequisites` declaration. Development checks use the system Python path fixed by the current launch bridge. This check does not establish clean macOS VM or signed-package acceptance.

The macOS GUI backend reads static system HTTP, HTTPS and SOCKS proxies for Core, model connection tests and subscription requests; explicit environment variables take precedence. Bypass rules, restart requirements and limitations are documented in [proxy configuration](../../docs/guides/configuration.en.md#proxies). `pnpm --dir clients/gui run test:proxy` verifies actual HTTP forwarding, HTTPS CONNECT, SOCKS5 remote DNS, backend TCP relays and direct local connections. Set `AREAL_TEST_MODEL_PROXY_BIN` to the compiled `core/engine/tests/model_proxy.rs` test executable to also verify real Core HTTP/HTTPS streaming responses.

## Candidate builds and package acceptance

Unified entry point (run from the repository root; builds release Core, installs dependencies, builds the GUI, and archives):

```sh
pnpm --dir clients/gui run dist --platform mac --arch arm64 --formats dmg,zip --signing none
pnpm --dir clients/gui run dist --platform mac --arch arm64 --formats dmg --signing adhoc
pnpm --dir clients/gui run dist --platform mac --arch arm64 --formats dmg,zip --signing developer-id --identity "$CSC_NAME" --keychain-profile "$APPLE_KEYCHAIN_PROFILE"
```

`--formats` accepts `dmg`, `zip`, or `dmg,zip`. `--output` must be a new directory; by default each run gets a timestamped directory. Existing outputs are rejected. `none` adds no signatures and preserves input signatures; application signature validity and launchability are not guaranteed. Its DMG deduplication requires byte-identical Framework copies. `adhoc` signs locally without notarization. `developer-id` reuses signing, notarization and package acceptance, requires both formats, and places final artifacts in `signed/`. Exit 2 means Apple is still processing: resume with `pnpm --dir clients/gui run sign:mac --resume --output /absolute/output/signed`; do not resubmit an unknown request. Nothing is published.

For signing, notarization and archives without post-signing functional tests, add `--skip-tests` to the Developer ID command, or resume with `sign:mac --resume --skip-tests --output ...`. Desktop smoke and model-selection acceptance are recorded as `skipped-by-request`; signing, Apple notarization, stapling, Gatekeeper, Core integrity and DMG size checks still run. The pre-sign history input check remains. This mode does not establish functional acceptance; release assembly still requires passed tests.

The current support matrix contains **native macOS arm64 only**. Linux, Windows, x64 and cross-compilation fail explicitly until their package and service owners implement support behind this entry point. ZIP has no DMG size budget. ## Installation and updates

Formal macOS arm64 releases use a DMG for first installation and a ZIP for automatic updates, with Developer ID signing and Apple notarization. Verify the matching release's `SHA256SUMS`, drag the app from the DMG to your chosen installation directory, and open it while following macOS security and privacy prompts.

Before upgrading, back up GUI data (normally `~/Library/Application Support/AReaL Harness GUI`), shared configuration in `~/.areal`, and custom project data. Downloading keeps tasks running. After native validation, installation waits for active tasks, queued input, and backend operations to settle safely before stopping the backend and handing replacement/relaunch to the system. If stop acceptance is unknown, inspect the original backend resources without submitting installation again. Retry download/validation failures; if the app does not reopen after system handoff, open its original installation location and check the version. Reverting the app does not downgrade data: restoring an older app may require its matching backup. Credentials keep their existing secure-storage identity; directory backups do not imply keychain portability between machines.

Previews are manual ad-hoc installations without Developer ID distribution signing or notarization, and do not advance the formal update channel. Use isolated data or make a backup first. Older formal versions may not read preview data; moving from preview to formal requires manual installation and separate validation. Do not disable security protection or clear quarantine attributes to bypass system rejection.

See [Browser](../../docs/api/browser.en.md) and [Computer control](../../docs/api/computer.en.md) for automation boundaries. `pnpm --dir clients/gui run test:automation` uses isolated Electron/Core and synthetic sites. Native input acceptance operates only the dedicated fixture and requires existing OS grants. GUI builds include the helper build. Source acceptance does not establish package, notarization or real-provider acceptance.
