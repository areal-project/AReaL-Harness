# D-005 设计规格为准，交给新 Agent 能复现

## 问题

现有设计知识写给在本仓库改代码的人：数值由源码拥有，文档描述代码；组件合同同时写设计与生产接线；参考截图只存在于作者本机；检查脚本绑定生产组件名和路径。离开源码就没有完整真相，另一个 Agent 无法从零复现界面与交互，也无法判断自己做对没有。

同一原因在视觉上表现为：圆角、阴影、模糊和文字层级没有分层，任何 CSS 都能直接写新值或引用刻度；数值写在合同正文中与代码漂移；页面可以覆盖组件外观；模糊没有使用范围与成本约束。

## 选择

1. <!-- rule:R-DECISION-022 -->**规格为准。** 建立独立规格包 [design/spec](../spec/README.md)，回答界面是什么、怎么动、怎么算做对，不写本仓库的框架、文件和服务名。本仓库的实现是规格的第一个复现者，必须通过规格包的验收。
2. **复现范围到界面与交互。** 规格包用示例数据渲染，不连后台。与 Host 的通信由协议 spec 拥有，规格包只引用。
3. **结构化为主。** 组件、界面、流程用 YAML 描述，文字只写取舍理由。数值只出现在 Token 源中。
4. **所有视觉维度分三层。** 原料刻度 → 用途角色 → 组件。组件和页面只引用用途层；全局旋钮只改原料层。颜色已经如此，圆角、阴影、模糊、文字层级照此补齐。
5. **五个机制由检查把关**，存量进基线只减不增：分层引用、文字层级与对比度下限、材质、组件外观只走变体、对齐参考有据可查。
6. **用真实交接检验。** 定期只把规格包交给新 Agent，在空项目中复现一个模块；未通过的验收追溯到规格缺口，修规格而不是修复现代码。一次通过率是规格质量的衡量。
7. **先试点再推广。** 输入框（组件、首页与对话两个界面、发送—运行—停止流程）先走完整闭环，一次通过率明显时再推广到其余模块。

## 已定取舍

| 问题 | 选择 |
| --- | --- |
| 文字下限 <!-- rule:R-DECISION-023 --> | 用户需要阅读的文字（含过程子步骤）对比度不低于 4.5:1；3:1 只用于时间戳、占位提示等不读也不影响操作的文字 |
| 合并一次性数值 | 允许 1–4px 的外观变化，每处在 PR 中列出并附亮暗截图 |
| 模糊范围 | 只用于窗口栏与浮层（菜单、弹窗）；输入框、卡片、列表重复项用实色加阴影；系统减少透明度时改用实色 |
| 圆角组织 | 组件只认用途名，九档刻度只做原料，另设内部圆角倍率，不开放给用户 |
| 参考截图 | 只提交本产品的标准截图；外部产品的截图不进仓库，对齐处在 Token 源中记录对方变量名与值 |
| 位置 | 规格包放在本仓库 `design/spec/`，与代码一起修改和检查；稳定后再评估是否独立 |
| 分工 | 检查与基线先行；后续阶段写成任务交给实现 Agent，逐步审查 |

## 代价与护栏

<!-- rule:R-DECISION-024 -->规格与代码两处维护，容易重新长成大量规则。护栏：能从代码生成的（组件清单、截图）不手写；Token 数量与规格篇幅设预算，只减不增；动效节奏和手感不写成规格，用录屏参考并由人验收。截图对比需要固定字体与运行环境，基线更新随 PR 说明。

## 重新评估

<!-- rule:R-DECISION-025 -->输入框试点交接后一次通过率低于一半，或规格维护成本明显高于收益时，退回只保留分层 Token、标准截图与通用验收，不继续扩展结构化规格。
