# Find and manage plugin resources

Users leave a task to find plugins, inspect their details, adjust the enabled scope, and return to their task. PluginCenter owns production navigation. Core owns management results and receipts.

## Find and inspect

Search filters the current marketplace or resource category. No results preserve the query and offer a clear action. Returning from a detail preserves the category, query, list position, and a suitable focus target. Loading has a text indication and does not appear as an empty catalog.

Catalog, connection, and Hook reads remain independent. An optional read failure retains the successful catalog and identifies the unavailable facts. Late responses belong to their original project and read generation. Hidden pages cannot take focus.

## Manage and recover

Installation, enabled scope, and connections are independent facts. Installation automatically verifies the exact source, revision, and digest. MCP execution and Hook definitions require separate authorization. The page shows the scope being changed.

Management uses the existing submission path. Pending actions prevent duplicate writes. Failure retains the target and a next step. Unknown results retain the original request identity and allow an explicit read of its receipt. They never trigger automatic replay.

## Return to the task

Returning is navigation. It preserves the project, task, unsent draft, and available reading context. Focus returns to the task input. Opening another task uses the existing navigation and error handling.

## Snapshot and component status

The plugin center reads the Rust Store through the packaged CLI before starting project Core. User reads need no selected project. Project reads take the workspace from Main. The page shows the read scope, revision, and observation time. Offline reads do not claim runtime readiness.

The read hook owns catalog and detail generations. A pure presentation chooses one primary status and next step while preserving MCP, authentication, and Hook facts. Optional Hook review does not block installed Skills. Both entry points share resource navigation and the same detail. An unresolved receipt retains its original identity while users browse another plugin or project.

## Ownership and evidence

PluginCenter owns resource navigation and management feedback. usePluginCenter owns reads. PluginInstallReview owns installation review layout. PluginOverview presents the primary status. Main and Core own configuration and submission receipts. SettingsSearchInput owns the shared search and clear controls.

Real desktop acceptance uses isolated local packages and a deterministic model. Remote marketplaces, OAuth, real providers, packaged applications, and all custom themes require separate evidence. Local captures do not approve a visual baseline. Current admission and evidence limits remain in the [GUI pattern catalog](../../clients/gui/design-system/patterns.md) and [Base](../../clients/gui/design-system/base.md).

## Templates, configuration, and development

Commands retain the plugin namespace, fixed component identity, and raw arguments through ordinary message submission. Agents select imported Profiles for a draft. Configuration saves patch named fields. Empty password input keeps a saved secret; clearing is explicit. Main owns credential creation and public snapshots omit private references. New shared secrets require each project Core to reload its trusted launch inputs. The current project has an idle drain and reload action.

Explicit development links publish immutable snapshots for later turns. Active turns retain their admitted snapshot. Static doctor results and runtime diagnostics remain separate facts. Required configuration and Agent publication failures appear in the primary next step while enabled Skills remain visible.
