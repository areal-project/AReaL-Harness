# 反馈与恢复

`R-RECOVERY-001` 只有需要用户决策或采取行动时才通知。新增或修改提示前先问：“如果我看到这个，我会怎么做？”如果只能等待、关闭提示或什么也做不了，就不发通知；不能为保留通知而增加无必要的按钮。系统可自行处理的状态安静处理，进度和结果按需在原位置呈现。本页维护通用状态的展示与动作约束。请求与审批的业务含义见[控制与审批](../people-and-agents/control-and-approval.md)，实际恢复保证由原执行契约决定。

## 状态必须先于样式决定

| 状态 | 展示与动作 |
| --- | --- |
| 首次加载 | 所属区域显示加载状态；无假数据，无可误触操作 |
| `R-RECOVERY-002` 刷新 | 保留已确认内容，局部标识刷新；请求失败时旧值不伪装为新结果 |
| 空 | 说明为何为空；只有存在可用下一步时提供动作 |
| `R-RECOVERY-003` 提交中 | 防重复提交，保留动作标签/草稿；只禁用受影响动作 |
| 成功 | 显示权威回执后的当前值；必要反馈就近出现 |
| `R-RECOVERY-004` 失败 | 明确原因及可行恢复，保留输入；无条件重试不作为默认。每个错误码登记一个动作与能否自动重试。**检查：** `clients/gui/renderer/src/errors/errorCopy.ts` |
| `R-RECOVERY-005` 待确认 / UNKNOWN | 与失败、成功分开；查看原请求，不以新身份重放。结果未知有单独的文案，不落到通用失败。**检查：** `clients/gui/renderer/src/errors/errorCopy.ts` |
| `R-RECOVERY-006` 不可用 / 无权限 | 显示真实原因与适用入口，不生成虚假开关或无效按钮 |

## 反馈的范围

`R-RECOVERY-007` 反馈绑定受影响的任务、字段或资源。局部问题保留其他可用内容，不用全局失败遮住已经确认的结果。反馈同时使用可理解文字，技术详情按需展开。成功、结果刷新和计量结算分别表达，不因后续刷新失败推翻已知结果。

## 短时通知

`R-RECOVERY-009` 必须打断用户且有明确处理入口的提示采用顶部居中的Toast：info、success、warning、error分别使用语义颜色和图标，默认5秒后消失，支持手动关闭；悬停或键盘聚焦暂停剩余计时。实际实现与无障碍合同见[NotificationToast](../../clients/gui/packages/ui/src/components/notification-toast/notification-toast.md)。通知消失只关闭提示，不删除草稿、原始结果、详情或恢复动作；任务状态与可核对事实由原所有者保留。

## 同窗口重载后的阅读连续性

`R-RECOVERY-010` 恢复任务时保留未发送草稿，并从权威快照重新附着原执行，不重放提交。对正在阅读历史的用户，当前仍可用的正文段落也是恢复对象。新输出保持在原任务中，只有显式返回最新后才恢复跟随。等待历史补齐不能覆盖用户之后的导航。

同一主窗口的 Renderer 重载与崩溃后显式重载已有真实 GUI 证据，见 [E-RECOVERY](../archive/gui/base-evidence.md#e-recovery)。阅读检查点的所有者、存储边界与排除范围见 [Messages 阅读合同](../../clients/gui/renderer/src/Messages.md#同窗口-renderer-恢复阅读)。完整应用重启、未加载历史与过程展开状态不在本次范围内。既有进程内外观切片证据不能替代此项验收。

## 统一短时反馈与待确认状态

`R-RECOVERY-012` 需要用户处理的短时通知采用NotificationToast，并提供核对或设置等必要动作。普通成功、后台处理中和自动恢复不弹通知；字段校验与局部读取失败在原位置保留原因及恢复入口。过期历史请求按视图版本失去展示资格，新视图成功后清除旧错误。默认5秒消失，悬停/聚焦暂停；同一requestId在多个展示位置只出现一次。默认只给简短事实和必要动作，不展示请求ID、协议错误或多层“查看详情”卡片。

`R-RECOVERY-013` 通知消失不清除UNKNOWN、持久请求或草稿，也不启用重复写入。真实待确认的Composer用小标识提供按需核对入口。恢复依据原请求回执和原Worktree就绪记录，不能因同项目另一条待确认请求阻塞已知成功的会话打开；也不能把无回执当成成功。定时任务新建沿同一原创建身份恢复，原Worktree已ready就打开原会话，不另建任务。
