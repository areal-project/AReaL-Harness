# 定时消息的会话目标

状态：核心产品决策已确认，尚未实现；创建、编辑和取消边界仍待定。本设计调整定时安排一律新建会话的原有规则，不改变 Core 对调度、历史和执行记录的所有权。

## 决策与取舍

新建定时安排默认复用创建安排时的当前会话。到点自动发送消息并启动 Agent；消息带有定时来源标记，回复延续在同一对话中。绑定的是固定会话，不是触发时界面选中的对话；实际开始执行时使用最新上下文，遵循普通会话的历史与压缩规则，而非保存创建时的历史快照。

设置入口提供“每次在新会话中运行”开关，新安排默认关闭。打开后每次执行新建独立会话，不自动继承来源会话或之前执行的聊天历史；不提供首次新建后持续复用的第三种模式。旧安排保留原执行方式，不因默认值变化而自动改绑。完成不抢占当前界面焦点。

复用会话使连续跟进能利用最新讨论，也会让后续人工消息和之前执行影响下一次工作。独立新会话适合不需要历史的周期检查。两种模式都保留安排身份和每次执行记录；会话数量不能代替执行次数。新会话不隔离工作目录或文件状态。

## 已确认的冲突与失效规则

- 目标会话正在处理其他工作或等待审批时，不打断、不并发注入；显示等待会话空闲。同一安排最多保留一次待发送，等待期间的新触发合并。
- 如果本安排上一轮已经启动且未结束，沿用跳过后续触发的规则，不额外积压下一轮。尚未发送与已启动执行必须区分。
- 归档只收起会话，不暂停安排，也不自动取消归档。删除目标或失去访问权限后停止投递并展示原因，要求用户处理，不静默切换到新会话。
- Core 与桌面 Host 恢复在线后，错过的触发至多合并补发一次；显示原计划时间与实际启动时间。主动暂停的安排不补发。
- 已开始但被中断的执行需要用户明确恢复，不能自动重跑。审批沿用现有权限边界，不因定时发送扩大授权。

## 实现约束

当前创建工具只接受目标内容和时间规则；来源会话与执行锚点要求分离，执行路径为新的 Run 创建 Thread。增加目标选择应在 Core 的安排契约与准入边界实现，不能只改 GUI，或把来源会话字段直接当作执行目标。

实现需明确区分安排来源、绑定的目标会话与每次执行身份，并保留幂等受理、版本冲突检查和恢复收据。普通人工消息与定时执行共享目标时，停止或删除安排不能误停无关人工工作；具体控制语义待下节确认。

相关实现入口：[创建工具](../../core/engine/src/task_mode/schedule_tools.rs)、[桌面调度](../../core/engine/src/task_mode/desktop_schedules.rs)、[Task 类型](../../core/protocol/src/tasks.rs)。当前已实现的契约仍见 [Task API](../api/tasks.md)，本设计不表示运行时已支持该能力。

## 尚待确认

- 从定时页面新建且没有来源会话时，如何建立绑定的会话。
- 设置开关的编辑生效边界，以及是否允许选择任意已有会话。
- 暂停、删除、取消一次待发送和停止本次执行之间的关系。
- 多个安排及人工消息同时等待同一会话时的顺序。
- 新开会话模式下任务内容是否需要补全为独立指令，以及运行配置的继承规则。

## 实现后的验收边界

需验证同一会话连续两次定时发送与人工续聊、新会话模式的历史隔离、忙碌与审批等待合并、重连不重复发送、归档不暂停、失效目标不改投、旧安排不改变行为。编辑和取消的用例在对应决策确认后补充。文档检查不替代 Core 行为回归或真实 GUI 交互验收。
