# 独立开发环境服务设计

> 已被[共享 Host 实施规格](../development/shared-host-spec.md)取代：不再采用“GUI 托管 / 后台托管”双模式；受控重启、提交 journal 单 writer 切换和迁移回执改由新规格定义。本文的权威边界、Host 身份、显式启动项目、停止意图和不重放规则仍由新规格沿用。

状态：目标设计，待实施。本文确定 Desktop Service 的演进边界，不表示后台独立启动、GUI 退出后继续执行或手机完整开发路径已经交付。分阶段交付与证据门槛见[实施计划](../development/environment-service-plan.md)。现行协议仍以[本地服务](../api/local-service.md)、[桌面 API](../api/desktop.md)和 [Remote API](../api/remote-control.md)为准；新增能力须在对应阶段更新契约后才能启用。

## 1. 目标与范围

Mac 是执行机器，代码、Git、开发工具链和模型凭据留在 Mac。手机通过现有 Relay 操作已授权项目；Mac GUI 通过本机后台访问相同项目和会话。退出 GUI 后，已启用的环境服务继续提供执行和远程访问。重新打开 GUI 后接续同一权威状态。

典型验收路径：本机启用并配对 → 手机选择已授权项目 → 必要时显式启动项目 → 新建会话并提出代码修改 → Mac 执行和测试 → 手机回答问题、审批和查看 Diff → 继续修改或请求提交 → Mac GUI 打开同一会话。

“与桌面等价”指相同工作区、Thread、权限、执行系统与命令语义，不要求把桌面窗口和全部编辑器搬到手机。用户口语中的“开发任务”首先映射普通 Thread/Turn；不为远程开发新建另一套 Task。既有 Task/TaskRun 保持调度含义，WorkItem 仍是概览投影。

首发范围是单个已登录 macOS 用户下的独立后台、现有 Relay 和已登记项目。沿用本机启用与配对，不增加 T3 Connect 式云账号、设备目录或托管隧道。SSH/WSL/Docker 远端部署、跨环境 Agent 委派、登录前服务、移动终端和浏览器接管不属于首发依赖。

## 2. 当前基础与演进缺口

| 当前所有者或入口 | 已有职责 | 演进要求 |
|---|---|---|
| `service-main.cjs` / `service-protocol.cjs` | 无窗口 Desktop Service，装配 Backend、Remote、通知和电源适配 | 复用进程与业务装配，增加独立于 GUI 的受管启动 |
| `application-owner.cjs` / `main.cjs` | GUI owner、生命周期管道、退出时后台停止协调 | 独立模式下 GUI 只释放客户端资源；后台死亡仍触发受监督清理 |
| `service-client.cjs` / `service-config.cjs` | 服务发现、部署身份、启动、配置及数据目录选择 | 区分附着与启动，保留同一环境单写者、版本和配置校验 |
| `local-service.cjs` / 公共 `areal service` | 按规范工作区定位并管理 Core | 延续公共生命周期入口，不直接接管 Core/Runtime PID |
| `remote.cjs` / `remote-session-commands.cjs` | 配对、授权、命令关联、会话操作 | 保留 Gateway 边界，增加明确授权的项目启动能力 |
| `remote-session-controls.cjs` | 配置、Goal、队列和 steer 映射 | 复用 Core 语义，不创建移动执行循环 |
| `submission-recovery.cjs` / `project-connections.cjs` | 收据核对、连接恢复与代际保护 | owner 迁移后保留原记录、UNKNOWN 和身份约束 |

以上文件均位于 `clients/gui/app/src/core/`。当前 `watchApplicationLifetime` 要求 GUI 生命周期管道；`requestQuit` 协调停止连接的后台。关闭窗口与退出应用不能混为一谈。[ADR 0008](../adr/0008-remote-host-ownership.md)描述了保留后台 Remote 的方向，但不能用它证明当前应用退出路径已经独立。Remote 设计文档中的早期只读切片也不代表当前全部能力；写命令范围以源码和 Remote API 为准。

独立环境服务首先是现有 Desktop Service 的生命周期和部署形态演进。首版继续复用 Electron 后台、系统凭据和订阅适配，不另建并行 Agent daemon，不要求先迁移目录或重写为 Rust/Node 服务。

## 3. 拓扑与权威边界

手机的业务路径是“手机 → Relay → 环境后台的 Remote Gateway → 工作区 Core → Runtime”。桌面路径是“Renderer → 窄 IPC/Main → 本机环境后台 → 同一个 Core”。手机路径不经过 GUI Renderer。两条入口可以使用不同适配器，业务准入和结果在 Core 汇合。

| 组件 | 拥有的状态与职责 | 不承担的职责 |
|---|---|---|
| GUI Renderer / 手机 | 草稿、连接状态、可重建投影、用户操作 | 持久执行权威、自动重放未知写入 |
| GUI Main | 窗口、窄 IPC、原生 UI 生命周期、本机管理入口 | 独立模式下后台和 Core 的生存租约 |
| 环境后台 | Host 身份、设备授权、项目登记、凭据适配、Gateway、Core 发现/激活、已有复合命令关联 | Agent 循环、第二份会话历史、第二套 Task 调度器 |
| Core | Thread/Turn、模型循环、Goal/Task/TaskRun、配置、业务准入、审批、权威收据和历史 | 云端连接发现、GUI 窗口、OS 服务注册 |
| Runtime | 工具执行权限、操作事实、子进程和资源清理证明 | 会话编排、设备配对、项目目录 |
| Relay | Host 登记和连接路由元数据、限流、加密记录转发 | 业务授权裁决、模型凭据、任务正文持久化、离线代执行 |
| macOS 服务管理器 | 用户级后台启动与退出监督 | 决定业务请求是否受理、证明工具已经清理 |

“环境服务”是产品边界，不新增一层拥有全部业务状态的服务。项目登记和连接映射由后台持有；执行和历史保持在各 Core。Relay 暂时不可用只影响远程可达性，不把 Mac 的运行状态改成失败，也不影响可用的本地客户端。

### 身份和隔离

复用持久 Remote Host 身份作为远程环境标识。产品可显示“开发环境”，协议内部不为改名再造一个 Environment UUID。未启用 Remote 的本机实例继续使用原服务发现身份；首次启用时由现有身份所有者持久创建 Host 身份。

| 标识 | 生命周期与用途 |
|---|---|
| Host 身份 | 绑定规范数据 home 和 OS 用户的授权域；网络、Relay 地址和后台重启不改变它 |
| 后台/Gateway generation | 一次后台运行与连接准入；重启使旧连接失效 |
| Project ID / 工作区绑定 | 后台登记映射到规范工作区及 Core 数据目录；不能用 Relay room 或 GUI 窗口推导 |
| Core serviceId / generation | 定位权威实例及本次运行；沿用现有核对规则 |
| Thread / Turn / Task / TaskRun | Core 的业务身份；切换客户端不创建副本 |
| Runtime epoch / 工具 Host generation | 执行与宿主能力归属；不能以 Gateway 在线代替有效性 |

一个环境聚合多个项目，各执行工作区继续使用独立 Core 和受锁保护的数据目录。逻辑项目和 worktree 复用既有映射；不同 worktree 不共享执行状态。PID、端口和 `service.json` 只是发现线索，附着还需验证认证身份、锁、部署兼容性和 owner。

首版不支持把同一持久身份目录复制到两台活跃机器。独立安装或开发 worktree 使用隔离 home；身份重置需要重新配对。密钥轮换须有单独的认证迁移契约，不能静默替换 pin 并保留旧授权。GUI 与后台应用身份可以不同，但首版保留现有用户数据、钥匙串访问和签名身份关系。

## 4. Desktop Service 的独立运行模式

### 启用与单一 owner

未启用独立环境时，保留当前 GUI-owned 生命周期。用户在本机启用“后台开发环境”后，使用用户级 LaunchAgent 启动现有后台应用入口；服务注册和远程网络启用分别保存，停用 Relay 不隐含停止本机执行。

同一 home 同时只允许一个执行 owner。新模式的 owner 表达稳定环境归属和本次后台运行代际，不把 `appRunId` 当环境身份。GUI 只是有权限的本地客户端；独立后台持有到受管 Core host 的监督链。具体字段须在实施阶段同步 JS/Rust owner 解码、CLI 参数与公开生命周期契约，不能只放宽一端校验。

LaunchAgent 的启动、重启和退出不替代现有 Core 锁、受理回执和清理协议。后台死亡后，继承管道/launcher 仍负责结束其拥有的执行资源；后继后台等待可证明的清理、锁释放和合法恢复条件，不能依据旧 PID 消失就启动替代。GUI-owned 模式的崩溃清理继续有效。

### 用户操作与运行行为

| 动作 | 独立模式目标行为 |
|---|---|
| 关闭窗口或退出 GUI | 释放 GUI 专属资源与订阅；后台、Remote 和已受理工作继续 |
| 手机断网或切后台 | 释放观察连接；Mac 继续工作；重新连接后同步状态 |
| 显式停止环境 | 先记录停止意图并阻止自动拉起，再通过既有 drain 路径停止；忙碌时默认拒绝，取消需明确确认 |
| 重新启动环境 | 清除明确停止抑制后，由服务管理器启动；核对原状态，不重放中断工作 |
| 后台崩溃 | 受监督清理与有界重启；重复失败进入可诊断状态，不忙循环 |
| GUI 崩溃 | 仅清理该 GUI 所有的资源，不触发后台退出 |
| 系统注销、休眠或关机 | 不承诺可达或执行继续；恢复后重新观察与核对 |

LaunchAgent 仅承诺用户登录会话内运行。锁屏与系统休眠分别验收：锁屏不等于后台退出，但钥匙串和需要用户交互的原生能力可能不可用。活动工作的电源策略继续由既有 `SharedPowerMonitor` 负责；不通过全局禁用休眠扩大承诺。

启动策略区分“异常退出重启”“用户停止”“更新排空”。不能使用无条件保活覆盖用户停止。停止失败、部分停止、清理未知都必须保留诊断和原操作引用；禁止显示为已停服。未启用独立模式时，GUI 的既有退出语义不变。

### 登录、凭据和原生能力

LaunchAgent 不继承交互 shell 的环境。后台启动配置固定可信可执行路径、规范 home、配置路径和受支持的工具环境；复用现有工具链与代理解析，敏感值不写入 plist、命令行或诊断。不能依赖首次 GUI 启动时临时注入的凭据或 PATH。

已有 `safeStorage`、Provider/订阅转发、网络代理和凭据刷新归环境后台。登录后无法解密或续期时返回真实不可用状态，由本机设置恢复；不得使用空凭据启动后再把故障解释为任务失败。首次登录和系统权限确认仍通过明确的本机交互完成。

原生能力按实际所有者分类：文件/命令和无需 GUI 的现有工具由 Core/Runtime 与后台继续提供；WebContentsView、窗口预览和 GUI 专属终端在窗口关闭时释放。依赖交互桌面、TCC 授权或可见页面的工具只有在其真实 Host 就绪时才发布能力；缺失时明确报告不可用，不自动弹窗抢焦点。首版不迁移整个 Browser/Computer 所有权。

### 调度与项目激活

保留现有 schedule owner 的项目发现与激活职责，Core 继续独占触发、漏执行处理、重叠准入和 TaskRun。独立模式下这些职责可以随后台存活，不随 GUI 退出消失；这是需要专项验收的行为变化。

登录启动只恢复已显式启用的后台执行策略与既有调度所需项目，不启动全部历史项目。用户显式停止的项目必须被激活协调器和手机入口共同尊重。重启不会自动恢复被 Core 暂停的中断 Goal、队列或执行；未来安排仍按 Core 的恢复规则处理。

## 5. 项目与开发操作契约

### 项目可用性

环境在线、项目可用、模型可用和 Turn 正在执行是不同状态。项目列表应能表达未启动、正在启动、可用、不兼容、配置/凭据受阻、清理待核对；缓存只能标为上次观察值。

手机只访问本机登记并授予当前设备的项目。首版不允许手机传任意绝对路径、注册新目录或更换数据目录。为已登记项目增加显式启动动作：

1. Gateway 验证当前设备、项目范围及单独授予的启动能力。已有 `submit` 授权不自动获得启动权限。
2. 接收 commandId 和预期授权/后台代际，持久关联操作意图，再通过现有服务启动所有者调用公共 `ensure --no-auto-restart`。
3. 在工作区锁下复用兼容实例或启动新实例；配置/二进制/权限冲突要求本机处理，不静默升级、取消任务或扩大权限。
4. ready 只在认证身份与能力核对后发布。启动结果未知时查询原启动操作及精确实例，保留未确认状态，不盲目再启动。

启动操作可能发生在没有 Core generation 时，不能强行使用现有要求在线 Core 的写 context；应在 Remote API 单独定义环境/项目生命周期命令的目标和回执。新方法名、字段和版本由实施阶段落到 schema，本文不声明其已经可调用。被动重连、刷新列表与创建会话均不隐式执行启动。

### 会话与结果闭环

手机继续使用现有会话创建、发送、配置、队列、Goal、审批、停止和只读 Review 入口。桌面和手机的适配器共同遵守 Core 规则，不为统一入口把全部桌面私有 RPC 暴露给 Remote。客户端按方法/能力协商启用操作，不依据版本字符串猜测支持。

多端可以同时观察和提交。配置携带预期 revision，停止绑定确切 Turn，审批绑定交互及参数摘要；冲突返回新状态供用户决定。普通会话不增加全局“手机独占控制权”。

首发结果闭环是 Diff/必要文件上下文、工具输出和测试结论，再发消息要求修改或提交。测试结果来自实际执行证据，Agent 文字总结不能冒充通过记录。专用 Git 提交按钮、文件编辑、worktree 创建和终端是后续能力；增加时必须定义操作目标、授权、审阅版本和副作用回执，复用既有 Git/worktree 所有者。

### 传输和恢复

Direct 与 Relay 继续共用业务命令和权限。手机与 Host 均主动连接 Relay，Noise 身份 pin、应用授权和 TLS 链/域名/有效期校验保留。Relay room/channel 只用于路由，不作为环境身份或权限。若 Relay 同时发布 Web 客户端，静态代码发布源仍属于信任边界。

手机重连先握手、读取授权和能力，再建立权威快照及有序增量；缺号、换代或背压后重建基线。已有命令 journal 保存原 commandId、语义摘要及 Core 请求关联。断线、超时、空回执和新 generation 都不能证明未受理；只有匹配的权威回执或严格负面证明可结算 UNKNOWN。该规则也覆盖项目启动和生命周期操作。

设备撤销/缩权在 Gateway 阻止新操作、失效订阅及后续内容发送，不能等客户端主动刷新。已经被 Core 受理的工作不因设备撤销隐式取消；本机用户可通过明确的停止操作处理。项目范围授权不是 OS 沙箱；Agent 的有效工具和执行权限继续由 Core/Runtime 限制。

## 6. 数据接管、兼容和更新

### 原地演进，避免第二份状态

保留现有 service home、Core registry、工作区数据绑定、项目/worktree 索引、Host 密钥与 grants、Provider 密文、submission pending/outcomes 和操作回执。不把历史导入新的环境数据库，不移动 Core Store，不复用其他开发 worktree 的状态。

仅为新运行模式增加必要的受版本约束的启动/owner 配置和转换回执。注册信息记录选定应用位置和部署身份；发现描述与 PID 可重建。转换回执引用原 home、旧 owner/代际、目标部署、已完成步骤及结果，复用生命周期持久化所有者，不创建通用工作流引擎。

### 安全切换步骤

1. 在本机预检后台应用入口、签名/凭据可用性、目录绑定和版本兼容；用户明确授权安装登录服务。
2. 在既有生命周期串行边界保存转换意图，停止新准入与自动激活。存在运行工作时等待或拒绝转换；取消由用户另行确认。
3. 通过现有停止路径结算旧后台及其拥有的 Core/Runtime，核对真实退出、锁释放与清理证明。保留所有历史、草稿和 UNKNOWN。
4. 服务管理器启动新 owner，读取同一数据目录，完成身份/兼容/凭据预检。需要格式迁移时，在原写锁下备份并按各 Store 契约迁移。
5. 发布新就绪描述；GUI 和手机重新附着，重新协商能力、读取快照并核对旧请求。
6. 持久完成转换。响应丢失时只查询原转换记录；不得让旧启动器与 LaunchAgent 同时争抢 home。

转换中断后，本机恢复入口先核对回执、OS 注册和实际进程状态。若新 owner 已启动，附着或报告不兼容；若旧执行仍未清理，继续阻塞。只有确认无活跃写者、清理完成且数据格式可兼容时，才允许用户恢复旧模式。不能把“新 GUI 连不上”当作回滚证据。

### 升级与停用

独立后台与 GUI 分开协商版本。旧 GUI 不得因无法识别新 owner 而终止或接管它；实现前必须验证旧客户端的拒绝行为。应用更新由同一生命周期所有者协调，先保护活动工作，再停止、核对、切换应用资源并重新握手。后台仍在使用主包资源时不能覆盖包体。

停止服务与卸载登录注册分别处理。停用独立模式采用同样的排空和单写者交接；保留用户数据及设备授权，除非用户另外选择撤销。无活动工作但 Remote 开启的情况应允许本机显式停服；不能让旧的“Remote 开启即忙碌”判断永久阻止维护。

二进制、部署、权限和持久化格式的兼容性分别检查。仅在旧版本可读且新 owner 已停止并完成清理时允许降级；不承诺跨不可逆 Store 迁移自动回滚。签名、公证、LaunchAgent 可执行路径和主包更新一致性属于安装包验收，源码测试不能替代。

## 7. 故障与可观察结果

| 故障 | 用户可见状态 | 权威恢复依据 |
|---|---|---|
| Relay 不可达 | 远程离线，任务结果未观察 | 重新连接 Host 后的 Core 快照 |
| 写入后响应丢失 | 待核对，保留草稿关联 | 原 commandId/请求收据，不自动重发 |
| GUI 退出/崩溃 | 环境仍在线；GUI 原生资源按归属关闭 | 后台身份和真实 Core 进度 |
| 后台异常退出 | 环境恢复中；中断工作不标成功 | owner 回执、清理证明、锁及 Core 恢复状态 |
| 某项目配置失败 | 该项目不可用，其他项目继续 | 对应项目认证状态和配置诊断 |
| 手机与桌面竞争 | 已受理或明确冲突 | Core 准入锁、revision 和确切目标 |
| 系统睡眠/注销 | 环境不可达 | 登录/唤醒后的握手、授权与权威快照 |
| 更新或转换部分完成 | 维护待核对 | 持久生命周期意图与实际实例，不推断全部回滚 |

诊断沿现有渠道携带 Host、后台代际、Project、Core serviceId/generation、commandId、受理/结算状态及脱敏错误。连接健康、请求受理和执行成功分别显示；不记录凭据或未授权业务正文。

## 8. 设计取舍与实施入口

采用现有 Electron 后台可复用凭据、订阅和原生适配，代价是首版仍需桌面运行时与用户登录会话。复用每工作区 Core 避免迁移历史和权限，代价是后台需要维护多项目可用性。显式启动项目避免被动重连产生副作用，代价是手机可能多一个启动动作。

ZCode 的 Source 身份和连接线路分离、T3 的客户端与环境生命周期分离是参考；不照搬它们的部署或 Provider 架构。参考材料：[ZCode Source Server](https://github.com/zai-org/ZCode/blob/3c5b2276/docs/architecture/r3-source-server-remote-architecture.md)、[T3 Remote architecture](https://github.com/pingdotgg/t3code/blob/c8a606c7b7/docs/internals/remote.md)。实现选择以本仓所有者和验收证据为准。

详见[分阶段实施计划](../development/environment-service-plan.md)。本设计对 ADR 0008 的“复用后台、不另建 Agent daemon”方向做生命周期细化；旧模式及现行 API 在对应阶段完成前仍然有效。
