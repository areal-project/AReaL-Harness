# Workbench service

A3 puts the existing desktop backend under Host supervision. Main connects as a client and continues to provide windows, system encryption, browser views and computer control. See [ADR 0017](../adr/0017-one-protocol-one-ui.md) and the [one-protocol spec](../development/one-protocol-spec.en.md). Domain routing and native capability wiring remain incomplete; this design is not evidence of A3 acceptance.

## Ownership and migration

Worktrees, the library and task catalog share project connections, session lifecycle, write queues and journals. Rebuilding these dependencies per domain would duplicate the backend. Instead, `services/workbench/src/backend-main.cjs` reuses `CoreBackend` and `DesktopService`. Project-local logic can move into Core and cross-project logic into Host later. Moving and rewriting remain separate; remove the old Main path only after its replacement passes acceptance.

Public clients connect only to Host. The backend retains an authenticated private attach listener for Main; browsers and phones do not use it as a business entry point. Host owns project connections and supervision. The backend accesses Core through the finite `core.request` allowlist. Main domain fallbacks also use Host connections bound to their original attachment. Observers and terminals have separate leases, so detaching them does not close another client's project connection. Core/Runtime authority and cleanup responsibilities remain unchanged.

Including `backend` in `areal.oneProtocol.domains` enables Host ownership after restarting the app. Main reads the switch before backend initialization; disabling it retains the in-process path. Data remains in the original GUI directory. Host checks the registered navigation source and Core executable paths. One Host currently owns one backend configuration; a different configuration is rejected rather than silently switching sources.

`CoreBackend`, `DesktopService` and their runtime dependency closure live in `services/workbench/src/desktop`; trajectory and feedback live in `src/domains`, and the library staging writer is built from `src/host-library-store.ts` into CommonJS. Host takeover and the Main fallback load the same implementation through `@areal/workbench-service`. Main retains application configuration, the connection client and the native lifecycle client. Deployment identity includes service sources, split contracts and the generated writer. The service package is an explicit GUI workspace dependency, staged with its resources and dependency closure inside `app.asar`; it does not rely on implicit module resolution from `Resources/areal-workbench` into a sibling archive.

## Supervision

Host reuses `workbench_route.rs` and `workbench.rs` to supervise analytics and the desktop backend separately:

- Authenticated local control methods `backend.ensure` and `backend.status` start/reuse the backend and return Host generation, PID and backend identity, without private connection tokens. Browsers cannot call them.
- Startup options travel over the private pipe. The child receives a cleared environment with only required variables. The backend retains the user's home and takes data paths from explicit options.
- Release layouts discover `Resources/areal-workbench` in the signed app, verify its signature and manifest, and use bundled Electron in Node mode. Source debug layouts can discover adjacent repository sources and Node on PATH without building a GUI package; release builds do not accept this source discovery path.
- A `ready` frame reports methods and identity within 20 seconds. The first observed exit recovers immediately; subsequent failures within the 10-minute window use 1, 2, 4… second backoff, and five failures within 10 minutes stop automatic restart.
- Main detach leaves the Host backend alive. Host stop closes its pipe; the backend drains in-flight operations and exits, with a five-second termination deadline for that child.
- Restart waits for the old child to end. Cleanup is limited to the retired identity recorded by Host and must not overwrite another backend's `service.json`. Recovery rebuilds observations and snapshots without replaying writes.

## Protocol and receipts

Host and the service exchange newline-delimited JSON over a private Unix socket pair, with `version: 1` and a 64 MiB frame cap. Public clients retain their own protocol limits. A method must be marked `x-owner: workbench` in `schemas/areal-host-protocol-v1.json`, allowlisted by Host and advertised in the service's `ready` frame. There is no generic backend RPC. `lifecycle.dependencies.lifecycleGeneration` projects the current lifecycle generation read-only; worktree deletion nests the original Host stop receipt in the existing desktop lifecycle envelope without changing stop or recovery semantics.

`library.command` accepts bounded organizing operations: rename, pin, sections, move, order, drag-and-drop, read markers, hiding projects and navigation preferences. Requests bind a `sourceId` that must match the running backend, preventing writes into another GUI source. Successful receipts return library state filtered like the navigation read model, without desktop configuration or cached conversation bodies. Host journals admission before side effects and isolates receipts by principal and `commandId`. Identical retries return the original receipt; different semantics with the same ID return `COMMAND_CONFLICT`. Missing authoritative replies remain `submissionUnknown`. `command.read` queries the original ID, without replay or fallback to Main. UNKNOWN entries that the backend cannot resolve remain unknown, never successful.

These domain methods currently require a local loopback connection. Ordinary browsers receive explicit scopes through authenticated local `web.approve`; existing approvals default to `observe`. The shared UI enables organizing based on library capability without enabling sending, archiving or native entry points. Library organizing and analytics import require `manage`, which does not also grant submission or approval. Browser receipts are device-specific and revocation invalidates the connection. Cross-project domain authorization for remote Noise devices is not connected yet; local grants must not bypass remote project scopes.

`worktree.read` and `worktree.command` reuse existing listing, settings, environment configuration, creation, reading, opening, cancellation, actions and deletion, retaining domain `requestId` and lifecycle records. Host receipts bind method, source and parameters; an ID cannot be reused for another operation. `tasks.read` reuses list, preview, observe and inbox. Preview retains published/unobserved semantics without waking stopped Core processes. Both domains currently require manage for local browsers; remote project-scoped authorization is still pending.

`manage.read/command` reuse the backend implementation and expose only bounded management operations. Reads cover task reading, schedule context and preview, task lists and inbox, run history, plugins (list, detail, components, hooks, MCP), configuration (server status, profile, skill), process lists and output, executions, and Workgroup/Workflow. Writes cover task editing, pausing, resuming, cancellation, deletion and stopping an in-flight Run, thread archive, resource closure, plan update, permission revocation, idle drain and GC, execution apply and cancel, Workgroup cancel, plugin and marketplace management, process start and terminal writes, and context compaction. Backend execution-owner resolution and Core receipt validation are retained; when the client omits the domain `requestId`, Host supplies its `commandId` to retain the original query identity. Terminal writes and context compaction admit work and additionally require `submit`; execution cancel, Workgroup cancel and Run stop additionally require `interrupt`. Creating tasks, replying to questions, running now and creating sessions wait for the Host tool forwarding path. Plugin archive import and archive selection are native file pickers; plugin credentials and connections, hook and tool approvals, MCP forms and apps, GenUI sources, path- or URI-addressed execution artifacts, provider settings (separate `providers` domain) and goal edits are not exposed through manage. Results are validated as a structural union; manage is not a generic RPC entry point.

`providers.read/command` reuse provider listing, discovery, probing, saving, application, default selection, and removal, bound to local browser manage authorization and source ownership. Browsers cannot use `revealKey`. The Host journal stores operation identity, semantic digest, and results, never raw parameters. Draft API keys travel only over the authenticated connection and private backend pipe; HostVault remains the owner of persistent credentials.

With the `pages` domain enabled, `pages.command` and `pages.resource` reuse the existing MCP Apps/Gen-UI host, with each page session owned by an authenticated Host connection. Host supplies the connection identity; page tokens cannot cross connections, and events reach only the original owner. Disconnect cancels existing requests before settling late open replies and page-tool leases. It does not register a native `computerHost` or journal page parameters. Reconnection must reopen the original source; it cannot adopt old tokens or replay unknown page requests.

Before admitting send/enqueue and steer requests from local `gui-write-v1` connections or remote sessions whose paired source matches the backend, the private `input.prepare` method reuses the backend `genUiText` state projection. Only modelContent enters the effective input; privateContent stays in page state. Host deduplicates the original request and freezes the prepared input in the existing journal, so duplicate commands do not read state again. Legacy entry points without a bound desktop backend retain their behavior; a bound backend becoming unavailable causes an explicit failure. Host project IDs first resolve through the bound source's authoritative bindings to backend aliases; the backend then resolves the thread execution project.

Private `execution.prepare` reuses the page host’s provider and tool preparation; Host dispatches Core send/enqueue and steer requests through its shared connection. Worktree creation still uses a thin backend adapter to join native Host preparation and binding, and the backend’s Core requests also pass through Host. Creation shares preparation with `createThreadInProject`; sending reuses `ensureBrowserTools` and `browserEntrypoints`. Host freezes the original Core requestId and parameters in its journal; the backend consumes a one-shot page-host handle bound to the original Host connection, project/thread, Core generation, client and native owner. Failures and disconnects never replay it. Browser discovery and page claims use the existing Main attach callbacks; the original Host connection disconnect revokes its entries, discovery plans and claims. Native window behavior still requires desktop acceptance. Remote ordinary creation, send and steer use this same execution path, retaining device, project and submit authorization. Matching a project alias alone cannot select another source’s backend. Connection termination revokes backend entries; published client request shapes and permission presets remain unchanged. A definite rejection after tool-host disconnect maps Core’s `TOOL_HOST_UNAVAILABLE` reason to Host `CAPABILITY_UNAVAILABLE`, retaining the original command receipt without automatic replay.

Resources travel over the authenticated WebSocket in chunks of at most 192 KiB, with an 8 MiB limit per resource. Public `/host/pages/proxy` contains only fixed proxy code. Outer and inner frames are sandboxed without same-origin permission; page HTML and resources have no public HTTP route. Gen-UI bundled resources are read through the original allowlist and inlined, while the page retains its original CSP. This phase supports only local loopback connections with `gui-write-v1` and manage; manual MCP App opening and page JSON-RPC requests additionally require submit. This conservative authorization does not yet support ordinary submit-only devices or remote Noise. Native file selection and opening remain shell capabilities.

## Rust domain implementations and rollback

The desktop backend receives `rustDomains` from `areal.oneProtocol.domains`: `library-rust`, `execution-rust`, `tasks-rust`, and `worktree-rust`. Restart the backend after changing these implementation selectors. The existing `backend` takeover flag and domain entry points remain available. Disabling a Rust domain selects the previous path without replaying unresolved commands. Environment acceptance is still required before retiring a previous implementation; compilation alone does not establish acceptance.

This table describes ownership with a Rust domain enabled. Previous JavaScript domain implementations remain available when their selector is disabled. Core connection and process ownership always stays with Host.

| Domain | Rust authority | Remaining JavaScript responsibility |
| --- | --- | --- |
| Library | Host transactions apply navigation commands and update unread markers and navigation summaries from Core notifications and authoritative snapshots of observed progress in the same generation, while preserving desktop settings | Settings validation and page projections; read-only cloud ownership and pending-submission facts |
| Execution and recovery | Host owns leased Core connections; Core reconciles original request receipts; Host aggregates lifecycle receipts | Reading windows, page tools, and input-state preparation |
| Scheduled tasks | Core owns tasks and configuration drafts; Host aggregates directories, published previews, inboxes, and observation state | Selected provider input preparation and directory display |
| Worktrees | Core executes Git and process operations; Host owns cross-project ownership, environment configuration, and lifecycle records | Page-tool preparation and result projections |

Page projections merge full Side conversations and execution conversations referenced by the original scheduled Task Runs only from a bound, connected source with the same service generation. Summaries do not substitute for full conversations. Run records retain readable projections without changing the selected conversation. Auxiliary conversations reuse their original workbench history windows for paging; the selected Host conversation retains its Host read context. Their window identities must not be mixed.

Host library transactions read the complete JSON from its original location, validate and modify it synchronously, and atomically replace it. Public navigation receipts still use the same field filter. Desktop settings use bounded compare-and-swap field updates; Host does not interpret proxy or hardware-acceleration settings. Worktree settings and environments use the same library transaction rather than another writer.

Core advertises pre-creation admission through `features.taskPrepareCreate`; Host registers support with `areal/task/host/ready {prepareCreate:true}` only for a GUI-source Core that declares it; CLI sources retain their existing admission path. The capability belongs to the original Host connection. After validating a scheduled task and before persisting or publishing it to the scheduler, Core uses `intent:create` on the existing `areal/task/prepare` callback to have Host check directory authorship and reserve the original creation request and execution anchor. A completed request returns its existing receipt. A lost creation result binds the Task only through the original Core receipt, without redispatch. Empty legacy readiness requests retain their existing semantics.

The fixed shared Scratch retains one Core registration root, with one real direct child directory per scheduled task. When `cwd` is omitted, its child name is the canonical UUID of the original creation requestId. Host checks the source registration against the allocation root and stores the original request, digest, and anchor authorship per child. Existing tasks recover only through a unique matching Core creation receipt; missing evidence never triggers redispatch. Activity in other children is allowed only when bounded complete snapshots establish its ownership and remain stable across status checks. Overlapping directories, unknown ownership, or changing snapshots reject execution.

`worktree.thread.prepare` returns the applied resource profile and revision from the original Core deployment. The backend uses them only to restore its rebuildable projection. While binding the original creation, resource checks still compare the current selection with that deployment. A change preserves the original request and rejects continuation instead of silently restarting Core or rebinding to another generation.

`areal tasks` and `areal worktree` expose native directories over the local Host protocol without GUI or Node dependencies. The default CLI source is `host`; register projects through `areal host` first. Task previews for stopped projects retain published/unobserved semantics; explicit observe requests obtain live state. Private task observation uses existing connections and never restarts a stopped project. Writes preserve domain requestId. Host commandId is separate from a Worktree creation requestId, so opening or cancelling that worktree does not conflict with its creation receipt.

Opening a worktree with environment scripts from the CLI requires `worktree open --agent id@revision` to select a deployed profile that permits thread processes. Existing concurrent-write authorization and process budgets still apply; Host does not elevate permissions. Repeating the original arguments with `worktree --command-id <original ID>` reconciles the admitted command; a new ID must not replay UNKNOWN. Local CLI calls using `--source <registered GUI source>` also support an explicit profile, while requiring the current backend to bind that source and enable `worktree-rust`; otherwise Host rejects the parameter before admission. Browser and remote clients retain the public contract without `agentProfile`.

The decreasing `workbenchConvergeLines` budget covers the library, submission recovery, history observation, lifecycle operations, service protocol, task catalog, task draft, and worktree modules. Other existing JavaScript uses exact retained paths. New and renamed files count by default; neither the budget nor retained-path classification may grow to hide migration code. Methods must still appear in the schema, Host allowlist, and service ready inventory. Private reverse calls are not public RPC entry points.

## Library and analytics

A Host-managed backend always uses Host as the sole writer of `library.json` at its original location. With `library-rust` disabled, the backend stages a document beside it, then calls `library.write` for digest-checked replacement; conflicts trigger reread and recomputation. When enabled, navigation changes execute directly in a Host transaction without backend staging. Main cannot restore a second writer by disabling the `library` switch. Without backend takeover, the original `library` switch still controls this transition.

Analytics exposes `analytics.read`, `analytics.sync`, `analytics.activity` and `analytics.import`. Sync reads allowlisted `thread/list` and `thread/read` through Host's shared Core connections. Host forwards turn events without starting the service solely for an event. Clients report activity every five seconds and the service takes the union; legacy Main activity merges by daily maximum. Disabled domains retain their old analytics path.

## Native capabilities and credentials

The backend entry point has no Electron dependency. Main provides native capabilities through the existing connection, including system encryption through `encryptionRequest/encryptionResult`. Requests bind to the capability-owning connection, cannot be settled by another client, and fail without replay on disconnect. Existing encrypted file formats remain unchanged; decryption failure must not overwrite old files. Decrypted runtime values stay in memory, never logs, URLs, argv or plaintext files. Real macOS safeStorage and existing ciphertext compatibility require separate local acceptance.

`trajectory.read/command` and `feedback.read/command` reuse the existing backend, require local browser manage authorization and a matching source, and journal writes through Host receipts. Trajectory status does not decrypt credentials; retry and feedback calls retain the backend's HostVault and provider credential environment. Credentials never return to the browser. The analytics service's `vault.read` still rejects every slot and is not the backend credential channel. Receiver authentication and actual feedback submission require separate acceptance. Backend attach and capability leases do not replace native tool acceptance on the desktop.

## Validation boundaries

Shared business behavior primarily uses Web, real Host/Node processes and isolated data for acceptance; GUI packaging is not a routine prerequisite. `pnpm --dir clients/gui test:workbench-backend` covers ordinary browser public-key pairing, library receipts, backend crashes, Main detach and Host stop at process/protocol boundaries. It does not replace browser page interaction acceptance. Only Electron-specific paths such as windows, encryption, browser views and computer control require the desktop app. Release resource discovery, signing and upgrades still require validation in the corresponding release task.
