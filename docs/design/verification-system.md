## 项目现状

已有 `ci-scope → ci-preflight → verification-evidence`，不另建平行 CLI。当前 [journey manifest](../../clients/gui/scripts/journey-manifest.json) 有四条旅程，新增 `connection-recovery` 仅声明 Web 范围。逐事实契约已接入计划、执行和聚合，新旅程不能仅凭 runner 退出码通过；旧旅程尚未全部采用该契约。

新增恢复 runner 和 counterexample 已包含真实 Host/Core、特定请求故障触达、已知回归变体、身份与清理证据。本次是源码盘点，没有重新运行它们。源码 Web/socket 验证不证明安装包、Host 进程换代、真实 15 分钟定时、真实供应商或移动真机。

身份、摘要和必填字段证明证据归属及完整性；任意 `passed: true` 的业务含义仍须由正确的断言支持。还缺用户功能地图、有边界的未知问题探索，以及人工成本下降的实测。

## 建议设计

### 1. 功能地图确定要证明什么

沿现有功能文档和 manifest 维护：用户目标、实际入口、前置条件、权威结果、可见结果、适用旅程、未覆盖范围。先覆盖打开项目与恢复、发送与取消、历史与重启、模型配置、停止与升级；随后覆盖 Relay/手机、工具与权限、定时任务。不要复制第二套命令清单。

例如“恢复后可继续聊天”必须同时证明：无需手动重连、原草稿和选择保留、原未决提交未重放、后续一条新消息在 Core 结算且 UI 可见。仅证明 socket 连通或加载提示消失不够。

### 2. 固定旅程与探索共用应用操作工具

优先复用现有 fixture/helper。第二条旅程出现同样的操作时再抽取打开项目、选择会话、输入、提交、断连、读取回执等公共操作；不让九百行专用脚本不断复制。用户行为走真实入口，故障注入走隔离设施，二者在证据中分开记录。

固定旅程保护已知回归。生成式探索在有限动作集合和资源预算内组合切项目、编辑草稿、断线、延迟基线、空闲回收、停止、恢复与提交，逐步检查不变量。保留 seed、完整事件序列、身份与初始状态；seed 单独不能复现异步调度。失败后缩减序列并转换为固定回归。

Agent 可以根据地图探索未脚本化功能，但通过判据来自契约与独立观察；不能让驱动 Agent 自评“看起来正常”就通过。探索在隔离资料、确定性本地模型中先运行，真实供应商和系统权限另设明确入口。

### 3. 恢复状态机同时验证安全与进展

| 性质 | 产品含义 | 验证方式 |
|---|---|---|
| 不重复副作用 | 丢响应后仍查原请求，不换 ID 重发 | 特定已受理请求丢响应，核对持久回执及执行次数 |
| 旧结果不污染新状态 | 原 Host/socket 的迟到结果不能覆盖当前选择或恢复状态 | 控制旧响应释放顺序，核对 owner/代际与当前 UI |
| 尊重显式停止 | 自动重连不能复活用户停止的服务 | 停止后触发读取/重连，核对无新执行代际 |
| 恢复能完成 | 后台恢复、无显式停止、依赖可用时最终能继续使用 | 释放故障后等待权威完成事件，发送新消息并核对结果 |

“最终恢复”必须说明环境假设：依赖恢复可用、必要事件获得处理机会、没有新的永久故障。模型检查可验证这些假设下的进展；实际运行用有理由的时间预算发现卡住，超时失败保留最后状态，不能无上限重试。

先为恢复 owner、连接代际、回执状态建立小模型。抽象动作对应代码中的真实原子边界，不把跨 `await` 的操作当作一步。模型反例映射回真实 runner；模型通过后仍需真实应用验证。是否使用 TLA+ 由该问题与维护成本决定，不因工具流行而选型。

### 4. 一份报告服务判断

复用 evidence：报告首先给用户目标是否达到，然后给首个失败阶段、对应断言、原请求/代际、最短复现步骤、权威与可见证据、清理结果、未到达部分。录像、截图展示过程，不能单独证明落盘或未重复提交。

错误必须区分产品失败、环境阻塞、验证器失败和未执行。不得以重试后的绿色覆盖首跑失败。性能验收固定工作量和基线，检查分布而非单次截图。

### 5. 验证系统也要验收

建议第一阶段验收：正确实现通过；两个已知错误变体在预期业务断言失败；构建失败不算发现回归；恢复后确实能提交；失败证据清楚且清理完成。

第二阶段：生成式探索输出可回放的短失败序列；由不参与实现的人核对契约与断言；补真实 Host 换代和正式安装包旅程，分别报告覆盖。

第三阶段：事先冻结连续一组变更，包含未命中旅程者，比较人工介入次数、阅读/归因时间、夹具阻塞、误报、逃逸缺陷、运行成本。历史材料不完整的样本不能证明节省。现有 `compare-journey-triage.py` 跳过未映射提交，需先修正抽样才适合衡量覆盖漏项。缺陷漏报只能由后续发现追踪，不能从“没有告警”推断为零。

## 三项规则的取舍

- **不全仓禁止 unwrap/expect。** 生产请求处理对用户输入、IO、网络和可恢复错误应返回结构化错误；测试中的 `expect` 常是合理断言；内部不变量失败需要明确策略。仅换成默认值或吞错会使故障更隐蔽。按模块和故障边界实施，不能用零关键词出现次数代替可靠性。
- **不要求每条规则都破坏整个应用。** 关键恢复性质、自动放行门禁、新验证器应证明能捕获相关错误。静态规则通常用正反 fixture 即可；既有修复前红灯可复用。形式模型的每项性质需要对应反例敏感度，昂贵端到端 mutation 不应成为所有小改动的默认负担。
- **不默认叠加多个模型审查。** 模型可能共享盲点，意见数量不等于证据。保留高影响契约、迁移、安全边界的独立审查，要求可达路径与具体后果；把常规成本优先投入可执行证据。验证需求和断言是否正确仍需要人或独立审查者，不能完全由自动化替代。

本建议只扩展现有验证基础设施。CI 必需检查或 hooks 的修改仍按项目授权规则执行。
