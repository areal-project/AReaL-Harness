# Conversation Submission & Follow-Up Feature Map

This map defines the user-facing product rules and verification bindings for the `conversation-submit` journey without duplicating test commands or source paths. Machine selection and execution contracts remain owned by [journey manifest](../../clients/gui/scripts/journey-manifest.json); see [verification system design](verification-system.md) for the overall methodology.

> Rule of thumb: **Expected product rules must be written strictly from the user's perspective, with zero internal error codes, process names, or implementation jargon**; engineering clues belong only in the current-reality column.

| Rule ID & User Goal | Expected Product Rule (PM Intent) | Current Reality & Engineering Clues | Authoritative & Visible Outcomes | Bound `factId` & Coverage Gaps | PM Adjudication |
|---|---|---|---|---|---|
| **`FM-CHAT-01`**<br>Open a cold project and press Enter as soon as the composer becomes sendable<br>(Web / Desktop / Mobile) | Once the input indicates it can send, pressing Enter sends the first message and produces a reply without errors, stalls, or asking the user to retry. | Wired in `web-journeys` without bypassing readiness via read-only schedule probes and verified on isolated Host/Core; guards against historical cold-start readiness races. | **Authoritative**: First `session.create` accepted once and settles a single Core Turn.<br>**Visible**: Message and reply appear with zero raw errors or page exceptions. | Locked in `conversation-submit`: `coldStartFirstSend`, `requestAccepted`, `turnSettled`, `visibleResult`.<br>Mobile and packaged app not run. | Approved · Locked |
| **`FM-CHAT-02`**<br>Send a message with files, images, or review comments attached<br>(Web / Desktop) | Attached files, images, or comments are delivered with the message, the draft clears after sending, and sent items remain inspectable in the thread. | Review comments are locked into `web-journeys` fact evidence; files/images are covered in `composer-smoke` and `composer-folder-vision`. | **Authoritative**: Core receives the exact attachments/structured parts without drop or duplication.<br>**Visible**: Draft settles and sent items are visible in the thread. | Locked in `conversation-submit`: `attachmentSubmitted` (review comments); files/images covered by `composer-smoke`. | Approved · Locked |
| **`FM-CHAT-03`**<br>Type and send a follow-up while the first turn is running or awaiting approval<br>(Web / Desktop / Mobile) | The composer remains usable while running or awaiting approval; the follow-up queues without dropping or overwriting, and the UI never claims "running" while waiting for approval. | Locked into `web-journeys` fact evidence, verifying honest approval status, queue feedback, and independent second Turn settlement in Core. | **Authoritative**: Follow-up settles as an independent Turn after the first settles.<br>**Visible**: Queue bar appears, approval status is honest, and both replies render. | Locked in `conversation-submit`: `queuedFollowUp`.<br>Mobile and packaged app not run. | Approved · Locked |
| **`FM-CHAT-04`**<br>Switch models mid-conversation and send the next follow-up<br>(Web / Desktop / Mobile) | The next message immediately uses the newly selected model without disturbing prior turns or drafts. | Model selection is covered by `model-selection-smoke`; mid-thread model switch + follow-up is not yet unified under `conversation-submit` facts. | **Authoritative**: Next outbound model request targets the newly chosen model/effort.<br>**Visible**: Picker reflects the new model and prior turns stay intact. | Planned `modelSwitchNextTurn` (align with `model-selection-smoke`). | Approved · Pending factId |
| **`FM-CHAT-05`**<br>Stop/cancel an in-flight turn and continue with a new message<br>(Web / Desktop / Mobile) | Triggering stop or Esc promptly ends generation without leaving a stuck spinner, and a subsequent message can be sent normally. | Covered by `stop-turn-smoke`; not yet surfaced in the shared `conversation-submit` evidence summary. | **Authoritative**: Active Turn settles as cancelled with no orphan execution.<br>**Visible**: Stopped state is clear and the composer accepts the next message. | Planned `cancelAndContinue` (covered by `stop-turn-smoke`). | Approved · Pending factId |

## Anti-Drift Discipline

Whenever live behavior disagrees with this map, classify it explicitly as **doc drift** (intentional product change, update map after PM sign-off), **verification gap** (rule exists but lacks a bound `factId`/assertion), or **product regression** (code broke an agreed rule; keep a failing test first and fix code—never edit the map to mask a regression).
