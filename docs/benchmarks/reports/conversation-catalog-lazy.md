# 会话目录：轻量元数据与按需历史

## 选型

推荐 `sqlite-lazy`：**SQLite 持久化轻量元数据，内存有序目录处理现有查询，历史按会话首次需要时加载**。原默认 `memory` 保留兼容；新方案以显式模式交付，不改变已配置服务的事实与恢复语义。配置见[会话目录后端](../../guides/configuration.md#会话目录后端)。

选择依据来自四模式相同程序的实测。20,000 会话的可复用缓存启动下降 74.1%，初始 Core RSS 下降 64.0%；2,000 个各含 64 KiB 历史的场景分别下降 69.8%、61.3%。收益主要来自加载分层、紧凑 State、按需工具绑定及事件缓冲；SQLite 在大元数据缓存的驻留量和增量维护上有额外价值。查询没有普遍加速，首次加载、首次构建与全部打开的代价列在下文。

下列完整矩阵对应首次冻结程序。缓存恢复修复后的独立复测见[故障恢复复核](#故障恢复复核)，其中保留首次执行变慢的不利样本；不同程序的样本分开统计。

| 模式 | 启动恢复 | 持久目录 | 运行时查询 |
|---|---|---|---|
| memory | 全量事实 | 无 | 内存 |
| sqlite | 全量事实 | SQLite 不可变键索引 | SQLite，故障回退内存 |
| memory-lazy | 已结算普通根会话按需 | JSON 元数据清单 | 内存 |
| sqlite-lazy | 同一按需机制 | SQLite 元数据缓存 | 内存 |

`sqlite-lazy` 的运行时内存查询是明确的职责划分。开发版曾同时查询 SQLite 键索引；20,000 条无来源匹配查询中位数为 8.152 ms，内存查询的 JSON 按需版为 3.294 ms。已保留内存排序目录时，这层 SQL 往返没有抵消成本。另一开发反例是 1,200 个混合会话、8 KiB 元数据：JSON 按需版初始 RSS 194.953 MiB，高于全量内存的 169.938 MiB；SQLite 元数据版为 159.516 MiB。完整清单编解码的临时分配及分配器保留页，使 JSON 在此负载并不省内存。两项证据促成最终组合，原结果完整保留。

## 兼容性与实现约束

- JSON 事实格式、状态版本 15、原子写入、同步落盘顺序、UNKNOWN、取消、权限、工具回执与工作区文件工具不变。缓存不是新提交点，正常 Turn 不双写目录；SQLite 的 NORMAL 仅用于可重建缓存。
- 只延迟已结算的 `appServer`、`cli`、`exec` 普通根会话。子会话、Fork/Side、Goal、未结算工具/进程/队列/交互和旧默认模型迁移继续全量恢复。不能声称所有历史都不常驻。
- 启动以设备、inode、长度、纳秒 mtime/ctime、模式及单链接普通文件身份核对缓存，并验证投影、归档头依赖和实现指纹。首次使用再校验完整事实 SHA-256、资格和元数据；禁止把未加载投影写回事实。并发首次读取只发布一份完整状态，取消不发布半份历史。
- 事实离线增删改、缓存坏损及历史限制收紧保留原校验；未知缓存版本保留并从事实恢复。首次使用发现错误投影时拒绝执行并隔离可识别缓存，重启重新验证事实；不增加重放或隐式执行重试。
- RPC 参数、返回字段、Idle 等状态、排序、权限、旧游标保持兼容。新增 Rust 视图过滤辅助方法，原过滤闭包方法不变；Rust 穷尽匹配需覆盖两个新增 SessionCatalog 变体。GUI 刷新合并复用既有实现。

## 为什么采用 SQLite，以及未来边界

SQLite 的价值在持久元数据层：行级更新、事务、版本化结构和控制大清单临时内存的能力均与本次需求对应。大元数据反例说明，JSON 清单并非始终是更轻的选择；流式 JSON 可能降低清单峰值，但本轮未实现比较，不能把现有反例视为 JSON 的物理下限；分段、增量更新与回收则需要维护另一套存储与恢复机制。当前简单排序使用已有内存索引，保留低查询开销。

后续多维过滤、标签、跨项目检索和全文搜索可增加类型化列、覆盖索引或独立 FTS 索引；当前 `metadata(id,body)` 仍以 JSON 保存投影，尚未实现这些能力。上线动态索引前必须定义事实提交后的增量通知、代际/脏行覆盖、重建与故障回退，避免旧索引漏项。若要进一步降低 N 个冷会话句柄的内存、跳过文件扫描或空闲卸载历史，还需独立的冷目录/活动会话拆分与恢复设计；SQLite 文件本身不会自动带来这些收益。[SQLite 查询规划](https://www.sqlite.org/queryplanner.html)、[FTS5](https://www.sqlite.org/fts5.html)

Codex 官方接口区分已加载会话、存储历史分页、数据库目录及 JSONL 修复，并提供 SQLite 支持的持久元数据更新。可参考这种分层；不能把其所有数据库内容概括为可丢弃索引，也不能把 Codex 的技术选型当作本仓库的性能证据。本实现仍明确以 JSON 为事实、SQLite 为可重建缓存。[OpenAI App Server](https://learn.chatgpt.com/docs/app-server)

仅有少量小会话、全部历史必然长期活跃、或不愿维护派生缓存时，`memory` 仍是合理选择。面对本次普通历史常驻与目录扩展需求，推荐 `sqlite-lazy`；这不证明它是所有工作负载的全局最优。原默认保留 `memory`，新性能策略按仓库门禁显式交付，不从合成局部结果推断四领域 Agent 收益。

## 故障恢复复核

额外故障用例先复现了两类可恢复性缺陷：事实成员已删减且数量上限收紧时，旧缓存超限会使后续启动持续放弃缓存；SQLite 首次初始化中断形成的空文件或零版本残片也会持续回退。这些情况保留事实、不会重放工具，但会让启动优化失效。修复将已识别的失效缓存先保留再重建，并将 SQLite 身份、schema 和版本在同一事务提交。外来数据库与未知正式版本继续原字节保留。

边界回归扩为 **19 项、全部通过**，覆盖初始化五阶段、收紧上限、重复身份、缓存写者占用、符号/硬链接和事实验证完成后等待发布锁时取消。推荐模式重新完成全量回归：**873 通过、0 失败、19 显式忽略**；上一轮超时用例连续单独复测五次均通过。默认和两个按需模式的真实 TUI/Core/Runtime smoke、推荐模式的大历史/归档/序列化 Unicode 条目与重连检查、GUI 历史和刷新、Clippy 及文档检查另行复测。

选型优先级是大量休眠历史的启动和初始内存，以及元数据增长；这一范围内仍推荐 `sqlite-lazy`。首次构建、全目录遍历、首次读取及部分执行样本更慢，全部打开也可能占更多内存。对首次执行延迟更敏感、历史始终全部活跃的工作负载，保留 `memory` 作为合理选择，当前默认继续为 `memory`。尚未实现的流式 JSON、完全独立冷目录或历史淘汰仍可能改善其他指标，不能据现有四方案宣称全局最优。
