# 会话目录的迭代验证与方案比较

[第一轮](conversation-catalog.md)消除了全量历史复制、每页重排目录和重复刷新。本轮进一步比较候选读取方式、加入真实 GUI 缓存写盘，并扩大原有功能的回归范围。结论只适用于目录与客户端同步机制，不等价于整体 Agent 能力提升或零退化的绝对证明。

## 比较的三个版本

| 版本 | 候选批次 | 内部扫描游标 | 判断 |
|---|---|---|---|
| R1：第一轮实现 | 随结果页剩余容量缩小 | 每个候选推进 | 页接近填满后，长过滤空洞会逐条查索引 |
| R2：固定批次 | 每批最多 `limit + 1` 个句柄 | 每个候选推进 | 消除上述退化，保持有界内存与原 API |
| R3：当前候选 | 同 R2 | 每批推进一次 | 进一步减少 UUID 临时克隆；没有独立状态缓存 |

R3 的扫描游标只用于读完当前候选批次后的继续查找；返回给调用方的游标仍来自最后一条返回结果。额外匹配项只用于判断 continuation，下一页不会跳过它。目录锁仍在取得会话锁前释放，文件事实和动态字段读取方式保持原样。

采用 R3 的依据是去除确定存在的重复查找与分配，并通过相同契约回归；不能据此把 R3 称为每个场景都最快。R2 与 R3 的部分差异很小，且保留了不利结果。

## 更有代表性的性能对照

沿用 Apple M5 Pro、24 GiB 内存、Rust 1.94.0 的本机 release 环境。每个进程中，各场景预热 2 次、记录 10 次；每侧独立启动 5 次，交替执行先后顺序。表中取各进程中位数的中位数，不把同一进程内样本当作独立机器或任务。原始样本、二进制与源码身份见 [JSON](conversation-catalog-validation-results.json)。

真实 Engine 从同版本文件恢复，测量实际 RPC 投影和 JSON 编码。权限集合构造三类反例：每 100 个候选仅 1 个可见；前 100 个及最后 1 个可见，中间为长空洞；全部不可见。文件准备与恢复不计入查询计时。

| 场景 | R1 | R3 |
|---|---:|---:|
| 2,000 会话，长权限空洞 | 0.814 ms | 0.443 ms |
| 20,000 会话，全部可见，首屏 | 0.131 ms | 0.117 ms |
| 20,000 会话，每 100 个仅 1 个可见 | 3.551 ms | 2.992 ms |
| 20,000 会话，长权限空洞 | 10.938 ms | 6.777 ms |
| 20,000 会话，全部不可见 | 4.413 ms | 3.701 ms |

第二组独立交替对照专门比较 R2 与 R3。2,000 会话的稀疏、长空洞及无匹配场景，R3 中位数分别减少约 18%、12%、14%；20,000 会话的长空洞却从 R2 的 7.168 ms 增加到 R3 的 7.478 ms，约慢 4.3%。这一不利结果没有删除。大目录密集查询几乎相同，不能声称游标调整在所有负载上更快。

初步单次进程中，固定批次曾测得约 4.8 ms 的长空洞结果；多轮对照的波动明显更大，因此最终判断使用上述交替结果。未测真实写入压力下的长期 p95、跨机器分布或生产用户等待时间，不把微秒差异当作可靠的产品收益。

## GUI 加入真实写盘后的收益与限制

运行生产 `HistoryObservation`、`CoreLibrary` 和 `CoreBackend.save`，使用临时目录真实执行 JSON 序列化、临时文件写入和 rename；Core 传输仍是异步 fixture，不计 Backend 快照投影、IPC 推送和 Renderer 绘制。固定 2,000 行和 20 次同步突发，每侧各 5 次。每次都核对最终摘要、最新完成 Turn 和未读标记。

| 场景 | 原实现中位数 | 当前方案中位数 | RPC 数 | 全部 library 写入 |
|---|---:|---:|---|---|
| 20 次完整刷新 | 81.13 ms | 2.56 ms | 400 → 20 | 20 → 1 |
| 同会话 20 条 Turn 通知 | 82.26 ms | 39.51 ms | 400 → 1 | 40 → 21 |

Turn 场景中的摘要缓存写入是 20 → 1，但活动标记仍保存 20 次。这解释了所测缓存路径约 2 倍的收益，不能把目录请求减少 400 倍写成 GUI 整体加速 400 倍。本轮保留活动与未读状态的持久化顺序，未为追求计时合并这些写入。

## 原有功能保护的证据范围

- 分页结果与完整授权参考逐项比较：257 个混合来源、归档、父子关系和并列创建时间，覆盖 main/all、归档开关以及页大小 1、7、100；比较完整旧元数据，检查无丢项、重复或不足页 continuation。
- 页中前 100 条与最后 1 条可见，验证长过滤空洞后的 continuation；在查询等待某一会话锁时创建另一个会话，验证目录读取不占住注册锁。
- 任务已受理并暂停在写文件工具中时反复查询目录：核对模型请求和权威记录未变，随后工具仅执行一次、用量按原请求结算，重启后历史保留且不重放工具。这属于确定性本地 Model/动态工具 Host 回归，不替代原生 Runtime 或供应商验收。
- GUI 生产缓存 fixture 检查完整目录、最终完成身份和未读状态；原有重连、Worktree、配置、历史与权限测试继续保护各自契约。

完整 Engine 与 app-server 回归在开发配置、3 个构建作业和 4 个测试线程下通过：777 通过、16 显式忽略，包含 71 组目标结果。GUI 完整 verify 的测试组共 318 通过、3 既有跳过，类型检查、Clippy、格式和文档检查通过。

默认测试并发的 Engine lib 曾出现 2 项 MCP 失败：Python 握手初始化超过 2 秒，以及目录预算断言不符；当时为 279 通过、2 失败、4 忽略。相同 MCP 测试隔离运行 4 项全部通过，随后限制测试框架并发的完整回归也通过，没有改产品代码、超时或断言。这支持测试资源争用的解释，但不把默认并发那次失败改写为通过。全量 release LTO 构建中断、首次测试 fixture 编译失败及缺失日志尝试同样保留在 JSON；性能比较始终使用冻结的 release 可执行文件。

新构建的真实 TUI/Core 冒烟通过多轮对话、取消、子会话导航、PTY、强杀恢复和 OTLP 上报。真实 CoreBackend 大历史检查通过超过 64 MiB 的 Unicode 条目重组、普通与归档历史分页、重连及视图释放：228 次历史响应均不超过 1 MiB，求解请求始终为 1 次，权威历史与回执不变。

未对四领域任务分布重新运行 Agent 能力评测，也未做安装包和人工视觉验收。源码没有改变提示词、模型输入规划、工具定义、权限规则、默认预算、持久化格式或 fsync 顺序；这与回归证据共同支持“已覆盖路径未发现功能退化”，不支持对所有正常能力作绝对保证。

## 是否继续换方案

以下是 R3 阶段的历史判断；后续已实现显式 SQLite 候选，当前选型和同口径实测见[内存与 SQLite 对照](conversation-catalog-sqlite.md)。

目前保留 R3，不接入 SQLite。已经比较的是三种实际运行的内存查询方式；没有做 SQLite 接入后的同口径端到端 A/B，因此不能宣称 SQLite 一定更慢，也不能宣称当前方案是全局最优。

| 方向 | 当前判断 |
|---|---|
| 固定候选批次与按批游标 | 保留；修复已证实的重复工作，API 与存储契约不变 |
| 继续添加动态摘要缓存 | 暂缓；会增加名称、权限、归档、来源等状态同步与失效职责 |
| SQLite 元数据索引 | 暂缓；没有启动、内存、全文检索或真实尾延迟证据支持当前迁移成本 |
| GUI 活动写入合并 | 已识别为剩余成本；需单独证明未读、排序、失败和崩溃语义，不在本轮改写 |
| 快照写入合并或异步持久化 | 暂缓；本轮没有采集其瓶颈证据，不改变既有提交和 UNKNOWN 语义 |

若真实用户负载下仍有明显等待，先分别测 Core 冷启动/内存、稀疏过滤与会话锁等待、GUI library 保存与 Renderer 投影。只有相应路径成为主要瓶颈，才继续比较对应方案。当前 Engine 仍会恢复全部 Thread；仅增加 SQLite 而不调整恢复路径，不会自动取消这部分工作。

## 复现

```sh
cargo test --locked -p areal-engine -p areal-app-server --jobs 3 -- --test-threads=4
cargo test --locked --release -p areal-app-server --lib catalog_tests
cargo test --locked --release -p areal-engine --lib catalog::tests
cargo test --locked --release -p areal-engine --test catalog_observation
AREAL_CATALOG_PERF_PHASE=candidate cargo test --locked --release \
  -p areal-app-server --lib catalog_filter_performance_comparison -- --ignored --nocapture
AREAL_CATALOG_BENCH_CACHE=production \
  node clients/gui/scripts/catalog-refresh-benchmark.cjs
```

GUI 脚本可另传旧版 `history-observation.cjs`。重建 R1/R2/R3 时，保持 fixture、release 配置与其他实现相同，分别使用表中的候选批次和内部游标方式，编译冻结可执行文件，再交替运行性能用例。完整回归使用本机代理的 loopback 绕过项，保留已有 `NO_PROXY/no_proxy` 条目并加入 `127.0.0.1,localhost,::1`。
