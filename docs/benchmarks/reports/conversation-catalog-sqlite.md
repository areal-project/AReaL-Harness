# 会话目录：内存与 SQLite 对照

本轮在[目录迭代验证](conversation-catalog-validation.md)之后，继续完善内存目录，并实现可显式切换的 SQLite 后端。比较对象是当前文件事实架构中的目录查询，不是两种数据库的通用排名，也不代表四领域 Agent 能力评测。

本报告限定于全量恢复与 SQLite 不可变键查询。轻量目录、按需历史及 SQLite 元数据与内存查询组合的后续实现和选型见[新对照](conversation-catalog-lazy.md)。

## 实测结论

默认继续使用完善后的内存目录，SQLite 保留为显式候选。当前所有会话都已恢复到内存，主要修复是减少历史复制、无效扫描和重复刷新；在相同查询条件下再经由 SQLite 查询，没有得到足以替换默认的收益。不能把这理解为 SQLite 通常比文件慢，或内存方案已经全局最优。

| 场景 | 内存 | SQLite |
|---|---:|---:|
| 100 会话，首屏 | 0.119 ms | 0.137 ms |
| 20,000 会话，首屏 | 0.123 ms | 0.150 ms |
| 20,000 会话，尾页 | 0.124 ms | 0.139 ms |
| 20,000 会话，完整分页 | 33.082 ms | 39.974 ms |
| 2,000 会话，各含 16 KiB 历史，完整分页 | 2.883 ms | 3.380 ms |
| 2,000 会话，各含 4 KiB 元数据，完整分页 | 10.872 ms | 11.173 ms |
| 20,000 会话，每 100 个仅 1 个授权可见 | 0.145 ms | 0.226 ms |
| 20,000 会话，授权长空洞 | 0.127 ms | 0.165 ms |
| 20,000 会话，动态归档长空洞 | 3.429 ms | 8.879 ms |
| 20,000 会话，动态来源无匹配 | 3.314 ms | 8.168 ms |

单页差距通常只有几十微秒，但完整分页和动态过滤的额外成本会累积。主对照中记录了索引指标的 SQLite 场景均保持 active，实际查询均有 SQL 命中，错误、溢出和回退均为零；没有把回退到内存的结果算作 SQL 性能。

授权前置给两个后端带来的收益，不能归因于 SQLite。下表另用历史 R3 的冻结 release 程序交替比较；这不是同一可执行文件，身份和适用范围单独保留。

| 20,000 会话，首屏授权条件 | R3 参考 | 当前内存 | 当前 SQLite |
|---|---:|---:|---:|
| 全部可见 | 0.119 ms | 0.120 ms | 0.133 ms |
| 每 100 个仅 1 个可见 | 2.269 ms | 0.145 ms | 0.226 ms |
| 前 100 个及最后 1 个可见 | 4.973 ms | 0.127 ms | 0.165 ms |
| 空授权集合 | 3.045 ms | <0.001 ms | <0.001 ms |

稀疏与长空洞约改善 15.6 倍、39.2 倍，主要来自在取得 State 锁前求交。空授权集合直接返回，两版都不查询数据库。密集路径没有普遍变快：2,000 会话从 R3 的 0.117 ms 到内存 0.122 ms，约慢 4.9%，保留这一不利结果。

## 恢复与资源成本

| 20,000 会话，暖文件缓存 | 内存 | SQLite |
|---|---:|---:|
| 完整恢复，首次构建条件 | 1,058.205 ms | 1,151.603 ms |
| 完整恢复，再次打开条件 | 1,157.240 ms | 1,099.996 ms |
| 仅目录初始化，首次构建 | 1.120 ms | 15.460 ms |
| 仅目录初始化，再次打开 | 1.075 ms | 4.810 ms |
| 主对照整个进程峰值 RSS 中位数 | 892.766 MiB | 900.125 MiB |

SQLite 复用时的完整恢复中位数反而较低；完整恢复的进程样本范围高度重叠，不能声称每种启动都更慢，也没有证据证明它取消了恢复瓶颈。目录本体初始化更贵，文件恢复仍主导约 1 秒的启动时间。SQLite 增加约 7.36 MiB 的所测进程峰值；这不是隔离索引内存或生产常驻量。

实际使用 SQLite 3.54.1，随固定 `rusqlite=0.41.0` 捆绑构建。20,000 键重用时数据库约 2.05 MiB；首次构建样本的 WAL 约 2.09 MiB，数据库尚为 4 KiB。该统计不含 SHM、被拒绝缓存和事实文件。默认内存不启动这些索引线程，但新增依赖仍增加构建与链接成本。

## 事实写入、快照与调度反例

64 次真实事实创建的进程中位数，再跨进程取中位数：内存 8.005 ms，SQLite 7.994 ms，不能把这点差别解释为稳定加速。每进程 16 次产生快照的 Turn 之后，SQLite 的 `rowsWritten` 仍为创建后的 64，没有因目录读取或正常快照重复更新索引，模型请求数始终为 16。

首组单线程 Tokio 闭环 fixture 的并发读中位数是 0.540 ms 对 8.792 ms。不能直接把它写成生产退化 16 倍：内存查询可以连续完成而不挂起，SQLite 会在等待工作线程时让出执行权，导致两组查询与写锁重叠的节奏不同。

为检验这一机制，保留原样本，在测量后只新增测试：每完成一次读取，两种后端都 `yield_now()`；再以同一份追加的 release 程序各交替运行 5 个进程，生产源码未变。

| 混合 fixture，每进程 16 Turn、80 次目录读取 | 内存 | SQLite |
|---|---:|---:|
| 原闭环，Turn 中位数 | 17.056 ms | 17.996 ms |
| 原闭环，目录读中位数 | 0.540 ms | 8.792 ms |
| 都主动让出调度，Turn 中位数 | 18.660 ms | 18.662 ms |
| 都主动让出调度，目录读中位数 | 8.418 ms | 8.703 ms |

控制调度后延迟接近，支持 State 快照写锁等待和请求节奏解释。仍保留内存某轮读取中位数 13.921 ms、同轮 SQLite 8.764 ms 的不利结果。这不是生产流量、外部模型延迟或稳定 p95；不能用首组差异论证 SQLite 普遍拖慢任务，也不能用单轮反例宣称 SQLite 更快。SQLite WAL 不会消除持有当前 State 锁等待事实同步的时间。

## 机制与公平性

内存版复用恢复阶段已有的 UUID 映射，避免销毁后重新注册。授权 ID 集合在取得会话锁之前与目录求交；UUID 查询沿授权集合范围读取，创建顺序查询在小集合时做候选求交与有界选取。较大的授权集合仍沿创建顺序扫描。剩余归档、来源和父子关系过滤读取当前 State，不能依赖过期副本。

SQLite 版与内存版接收完全相同的授权条件。表 `entries(id PRIMARY KEY,created_at)` 和覆盖索引 `(created_at,id)` 只保存不可变键，`version` 表与变更在同一事务中更新。查询使用复合键继续、参数绑定和 `LIMIT`，不使用 OFFSET；授权集合通过绑定 JSON 求交。返回键在相同目录代际下接回实时会话，名称、归档、权限与旧元数据仍走同一投影。

一个写线程按有界队列合并增删，两个读线程各持独立连接。连接在线程内使用，异步 RPC 不直接执行 SQLite 调用，也不持目录锁等待数据库。队列容量 128；索引落后或读队列忙时直接走内存。数据库错误、写队列溢出、读取超过 250 ms 会在该实例中停用 SQLite；控制屏障各限 1 秒。超时不强制取消挂起的底层文件系统调用。

文件完整恢复后核对全部 SQLite 键，一致才重用；不一致则事务重建。损坏或格式不符的普通缓存文件先保留，再重建。缓存路径拒绝符号链接和多硬链接。两版均保留内存排序目录作为安全回退，SQLite 增加连接、线程、页缓存和文件成本，不宣称降低常驻历史内存。

## 事实写入与兼容性

原 JSON 事实、快照版本、同步落盘顺序、UNKNOWN 和工具副作用规则保持原样。注册或回滚只追加索引事件，缓存失败不改变原事实提交结果；名称、归档及正常 Turn 快照不更新 SQLite 行。`flush_catalog` 只等待缓存队列，不是新的事实提交点。

现有 RPC 名称、参数、返回元数据、UUID/创建顺序、权限过滤、游标编码和跨页非快照语义保持一致。默认后端仍为 `memory`；显式配置或环境变量选择 `sqlite`，见[配置指南](../../guides/configuration.md#会话目录后端)。Rust 嵌入方可在 `Limits` 中设置 `session_catalog`；不指定时使用 `Limits::default()` 的内存后端。持有完整字段字面量的 Rust 调用方需补上新增字段，JSON/RPC 客户端无需修改。

本轮未修改模型提示、输入规划、工具定义、执行预算或 GUI 生产交互。较少的目录工作可能减少资源争用，但不能写成模型求解、执行命令或用户文件读写普遍加速。

## 测量方法

同一台 Apple M5 Pro、24 GiB 内存、Rust 1.94.0，使用同一个冻结的 release app-server `--lib` 测试可执行文件，通过测试专用变量选择两种后端。每侧独立启动 5 个进程，交替先后顺序，测量期间不运行本任务的构建或功能测试。查询计入真实 Engine、RPC 投影和 JSON 编码，排除 fixture 准备；各场景预热 2 次，首/尾页保留 7 次，过滤保留 10 次，完整目录保留 5 次。表中先取各进程中位数，再取 5 个进程中位数，不将进程内样本当作独立机器。

完整恢复使用刚准备的文件，因此是**暖文件缓存**；首次构建与再次重用索引各测一次、每侧共 5 次，不称为磁盘冷启动。额外覆盖 4 KiB 元数据、长归档空洞和来源无匹配。读写 fixture 测量 64 次真实事实创建、16 个生成快照的已完成 Turn 与 4 个查询任务的 80 次读取，同时核对索引写入行数、真实 SQL 命中、回退和模型请求数。RSS 是整个测试进程的峰值，不能当作孤立索引内存。

旧性能入口 `catalog_performance_comparison` 的 `all` 样本保留 5 次、未单独预热，仅作附加记录；主表完整分页统一采用新后端入口的预热方案，不跨入口择优拼接。RSS 还包含两侧相同的系统 Python 启动包装。

历史 R3 冻结二进制另跑 5 次稀疏授权对照，作为继续优化的参考；主结论来自两种后端共用当前可执行文件的比较。所有原始样本、进程退出码、源码与二进制 SHA256、索引状态及失败尝试保存在[结果 JSON](conversation-catalog-sqlite-results.json)。

## 功能保护与验收边界

- 默认后端的完整 Engine、app-server、config 回归：854 通过、0 失败、17 显式忽略，共 78 组结果（含 doc-tests）。Engine 索引回归同时覆盖两种后端；追加性能诊断的当前 release 程序另在 SQLite 模式运行目录契约，10 通过、4 显式忽略。
- 元数据与持久字节、混合权限/归档/父子关系的完整参考、页大小 1/7/100、同时间排序、旧游标、Fork、注册回滚和锁独立进展均通过。新增 4 组查询与 32 次创建并发，核对已发布会话不丢失、不重复，SQL 仍 active 且结算 32 行。
- SQL 单独覆盖重用和旧键修复、损坏保留重建、外部写锁、索引落后、队列溢出、读取期限与安全路径。缓存故障不被返回成事实提交错误；这不排除磁盘和 CPU 等共享资源竞争。
- 两种后端反复目录观察时，模型输入和事实字节不变；真实文件工具副作用只执行一次，用量与重启历史保持，不重放工具。
- GUI 刷新回归 13 通过。新构建的 TUI/Core 在两个后端均通过多轮持久化、PTY、取消、子会话导航、重连、强杀恢复与 OTLP 检查。真实 CoreBackend/桌面连接的大历史检查也分别通过：普通与归档分页、超过 64 MiB 的 Unicode 条目重组、视图释放和重连；每侧 228 次历史响应均不超过 1 MiB，求解 1 次、命名 1 次，原历史与回执保持。
- Clippy（四个相关 crate 的 all-targets，`-D warnings`）、相关 Rust 格式、JS 格式/语法、文档与链接检查通过。未修改 GUI 生产页面或视觉组件，未重新做全 GUI verify、人工 Renderer 视觉验收、发行安装包或 Linux 原生验收，不将上一轮的 GUI 结果算作本轮运行。

这些证据支持已覆盖路径未发现功能退化；不支持“所有能力绝对零影响”。SQL 对内存、连接、线程、构建依赖和磁盘的新增成本已经记录。未运行四领域 Agent 对照，不宣称模型推理或用户文件工具普遍提速。

首次用计时器直接启动历史程序时，进程在测试入口前异常终止，没有有效样本；相同 SHA 经系统 Python 可启动，后续所有版本统一采用该入口。此前执行环境切换导致一次未完成回归及临时日志丢失，其最终退出状态记为 UNKNOWN，不计入通过数；完整回归已重新运行并保留工作区日志。最初配置类型、编译和 macOS NOFOLLOW 适配失败的已知记录也在 JSON 中保留，不将修复后的通过改写成首次就成功。

## 从 Codex 借鉴什么

官方接口区分数据库目录、JSONL 修复和已加载会话；`useStateDbOnly` 可跳过日志修复，部分元数据直接写 SQLite。可借鉴这些边界，不能推断它的所有 SQLite 内容都只是可丢弃缓存。[OpenAI App Server 文档](https://learn.chatgpt.com/docs/app-server)

本轮选择可重建的不可变键索引，是为了按当前架构验证引入 SQLite 的收益与成本。它不是对 Codex 完整存储模型的复刻。要获得历史不常驻或跳过完整恢复的潜在收益，还需要设计延迟加载、事实版本/增量发现、崩溃核对、动态元数据一致性及恢复门禁；不能把这些尚未实现的收益算在本轮候选头上。

WAL 可以让短读事务与写入并行，但仍只有一个写入者；它不会消除当前 State 的锁或事实文件的同步成本。`synchronous=NORMAL` 用于可重建缓存，不替代事实持久化。[SQLite WAL](https://www.sqlite.org/wal.html)、[SQLite PRAGMA](https://www.sqlite.org/pragma.html#pragma_synchronous)

## 后续方案的取舍

本轮保留完整内存索引以便安全回退，是兼容性取舍，并非 SQLite 最省内存的设计。结果只否定当前架构中“再加一层等价 SQL 键索引”作为默认优化的必要性；未比较移除常驻历史后的完整数据库架构，不能据此证明 SQLite 的最佳实现一定落后。


| 方向 | 当前架构中的适用条件与代价 |
|---|---|
| 保持内存目录并推下授权条件 | 小范围修复；无需第二份动态状态，正确性可直接验证 |
| 当前 SQLite 索引 | 可运行、可回退的显式候选；增加持久缓存与线程，但仍恢复完整事实 |
| 将归档、来源、父子关系也索引化 | 可能减少长动态过滤扫描；须覆盖所有修改入口并用代际验证，否则会漏项或返回过期状态；内存索引同样可实现 |
| 可选精简摘要接口 | 若网络、JSON 或大元数据成为瓶颈，可在保留旧 API 的同时提供摘要投影；需 Core/GUI 能力协商与兼容验证 |
| 独立轻量目录与按需历史加载 | 适合启动或历史内存成为主要瓶颈；SQLite 是可选实现，需要同时处理文件发现、版本和未结算执行恢复 |
| 快照写入合并 | 需要先证明快照是主要成本，并定义事实提交边界；不能通过异步丢写、降低 fsync 或隐藏重试换取目录计时 |
| GUI 活动写入合并 | 仍需单独证明未读、活动排序、失败和崩溃语义；目录索引不会自动优化这些写入 |

任何方案都不称为全局最佳。机制回归保护正确性，正式 Agent 策略收益仍须按来源隔离和四领域固定分布评测；单机目录、确定性模型与原生 smoke 不能替代这些证据。

## 复现

```sh
cargo test --locked -p areal-engine -p areal-app-server -p areal-config --jobs 3 -- --test-threads=4
AREAL_CATALOG_TEST_BACKEND=sqlite cargo test --locked -p areal-app-server --lib catalog_tests --jobs 3 -- --test-threads=4
cargo test --locked --release -p areal-app-server --lib --no-run --jobs 3
AREAL_CATALOG_TEST_BACKEND=memory cargo test --locked --release -p areal-app-server --lib catalog_backend_performance_comparison -- --ignored --nocapture
AREAL_CATALOG_TEST_BACKEND=sqlite cargo test --locked --release -p areal-app-server --lib catalog_backend_performance_comparison -- --ignored --nocapture
AREAL_CATALOG_TEST_BACKEND=memory cargo test --locked --release -p areal-app-server --lib catalog_cooperative_concurrency_performance_comparison -- --ignored --nocapture
AREAL_CATALOG_TEST_BACKEND=sqlite cargo test --locked --release -p areal-app-server --lib catalog_cooperative_concurrency_performance_comparison -- --ignored --nocapture
AREAL_CATALOG_TEST_BACKEND=sqlite node scripts/smoke.mjs
AREAL_CATALOG_TEST_BACKEND=sqlite node clients/gui/scripts/large-history-smoke.mjs
```

性能运行先冻结构建产物，交替直接调用该可执行文件，避免构建穿插或产物被覆盖。原生脚本需先构建 Core/Runtime，可用 `AREAL_TEST_BIN_DIR`、`AREAL_CORE_BIN` 指定独立构建位置。所有 smoke 使用临时配置和数据，不操作既有用户服务。
