# Remote Control API: areal.remote.v2

Except for the RC-01/RC-02/RC-03/RC-04/RC-05/RC-06/RC-07/RC-08/RC-10/RC-11/RC-13 scope explicitly identified below, this is a proposed contract rather than implemented capability. Native Core APIs remain independently versioned. C14 defines minimum view fields.

## Implemented boundary: RC-01/RC-02/RC-03/RC-04/RC-05/RC-06/RC-07/RC-08/RC-10/RC-11/RC-13

The development encrypted Direct entry and locally confirmed pairing are implemented: a separate, default-disabled `127.0.0.1` listener, optionally remembered browser identity, Host pin verification, v2 hello, and `host.describe` / `project.list` / `project.models` / `work.list` / `attention.list` / `session.open` / `session.history` / `subscription.close` / `session.create` / `session.send` / `turn.stop` / `attention.read` / `interaction.respond` / `task.question.read` / `task.question.reply` / `task.read` / `task.pause` / `review.read` / `artifact.read` / `command.read` / `device.push.register` / `device.push.unregister`. Trusted Desktop integrates Serve, optional Funnel scope changes and organization HTTPS-origin configuration (public Funnel capability is uncertified) as described in C11. Actual Tailscale/organization proxies, physical mobile acceptance, and other methods still require further evidence; Relay now joins the same Host/PWA protocol with source and local strict-TLS fixture coverage described in C12; the complete P0 contract below does not claim their availability.

The desktop creates a one-use 120-second link (loopback HTTP in development) with `host` and `invite` in the fragment. The browser immediately removes the invitation, retaining only the validated public `host` pin and optional Relay `room`, sends `inviteSecret` only after Noise verifies the Host, and waits for local confirmation after `pairing`. Trusted local `remoteControl` supports `pair/cancelPair/approve/reject/updateGrant/revoke/renameDevice/forgetRevoked`; approval and updates take device `id`, explicitly selected existing `projects`, and `preset: Observer|Operator`. Desktop review shows the full Noise peer fingerprint and project selection, with copy/paste alternatives to QR. The local approval decision must occur before the deadline; ready follows successful persistence. Failed persistence grants no new authority. The 15-second transport-establishment deadline ends on pairing; human confirmation remains bound by the Host’s 120-second invitation expiry and cancellation/refusal results.

Encrypted `remote.json` retains Host identity and `deviceGrants` with `devicePeerId/displayName/projectIds/capabilities/revision/status`. Scope changes and revocation persist before closing old device connections. Implemented capabilities are `observe`, `review`, `submit`, `interrupt`, `answer`, and `pauseTask`; ready and host.describe advertise their intersection with the current grant. The existing Operator `pauseTask` is advertised through the same current-grant intersection as `review`; Observer and legacy grants without that capability never receive it. Legacy `devices` retain identity and projects as `reviewRequired`; legacy write clients receive an upgrade requirement. Failed migration preserves the original file and disables entry points. Unavailable secure storage or `basic_text` rejects enable. Browser identity defaults to session-only use. With explicit remember opt-in, the validated public Relay room is committed with the Host pin/identity in the same IndexedDB transaction; older records without room retain Direct semantics. Root/manifest launches restore that room before selecting transport. Same-Host re-enrollment refreshes public room and revision atomically only after pin verification and ready; failure preserves the previous binding, and Forget removes this routing metadata with the credential. A failed save never claims persistence succeeded.

If the optional Direct entry fails to start, the desktop service still starts, `directEnabled` becomes false for that run, and it attempts to persist the disabled state. Trusted local `remoteControl.status.directError` also reports a persistence failure. A failed enable leaves no listener. When the Host disconnects, the browser clears old connection projections. Transient failures retry with jittered 0.5–30 second backoff, paused while hidden or offline. Foreground recovery revalidates local identity and establishes a fresh connection, baseline and subscriptions; authorization or protocol refusal stops automatic retries.

Read requests use `{id,method,params,context?}`. `host.describe` takes an empty params object; `project.list` accepts optional cursor and limit and returns `{projects,nextCursor}`. Optional `context.projectId` must identify a currently authorized, registered project. Host/project responses contain only ProjectView metadata, never desktop snapshots, project roots or service credentials. Overview responses add authorized bounded task titles and attention summaries. ready and host.describe report effective capabilities and limits; write methods are limited to the ordinary-session, exact Turn stop, synchronous-interaction, and asynchronous Task-reply scopes below.

`work.list` requires `context.projectId`, accepts `filter: all|active|attention` (default all), `cursor?` and `limit?`, and returns `{projectId,serviceGeneration,data,nextCursor,complete}`. `attention.list` requires the same project context and accepts cursor/limit; its bounded AttentionSummary page also reports `summariesComplete`. Both require a currently online compatible existing Core connection and recheck the grant after asynchronous reads; neither starts a service or repairs configuration. ready and host.describe include the implemented method list.

Native `areal/work/overview` applies principal/thread restrictions before selecting pages. It reads existing Thread/Turn, TaskRun, pending interactions, queues and Task Channel state without transcript hydration or new persistent state. Ordinary archived threads are omitted. Task coordinators and workers represented by a Run are not duplicated as ordinary sessions; workers remain attributed under the Run. Results may be readable while execution is ongoing or failed; availability does not imply success. Timestamps use source records only, with null when no recorded update exists.

Overview defaults to 30 entries, allows at most 100 and stays within 128 KiB. Titles are at most 512 UTF-8 bytes and attention summaries 256; each work card carries at most 32 attention references and 32 workers, with separate actual counts, completeness and `summaryTruncated` fields. Native thread/task/run/interaction/question identities are the references for desktop details. Truncated summaries do not imply full attention or worker data was loaded; attention.list reports `summariesComplete: false` in that case. No full parameters or transcript are included. `availableActions` remains empty; create/send controls use connection capabilities and current detail state.

The production Remote page polls work only while visible every five seconds, refreshes when visible again or on `remote-operation-complete`, and marks incomplete page counts explicitly. The operation hook rereads Core rather than guessing a result. Foreground refresh replaces the page; load-more is explicit. No global Inbox subscription is created.

### Session observation and history pages

`session.open` accepts `{context:{projectId},params:{threadId}}` and returns `connectionId/gatewayGeneration/serviceGeneration/subscriptionId/projectId/sequence:0/snapshot`. Each connection owns one detail reference. References to the same project and Thread share a dedicated read-only Core observer. Each open or refresh obtains an atomic baseline and ownership through `areal/thread/observe`; `atomicObserve/atomicObserveOwnership/subscriptionRemoval` are required, otherwise `CORE_INCOMPATIBLE` is returned. Ownership is not inferred through Gateway Task scans. Turn, Goal and configuration events refresh it; Task-only changes require refresh or reopen.

`session.updated` carries the same identity, increasing sequence and a replacement snapshot. `session.invalidated` carries an error and unavailable/truncated state. Old identities cannot mutate the current view; sequence gaps reopen and replace the baseline without durable delta replay. CoreClient establishes the baseline in its synchronous result dispatch, and publication synchronously rechecks the device grant, Desktop client, endpoint and service generation.

`session.history` accepts `{threadId,cursor?,limit?}` and returns the same detail identity, turns, nextCursor, hasMore, truncated, unavailable and range. Pages contain at most 100 Items; body previews are limited to 1024 UTF-8 bytes. Bodies that cannot be inlined carry a `bodyDetail` Thread/Turn/Item reference and an unavailable reason; full viewing currently requires the desktop, without a generic file reader. Cursors address the current Core-accessible range, not durable replay. `subscription.close` accepts `{subscriptionId}` and releases only the caller's matching reference.

Limits are 16 dedicated project observer connections and 16 Thread subscriptions, including pending creation; each project's serialized read queue admits 16 pending requests. Only an already-online project with authorized demand connects. Observation never ensures/resumes Core, configures, binds or takes over the ToolHost. Each connection has a combined 2 MiB queued-send budget: 1 MiB for plaintext output and 1 MiB for the WebSocket send queue. Bounded in-flight Noise framing is separate; queue limits are not a total process-memory bound. A native observer message exceeding 4 MiB invalidates the project's Remote views and closes that observer, while preserving the Desktop ToolHost. This does not guarantee CPU or memory isolation for Core history hydration. Closing the final reference releases the dedicated connection without cancelling Core work. A Web client `session.open` timeout after 15 seconds closes the originating connection to release any observation subscription that may have been created but remains unconfirmed; other read-only request timeouts do not disconnect the connection.

Run `pnpm --dir clients/gui run test:remote-session` and `AREAL_CORE_BIN=/absolute/path/to/areal pnpm --dir clients/gui run test:remote-session-e2e`. The latter uses isolated Core/Runtime, real Electron, the production Remote page, a deterministic model and explicit transport faults. It does not verify the system keychain, a distribution package, public networking or physical mobile devices.

### Original Turn results and raster review

`review.read` requires current `observe` and `review`, with `{threadId,turnId,itemId?,cursor?,limit?}` and `context.projectId`. It reads `thread/read` through the existing dedicated read-only connection without starting, opening, resuming or configuring a desktop Thread or registering a tool host. Responses bind `projectId/threadId/turnId/itemId/connectionId/gatewayGeneration/serviceGeneration`. `review:{encoding:"json-utf8",offset,totalBytes,chunk}` pages a JSON body; encrypted `nextCursor` values are valid only for the current Gateway/device connection and original content. `limit` is a UTF-8 byte budget, default/maximum 16 KiB; the complete JSON body is at most 4 MiB. Content changes invalidate cursors rather than combining versions.

The complete body preserves original `turnStatus/error/partial`, Item-keyed text, phase, tool status and executionOutcome, plus diff state, scope, base/head, notice, provenance and path-keyed structured hunks. Failed or interrupted Turn text is explicitly partial, never inferred success. `taskRunStatus:null` means this interface has no TaskRun status for the original Turn: coordinator TaskRuns bind a Thread rather than a Turn, while exact worker Turn bindings exist only inside a known TaskRun. Current Task ownership or the latest Run cannot substitute for historical association. Overview/Task reads continue to show TaskRun status separately.

Diffs reuse existing historical Runtime file-write reconstruction without reading the current working tree. Only completed tools with an explicitly succeeded Runtime outcome qualify. When `execution.effectiveArguments` is present, that object is mandatory; only an absent field permits the Core-parsed `item.arguments` object. Explicit null, strings, arrays or other invalid overrides never fall back; `originalArguments` is not parsed and `modelArguments` is not used. Argument and result paths must match, and confirmed UTF-8 byte size and SHA-256 must match the after text. Overwrites and patches also require a continuous version chain with complete before text/hash. Creation needs no existing before text. A complete `fs_read` still requires zero offset, eof, verified byte size and hash; clamping the requested length does not relax these conditions. Shell, rename, deletion, binary, missing-before evidence and unfinished Turns are explicitly unavailable. Notices retain those limits; verified writes do not establish exclusive provenance for every change in the Turn. Each review still reconstructs text and diff from original records; paged body budgets do not bound Core history reads or reconstruction CPU/memory.

The first page returns at most 16 `artifacts` with `{itemId,mime,size,artifactRef}`. The Host issues opaque encrypted refs only from original Turn/Item AgentMedia or tool arealMedia, binding grant revision, device connection, project, service generation, Desktop client identity and native blob metadata. Upload registration alone does not establish Turn membership. Entries beyond the list budget, non-native blobs, unknown MIME and metadata above 16 MiB do not receive readable refs and direct users to Desktop. Each `artifact.read {artifactRef,offset,length}` re-reads exact membership and current authorization; length is 1–48 KiB. Its response carries the same identities, artifactRef, offset, totalBytes, nextOffset, base64 and `raster:{mime,width,height}`. Missing resources return `RESOURCE_UNAVAILABLE` without file substitution.

The Host uses authenticated GET only to the verified native endpoint, rejects redirects, streams with metadata/Content-Length/actual-byte limits, verifies SHA-256 and raster signature/dimensions, cancels on error, revocation or timeout, then re-reads membership and checks identity immediately before publication. There is no body cache: every chunk request streams the entire original blob again. Existing Core HTTP still allocates the whole blob; Remote chunk limits do not establish native allocation bounds or large-image throughput.

PNG/JPEG/GIF/WebP dimensions are at most 16384 per side and 16 Mi decoded pixels. Animated PNG/GIF/WebP do not receive inline previews. The browser independently checks totals, chunk sizes, signatures and dimensions, then verifies actual browser decoding before creating a blob URL. Only one image remains active. Closing review/Session, switching images, or changing grant/connection/service clears content and revokes URLs. Text uses textContent, HTML/SVG never executes, external resources never load automatically, and no API/artifact caching or file mutation occurs. Source and fixture checks do not establish actual Native, browser/phone decoding or package acceptance.

### Ordinary-session commands and admission queries

Source implements `session.create`, `session.send`, `turn.stop`, and `command.read`; fixture and build checks do not establish native T18–T22, package, or physical-device acceptance. New writes use the commandId and complete context from C3. Queries use `{context:{projectId},params:{commandId}}` and still require the device's current project grant and the original command's capability (initial observe, then `submit` for create/send, `interrupt` for stop, or `answer` for interaction.respond). Existing associations remain readable across grant revisions and service generations without redispatch. If a concurrent request encounters an asynchronous admission refusal, it first checks for a durable same-key association at the serialized journal read point: matching semantics return the original state, changed semantics return COMMAND_CONFLICT. Current authorization and connection identity checks still apply.

Creation uses the Host's default ordinary Profile and requires native `threadStartAdmissionGuard`; a Workflow default Profile yields `UNSUPPORTED_PROFILE`. Sending requires `turnStartAdmissionGuard` and retains the original threadId, text, and expectedConfigRevision without automatic enqueue. A temporary reference through the existing bounded read-only observer owner checks atomic ownership and state without replacing the user's detail reference. Task ownership, busy state, and changed configuration/queue conditions produce structured refusals. Core rechecks ordinary ownership, idle admission, and configuration revision under its lock; prechecks are not the final admission authority. A paused empty queue does not block an explicit new turn or automatically resume the queue; retained pending/running queue items still block ordinary new-turn admission.

The Host persists the scoped association and generated journal UUID (also the native requestId for create/send) in the existing pending/outcomes files before the final grant check and synchronous RPC initiation in the grant-write queue. The RPC response does not hold that queue. Terminal records retain the semantic digest, immutable grant provenance, restricted Thread/Turn IDs or error, and are saved before pending removal; they do not duplicate text or transcript. A failed pending write prevents dispatch; a failed outcome write retains unknown; a saved terminal outcome wins over leftover pending. Each project admits at most 4096 combined pending/outcome records, with a 72 KiB Remote pending-record budget and a 4 KiB terminal-record budget. Deduplication evidence is not evicted. Text has a separate 64 KiB UTF-8 limit.

CommandView returns `commandId/method/target/operationId/admissionState/submissionUnknown`, plus `nativeRequestId` for methods with a native request key; known terminal states may include `threadId/turnId/error:{code,coreCode?,message}`. Creation recovery uses the exact native receipt threadId; send recovery uses the exact Turn result. Queries only load local journals and, when needed, call `areal/request/read` on an existing online connection. They never start Core, open sessions, configure, or replay. Saved terminal outcomes remain readable while Core is offline. Authorization and connection identity are rechecked before publication after native reads or submissions. Direct command errors use fixed protocol messages. Underlying filesystem/network errors, including string error codes, never forward raw messages, paths, or credentials, and conservatively direct the client to query the original command.

The production page retains commandId, original parameters, and draft in memory before the first transport call. Disconnects/timeouts allow only original-command queries; reconnection automatically performs read-only queries. notFound does not prove non-execution. Only explicit acceptance clears the matching unchanged draft. Refusals/conflicts preserve it; another explicit send creates a new intent. Session-only identity and command records still disappear with the page. Remembered devices wait for an IndexedDB transaction committing minimal command locators before transport send. A locator contains only Host, project, original commandId, method and target identities, with an optional approval arguments digest; never body, answer, decision or reviewToken. Reload restores every locator as unknown and queries only its original command.read. Pending, unknown and notFound remain; accepted/rejected release the unresolved state only after local cleanup commits. A separate query entry remains when the original target is no longer displayed.

Checks: `pnpm --dir clients/gui run test:remote-command` exercises disk faults with RPC fixtures; `pnpm --dir clients/gui run test:remote-session` exercises the production page with DOM/transport fixtures. The native entry is `AREAL_REMOTE_NATIVE_ALLOWED=1 AREAL_CORE_BIN=/absolute/path/to/areal pnpm --dir clients/gui run test:remote-command-e2e`, using separate Host processes, actual Core/Runtime and Noise, with 100 deterministic race iterations by default. Run it only after native startup is authorized; source availability does not imply a pass. Setting `RC05_RACE_REPETITIONS` below 100 is diagnostic and does not meet the race acceptance threshold.

`turn.stop` accepts only `threadId` and `expectedTurnId`, requiring the `interrupt` capability and native `turnInterruptAdmissionGuard`. Observed Task ownership returns `TASK_CONTROL_REQUIRED` and directs users to explicit Task controls; a finished or replaced original Turn returns `TARGET_CHANGED`. The Core guard under its lock remains authoritative; target or ownership changes after prechecks return a native conflict. Both original IDs enter the semantic digest and journal target. The Gateway sends `turn/interrupt {threadId,turnId:expectedTurnId,admissionGuard:{ordinarySession:true}}` unchanged and never selects a newer Turn.

A stop operationId is only the journal UUID persisted before dispatch. Native interrupt has no requestId, so the Gateway neither injects one nor returns a fabricated nativeRequestId. Saved explicit responses are recoverable; a lost response or outcome-save failure remains unknown. Stop `command.read` never calls `areal/request/read` or repeats interrupt. An unknown stop association does not block another device stopping an exact target or a new message after Core confirms idle; native guards still check every new command. Desktop pending controls and submit/configure/lifecycle blockers exclude these exact Remote stop records and the synchronous-interaction records described below. The association remains intact in the existing journal; unknown create/send records still block, and the exclusion does not claim stop success.

The production page enables Stop only for an explicitly inProgress ordinary Turn in the current projection. Each target retains its own intent; stopping a later Turn requires a new explicit action. Admission and observation of the original Turn appear separately: only an explicit completed/interrupted/failed status for that same Turn is terminal evidence. A changed activeTurnId, absent Turn, or disconnect is not completion. Observing a terminal state never converts unknown into accepted or claims this device caused the stop. Users can refresh the Session when target state is unavailable. Stopping always preserves message drafts.

### Synchronous interaction review and response

Source exposes `attention.read` and `interaction.respond`, requiring `observe` and `answer` respectively. Native T25–T27, package, and physical-device acceptance remain separate. The AttentionSummary's `threadId/turnId/interactionId` identify the original target; they are never endpoints, paths, or credentials. Detail requests are `{context:{projectId},params:{threadId,turnId,interactionId,cursor?}}`. Only tool approvals and synchronous questions are implemented here, not Task Channel questions.

Detail reads reuse SessionObservers' dedicated read-only connection and its connection/pending budgets for `areal/interaction/list`, preserving the current Session subscription and Desktop ToolHost. After every asynchronous read, publication synchronously rechecks the connection, current grant, project object, Desktop client, endpoint, service identity and generation. An entire native response over 4 MiB becomes unavailable; no native paging or alternate service read is introduced.

Responses retain `projectId/serviceGeneration/threadId/turnId/interactionId/kind/status/expiresAt/argumentsDigest`; expiresAt is Unix seconds. `review:{encoding:"json-utf8",offset,totalBytes,chunk}` pages the serialized `{tool,generation,effectiveArguments,effectivePermissions,questions}`. Each chunk contains at most 16 KiB UTF-8 without splitting characters, keeping JSON-escaped messages bounded. A complete single-page result also exposes those fields directly; multiple pages must be joined at contiguous byte offsets before parsing. `complete/nextCursor` describe review completeness; the final chunk alone is not the entire body.

A Gateway-lifetime in-memory signature binds each continuation to device connection, grant revision, project/service identity, original target/digest, expiry, and the entire serialized review body. A later page requires the previous page's cursor; only the final page provides `reviewToken`. Changed content, targets, grants, or connections require a new review. The proof means the complete content was provided to this connection; it neither claims the human read it nor grants native execution authority.

Submission uses C3's full context and commandId. Approval params are `{threadId,turnId,interactionId,argumentsDigest,decision,reviewToken?}`, with only `allowOnce/deny` decisions. allowOnce requires the complete-review proof and a current Core read checking pending status, expiry, original digest and content; incomplete review returns `REVIEW_INCOMPLETE`. deny requires neither proof nor readable full content: original IDs/digest pass unchanged to Core, so a previously read original request can still be denied when its body is unavailable. Without the original digest, use Desktop; the Gateway never invents it. Question params are `{threadId,turnId,interactionId,answers,reviewToken}`. Questions/options come only from Core; answers must exactly match its actual question keys, at most eight questions and 4096 UTF-8 bytes per answer, with option membership required when free text is disabled.

The Host deeply snapshots intent. Semantic deduplication includes original IDs/digest/decision/answers, excluding the connection-bound review proof. Existing associations, including those durably admitted during a concurrent preflight, take precedence over fresh-review refusal; changed semantics under the same key return `COMMAND_CONFLICT`. Initial dispatch shares the grant-write queue for its final synchronous check and RPC initiation, while awaiting the response does not hold revocation. Core remains the atomic pending/Turn/digest arbiter. The Gateway never uses Desktop respond's cached Turn/digest substitution.

The interaction's `operationId` is a separate journal UUID. Native `requestId` remains the original interactionId, without a fabricated native command-receipt key. Explicit responses are saved in existing outcomes before pending removal; accepted means decision admission, not tool effects. Lost responses, Host crashes, or outcome-save failures remain unknown, without native request-receipt lookup or replay. `command.read` initially requires observe, then the current original capability (answer here) for any found association and before publication. It may also return `observedState:{source:"interaction.read",status,expiresAt?,threadId?,turnId?,interactionId?,provesCommandAdmission:false}`. answered/expired/cancelled never imply this command was admitted; failed observation reports status unavailable.

Like exact Remote stop records, interaction UNKNOWN associations remain durable but do not become Desktop pending controls or unknown-send blockers for later submit/configure/lifecycle checks. Native active-Turn/configuration guards remain authoritative; unknown create/send records still block. The production page supports original-target review, more pages, allow-once/deny, Core question forms, and original-command queries. Incomplete review cannot allow; conflicts refresh the original target and reconnects only query. Admission and independent observation are separate; opening review preserves the active Session.

### Asynchronous Task questions and replies

Source exposes `task.question.read` (observe) and `task.question.reply` (answer). Native T28/T29, package and physical-device evidence remain separate gates. Detail params are the original Inbox `{taskId,runId,questionId}`. The response contains `projectId/serviceGeneration`, those original IDs, `kind:"asyncQuestion"`, Core `questions/status/expiresAt`, and `taskPaused/taskCancelled/runStatus/complete`. Expiry is Unix seconds or null. Reading never opens or resumes the coordinator Thread or replaces the current Session detail.

Reads reuse SessionObservers' dedicated read-only connection, authorization and queue budgets. `areal/task/read` verifies the original Run, followed by at most eight `areal/channel/read` pages of at most 100 messages; unrelated Channel history is not returned. The detail has at most eight questions and 32 KiB of serialized questions. A complete original question unavailable within those bounds returns `complete:false` and cannot be answered. Every asynchronous read and final publication checks the current grant, project object, service identity and connection generation. Core question content is immutable under its questionId; no Task review proof is introduced.

Reply params are exactly `{taskId,runId,questionId,answers}` with C3 commandId/context. Deep snapshots precede awaits. Semantics bind the original Task/Run/question and canonically sorted answers: changed answers or targets under the same key return COMMAND_CONFLICT, while saved associations precede fresh state prechecks. A new reply rereads complete Core questions, requires exact question keys, nonempty answers, at most 4096 UTF-8 bytes per answer and option membership where required. Expired, answered, terminal or cancelled targets are refused; Core's atomic check remains authoritative. Original IDs and answers go directly to `areal/channel/reply`, using the journal operationId as native requestId, without Session text conversion, pause or resume.

A validated explicit native response is saved in existing outcomes as `receipt:{accepted:true,messageId,taskId,runId,channelSequence}` before pending removal. Lost responses, Host crashes and failed outcome persistence remain UNKNOWN: no nonexistent Task receipt API, replay, service restart or matching-answer inference. `command.read` initially requires observe, then answer for a found association. It may return independent `observedState:{source:"task.question.read",taskId,runId,questionId,status,expiresAt,taskPaused,complete,provesCommandAdmission:false}`. Offline recovery uses only saved receipts; unavailable observation reports status unavailable. The original UNKNOWN association remains durable without becoming an unknown-send blocker for subsequent Desktop Task control; Core still validates new operations.

Task Inbox opens the question and Core options without selecting its coordinator Session. The page explains that the Agent may continue useful work while awaiting an answer and that replying to a paused Task does not resume it. Remembered devices commit original Host/Project/commandId/Task/Run/question locators to IndexedDB before network send, never persisting answers. Reload only queries original command.read and never resends. A changed detail, connection or identity during persistence prevents dispatch; failed locator retirement remains UNKNOWN.

### Browser lifecycle and static shell

Forget this browser device synchronously stops connections, retries and stale asynchronous writes before atomically clearing identity, Host pin and unresolved locators. A failed clear remains visibly unconfirmed. Other tabs invalidate through change notifications and storage revalidation before connections/submissions; stale pages cannot recreate cleared identity. This does not revoke the Host grant, which must be revoked separately on Desktop. Another Host invitation cannot replace a remembered pin.

Drafts default to page memory. Restore drafts in this tab is a separate choice for remembered devices, storing text in this tab’s sessionStorage. Reload can restore it; closing the tab ends the session, subject to the browser’s own session-restoration policy. Storage errors are explicit and reconnection never submits drafts. Recovered commands contain no original text, so an accepted recovery query cannot guess which draft to clear. IndexedDB and sessionStorage are not OS keychain protection; malicious same-origin scripts may read identities and content.

The build produces remote-assets.json, a manifest, 192/512 PNG icons and a standalone Service Worker. Direct serves only the Remote entry’s complete transitive asset closure from the descriptor, checking hashes and MIME without exposing Desktop or the whole dist. Worker installation verifies static hashes and caches exact same-origin GET paths by content version; queries, APIs, invitations and business content are excluded. A new Worker waits until old pages close; the page only displays an update notice, without skipWaiting, takeover or automatic mid-submission reload. An offline shell does not imply an online Host. GUI quit disconnects the interface while the existing background Host and Core retain their established lifecycle. After explicit background-service stop, the page cannot remotely wake or repair Core. Direct persists its dedicated port and configuration, binds that port on restart and reconciles recorded mappings. Actual HTTPS reachability, phone installation and background operation require separate validation.

Checks: run `pnpm --dir clients/gui build`, then `pnpm --dir clients/gui run test:remote-browser` and `pnpm --dir clients/gui run test:remote-static`. These cover storage/production-page contracts and actual built HTTP boundaries, not physical phones, system keychain or public deployment acceptance.

## C1. Transport, identity and versions

Application messages run inside the existing libp2p Noise channel. The library owns identity, randomness, nonces, AEAD and replay protection. Keep the existing `areal.remote.v1` Noise prologue as a transport compatibility marker; it is not this application's version. Encrypted hello explicitly requests `areal.remote.v2`. Hello accepts optional `clientKind: "web" | "ios" | "android"`; other values fail with `INVALID_PARAMS`. This client-provided display metadata is saved only after local pairing approval and grants no authority. Settings displays absent metadata as Web browser. Reconnects do not update saved metadata. Unsupported versions fail without mutation downgrade.

Android hello requires a desktop accepting `android`. Older Hosts reject it, and their configuration parser rejects persisted Android grants. Direct downgrade after approval is unsupported. Android `https://localhost` belongs in Relay `allowedClientOrigins`; iOS `capacitor://localhost` belongs in `allowedAppOrigins`. See [Android development](../development/android-development.en.md).

Direct exposes a dedicated `/remote/socket` alongside static PWA assets and nonsensitive health on a separate low-privilege listener. Relay retains room/channel byte forwarding with outer `areal.relay.v1`; it never interprets business methods. Production requires HTTPS/WSS; only loopback development permits HTTP/WS.

Hello carries apiVersion, client version, display name and inviteSecret for first pairing. Restoring a paired identity needs no invitation. The Client must authenticate the pinned Host identity before sending secrets. The authenticated Noise peer, never a client-provided deviceId, identifies the caller.

ready returns hostId, gatewayGeneration, connectionId, apiVersion, grantRevision, capabilities and limits. Core service generation is distinct. No private keys, Core/desktop Bearers, authFile paths, absolute project roots or provider/MCP credentials cross this boundary.

## C2. Pairing and authorization

Invitations contain a Host-generated 256-bit random secret, a 120-second lifetime and single-use consumption. QR codes open an HTTPS URL carrying the invitation in its fragment. Remove invitation fragment fields before application network requests, retaining only the public Host pin and optional room; never log or persist the secret in analytics, localStorage or Service Worker cache. Offer copy/paste alternatives. Host time decides expiry.

States are created → claimed → awaitingLocalApproval → approved, or expired/rejected/cancelled. Atomic claiming consumes the invitation but grants no authority. Desktop confirmation shows name, identity fingerprint, existing projects and capabilities; persist the grant before ready. Names are untrusted descriptions, not identity proof.

DeviceGrant contains devicePeerId, displayName, projectIds, capabilities, revision and status (active/reviewRequired/revoked), with optional `clientKind: "web" | "ios" | "android"`, `pairedAt` and `revokedAt` (millisecond timestamps). On approval, a displayName already used by another non-revoked device gets a suffix such as `Chrome · macOS (2)`; browsers report “browser · system” by default. `renameDevice` changes only the desktop display name without bumping revision or disconnecting; `forgetRevoked` deletes all revoked device records and their push commands. Status also reports runtime-only `online` and `lastSeenAt` (latest connection during this run, not persisted). Projects are explicitly selected existing entries, never future-project inheritance. Observer grants observe/review; Operator adds submit/interrupt/answer/pauseTask. Neither grants remote administration, pairing approval, configuration, terminals or permission memory. This is project scope, not human identity management or an OS sandbox.

Re-read the current grant on admission, result serialization, projection publication and every artifact chunk. Revision changes close affected channels and clear their projections/streams. Revocation prevents further admission/output and does not retract downloaded data. After persisting command correlation and before handing it to Core, the Host must recheck the current grant at its serialized authorization boundary; earlier revocation prevents dispatch. Requests already admitted and handed to Core may acknowledge after revocation, so do not promise to retract already transmitted operations. Failed persistence is a failed revocation, not success.

## C3. Envelopes and admission

One bounded JSON object per application message. Reject unknown request fields/methods; clients may ignore unknown events and refresh the baseline. Envelope fields are id, method, optional commandId, context and params. context carries gatewayGeneration/grantRevision plus projectId/serviceGeneration for project methods. id is a 1–64-character connection-local correlation key. Every mutation requires a UUID commandId generated and saved by the Client before first submission.

The durable correlation key is Host + authenticated devicePeerId + Project + commandId. Extend existing pending/outcomes records with the action, canonical semantic digest, journal operationId, native Core requestId when supported, original target and grant revision. Generate and persist the operation UUID before dispatch, using it as the native requestId for create/send; do not directly use an untrusted client key in the shared Core principal namespace. Persist a created Thread identifier for recovery.

Same key and semantics returns original status; changed semantics returns COMMAND_CONFLICT. The digest excludes RPC IDs and new transport generations, but includes action, target, content/answers and reviewed conditions. Original receipts can be queried across connection/Core restart subject to current authorization. New commands must match current generations; previously admitted commands are only queried, never redispatched on generation change.

Write the correlation before Core dispatch. Reuse the submission journal, not a second execution ledger; retain necessary recovery input and receipt references rather than transcript copies. Existing capacity rules apply: reject at capacity rather than silently forgetting deduplication keys. P0 adds no unsafe automatic receipt eviction.

Admission states are pending/accepted/rejected/unknown. accepted is not execution success. command.read can return notFound, which is not proof that in-flight work never happened. Sent requests that time out become unknown and are queried without automatic mutation replay; notSent is valid only when the Client knows send was never invoked.

For interactions/Task controls without public native receipt lookup, use a stored explicit response when available. A changed target may be reported separately as observedState, not a fabricated acknowledgement that this device caused the change. Otherwise preserve unknown; never match similar text to attribute a command.

### Device push registration and notifications

`device.push.register` and `device.push.unregister` are Host-scoped writes requiring a UUID `commandId` and no project context. Registration accepts `{platform:"apns",token,environment:"production"|"development"}`, with a 64–200 hexadecimal character token. It requires the current Relay to advertise push support, otherwise returning `RESOURCE_UNAVAILABLE`. Unregister uses empty `params:{}`. Results are `{registered:true|false}`. Registration preserves grantRevision, grant updates preserve the token, and revocation removes it. Tokens use existing encrypted `remote.json` storage; public Host status exposes `pushSupported`, and device projections expose only `pushRegistered`.

The Host commits registration outcomes and device grants in one encrypted save. Push receipts bind device identity, commandId and a semantic digest. Identical retries return the original outcome; changed semantics return `COMMAND_CONFLICT`. A context-free `command.read {params:{commandId}}` queries only the authenticated device’s push receipts and rechecks its current observe grant. Known outcomes return `{commandId,method,admissionState:"accepted",submissionUnknown:false,receipt:{registered}}`; missing receipts return `{commandId,admissionState:"notFound",submissionUnknown:true}`. Lost responses or failed local cleanup only query the original command without replay; notFound does not prove non-execution. The Host retains at most 4096 receipts and refuses new device push writes, including unregister, at capacity without evicting unresolved records. Project actions retain their existing context-scoped Core journal.

The sender reuses RemoteControl and native session observation. It scans attention only for online projects granted to registered devices, every five seconds, with at most eight bounded reads per project per cycle and four native overview pages per read. The first complete scan establishes a baseline. Native attentionRef deduplication retains at most 4096 references. Only approvals, synchronous questions and Task asynchronous questions trigger notifications. Incomplete baselines, exhausted capacity or unavailable reads can miss notifications. The first notification sends immediately; subsequent events in the same project reuse a collapse ID for 30 seconds with an updated count. Dispatch rechecks project identity, capabilities, token and connection state. Devices with an active Direct or Relay connection receive no push.

Turn notifications follow only exact threadId/turnId or queueItemId associations in that device’s existing session.send journal. At most 16 push observers share existing native subscription budgets. Closing the UI observer can leave the exact turn watcher active; reopening the UI reads a fresh baseline. Queue association uses the same queueItemId’s turnId, never a guessed latest turn. Terminal startup baselines are not replayed. Old turns absent from bounded baselines, removed queue items, observer capacity or service-generation changes can cause missed notifications. Revocation, offline state and shutdown release observers. Unavailable Relay, throttling or send-budget exhaustion drops notifications without retry queues. Real APNs and lock-screen delivery still require device acceptance; see C12 for Relay boundaries.

## C6. Snapshots and deltas

Open a bounded Remote projection using the atomic Core areal/thread/observe baseline. Serialize baseline capture and delta enqueueing for a projection, sending the baseline first. Reading before independently attaching an observer is not safe.

Observation messages carry connectionId, gatewayGeneration, serviceGeneration, subscriptionId and a sequence monotonic within that connection's subscription. The window is memory-only, not permanent replay. Old-connection or old-service asynchronous results cannot mutate new projections.

On sequence gaps, lag, restart or protocol mismatch, stop applying deltas, reopen and replace the baseline rather than appending it again. Support text deltas, Item completion/replacement, Turn state and invalidated interactions. Only Core determines final state. Large Items use bounded previews and paged history.

## C7. Concurrency: stop, interactions and Tasks

**Turn stop:** carry and forward the exact expectedTurnId without replacing it with a newer active Turn. Ended/changed targets return TARGET_CHANGED or explicit terminal state. Request acknowledgement is not completion; wait for that Turn's terminal state. Another device's stop cannot be fabricated as this command's acknowledgement.

**Synchronous interactions:** show tool name, bounded effective arguments, truncation information and argumentsDigest. Page oversized arguments. Disable allow when a complete reviewable representation cannot be obtained, directing the user to desktop while still permitting deny. Submit the original threadId/turnId/interactionId/digest; both Host and Core check the binding. Permit only allowOnce/deny. Question answers must cover the real questions/options, at most eight answers, each at most 4096 UTF-8 bytes. Late/already answered/cross-Turn decisions conflict and refresh, never retarget.

**Asynchronous questions:** Task/Run/Question must identify a pending unexpired native question. Use channel/reply, not ordinary chat. Answering need not pause or immediately interrupt the agent; show actual Run state.

**Task pause:** confirm that current work and future scheduling are paused. This prevents a Run-changing race between Gateway checks and Core mutation. Wait for Run/worker settlement; coordinator Turn completion is insufficient. P0 excludes task.cancel/resume and schedule editing.

## C10. Recovery

On disconnect, mark unconfirmed mutations unknown and retain commandId. Retry connections with jittered 500 ms–30 s backoff. Reauthenticate, reload capabilities/overview/current Session, then query receipts read-only. Remote recovery must use observeOnly, never the existing default reconcile path that can repair configuration.

On Core restart, verify the compatible running service's new generation; discard old events and preserve UNKNOWN tool facts. Do not acknowledge unknown tools, start/restart stopped services or widen permissions remotely. GUI closure leaves the independent adapter alive. Relay restart/network changes do not cancel accepted work. OS sleep is outside the protocol.

Trusted desktop-background `RemoteControl` is the sole owner, retaining the same system-secure-storage-encrypted `remote.json`. It derives targets from its actual live `127.0.0.1` server, never accepts renderer-supplied listeners, targets or executables, and never forwards Core or desktop management endpoints. These operations reuse the local `remoteControl` command; they are not mobile Remote APIs.

The pending journal must persist before mutation and exact mapping verification; HTTPS is advertised only after the final save. A failed final save retains pending. Recovery reconciles ownership without replay, and absent or changed mappings are not advertised as available.

Funnel changes only the exactly owned mapping, with no additional configuration owner. Publication checks stable CLI version, login, certificate domain and local `Self.CapMap` HTTPS/Funnel grants plus one unambiguous port grant; supported ports are 443, 8443 and 10000. Scope changes persist pending before withdrawing HTTPS advertisement, cancelling invitations and closing existing connections, even when the HTTPS origin is unchanged. Existing device grants, Host pins and per-operation checks remain intact. Restart only reads pending scope state as `reconciliation: destination|source|absent|changed`, retains pending and does not advertise HTTPS. Explicit local `networkRecover` saves the observed destination/source scope or absence; drift remains unresolved. There is no replay, public fallback or inferred authorization. Private restoration and exact removal remain available after Funnel grants disappear; interrupted removal first reads the actual scope and cannot delete a foreign mapping. Public-phone, certificate, policy and shutdown reachability are uncertified; local fixtures are not public deployment acceptance.

HTTP accepts only the exact Host for current loopback or configured HTTPS origin. WebSocket must also match the exact Origin associated with that Host. The two tuples cannot be mixed; forwarded identity headers are not trusted. CSP allows only the current origin and its exact WS/WSS origin. Origin changes cancel invitations and disconnect old connections. Pairing uses the verified active HTTPS origin, otherwise an explicitly local development link.

`disableDirect` persists disabled state, cancels invitations and closes ingress before awaiting exact owned-mapping removal. Failed disabled-state persistence rejects the operation and retains prior state. Later cleanup failure retains pending/diagnostics and never reopens ingress. Process `close()` synchronously closes ingress and retains the mapping, starting no asynchronous CLI cleanup. The existing service stop path refuses exit while local operations are in flight. Restart binds the fixed port and reconciles owned/pending records before advertising HTTPS. Actual networking and phone evidence remain separate acceptance layers.

### Implemented encrypted configuration and legacy identity migration

The trusted Desktop background `RemoteControl` is the sole configuration owner. Electron `safeStorage` encrypts the complete configuration object; the existing Backend saves it as a `{encrypted}` envelope in `remote.json` using temporary-file replacement. This is neither Core configuration nor a JSON interface editable by phones. Unavailable secure storage or the `basic_text` backend rejects enable.

| Actual fields | Meaning and boundary |
|---|---|
| `identity`, `deviceGrants` | Host identity and device grants; see C2 for grant fields. The Host private key is never sent to browsers |
| `enabled`, `relay`, `relayProtocol`, `room`, `capability` | Relay switch, HTTPS origin, protocol and enrollment; `enabled` controls only Relay, and the durable capability stays in encrypted configuration |

## C12. Minimal Relay service

Trusted local `remoteControl` action `enable` accepts `{relay, code?, confirmed: true}`. `relay` must be an exact HTTPS origin; initial enrollment or changing origin requires an administrator code, while the same enrolled origin may be explicitly enabled without a new code. Host uses system TLS verification and an Origin-less `POST /enroll`, rejects redirects, persists capability/room in existing encrypted `remote.json`, then connects outbound WSS. `disable` closes Relay but retains encrypted enrollment for explicit reuse. Legacy Relay configuration is not automatically upgraded. Trusted status exposes only public origin/room/pin, connection state and sanitized errors, never capability.

`pair` accepts optional `transport: "direct" | "relay"` (Direct by default); Relay must be connected. Links contain only public origin, Host pin, room and a 120-second invitation. Production PWA completes Relay client registration and ready-channel through one wire factory before the same Noise, hello, authorization and business path. Host owns one session acceptor, observer and device/handshake budget; revocation and scope shrink close both transports. Shared ceilings are 16 connections, 8 unfinished handshakes, 2 connections per device and 8 MiB each of Host receive/send backlog. Relay per-channel send backlog is 1 MiB; raw chunks are at most 49152 bytes and outer JSON including base64 stays below 512 KiB. Channels drain fairly and slow-device closure remains isolated.

Host Relay `ready` must carry exact `limits: {framesPerSecond, bytesPerSecond, maxFrameBytes, heartbeatIntervalMs}`, with optional `push:boolean` for APNs support. An older service without `push` means unsupported. Client ready-channel is unchanged. Missing/invalid limits from an older service, or budgets insufficient for heartbeat reserve and data, stop Host automatic retries with a protocol/budget diagnostic. Host never guesses default ceilings; administrators adjust service policy then explicitly re-enable in Desktop. Existing deliberately low service configurations remain accepted without relaxing operator policy.

After enrollment's one-second window, Host drains data and close through the same bounded queue paced by actual JSON/base64 bytes. Each chunk stays within one quarter of the service byte budget, sustained rate uses at most three quarters, and frame pacing reserves automatic pongs plus a boundary margin. Channels rotate and alternate with close controls; aggregate counters retain closing accepted bytes and pending close frames. Orderly close drains only already accepted bounded bytes with a 15-second deadline. The receiver delivers already received bounded bytes in order before reporting end of input, preserving refusal responses delivered in the same batch as close. Revocation, grant shrink, network-origin/generation changes, overflow and hostile inbound data terminate immediately and discard pending bytes.

Relay or Host reconnection drops old channels and creates fresh application connections/read baselines, without replaying business commands. When a new Host connection replaces the same enrollment, the old connection stops automatic retries and requires explicit trusted Desktop re-enabling. Relay owns bytes, liveness and backpressure only; Direct retains HTTP, static assets, exact Host/Origin and heartbeat.


A single Relay instance has a public origin, allowed Web origins, data volume and local administration. Server-local administration generates a 256-bit, ten-minute, one-use Host enrollment code; store only its hash. No public unauthenticated admin page. Host enrollment uses HTTPS once and registers a per-Host capability, kept in Host secure storage and never in QR codes.

Relay `allowedClientOrigins` continues to accept Web origins only. Optional `allowedAppOrigins` defaults to `[]`; native App deployments can explicitly set `["capacitor://localhost"]`. Each entry must be an exact `scheme://host` with a scheme other than `http`, `https`, `ws` or `wss`. Empty hosts, credentials, ports, paths (including a trailing slash), queries, fragments, whitespace and percent encoding are rejected. Both WebSocket upgrade and client registration require an Origin that exactly matches either list. Origin-less connections can only register as Hosts with valid enrollment credentials, never as Clients. A custom scheme can have `URL.origin` equal to `null`, so comparison uses the validated complete string. Native Apps can forge Origin; it grants no identity or execution authority. Noise pins still verify Host identity, and Host DeviceGrant still determines permissions.

Retain room = SHA-256(capability). Store allowed rooms, enrollment status and quotas. Hosts prove room ownership with capability; authenticated replacement connections may replace the same Host's old connection but never hijack another room. Clients know only an unenumerable room identifier, which is routing rather than execution authority. Noise pins and Host DeviceGrant decide authorization.

The outer service handles host/client registration, ready/open/data/close/error, and optional Host push/pushResult. Validate room/channel ownership for every frame. Offline Hosts yield unavailable, with no business command queue. Rate-limit unauthenticated handshakes and do not reveal existence of unrelated rooms.

SQLite stores enrollment metadata and consumed code hashes; connection routing is in memory and rebuilt by reconnection after normal restart. Backup restore instead disables restored Host registrations pending administrative re-enrollment/review, rather than treating stale revocation data as current authorization. Publish all TLS proxy, Relay and static-client source/build inputs. No Redis, cluster, SSO or billing is required. Logs contain time, random route identifiers, byte counts and error classes, never payloads, tokens, invitations, project names or prompts.

### Relay APNs forwarding

Push-capable Hosts include `X-Areal-Relay-Capabilities: push` in the WebSocket upgrade. Only these Hosts receive the optional ready `push` field and `pushResult`; legacy Hosts retain the original shape. A legacy Relay ignores the header and omits `push`, meaning unavailable. The header advertises decoder support and does not replace the registered Host capability.

Optional `apns` configuration contains `teamId`, `keyId`, `keyFile`, `bundleId`, and `maxPerHostPerMinute`. Team/key IDs contain 10 uppercase letters or digits; Bundle ID is a dot-separated identifier of at most 255 characters. Startup reads the P-256 `.p8` key from the configured path; administration commands do not read it. Without `apns`, Host ready declares `push:false` and no APNs connection opens. See the [Relay README](../../services/remote-relay/README.en.md) for configuration and read-only key mounts.

A Host that proves registration credentials and owns the current room can send `{"type":"push","token":"…","environment":"production","collapseId":"…","kind":"attention","count":1,"target":{"projectId":"…","threadId":"…","attentionRef":"…"}}`. Token is 64 through 200 hexadecimal characters; environment is `production` or `development`; collapseId is nonempty and at most 64 UTF-8 bytes; count is a positive safe integer. Kind is `attention`, `turnCompleted`, or `turnFailed`. Optional target contains only optional projectId, threadId, and attentionRef, each a nonempty opaque string of at most 256 UTF-8 bytes. Unknown fields, invalid parameters, and Client push close with `INVALID_FRAME`. Existing frame size, byte, and rate budgets apply before push routing.

Relay generates title `AReaL`. Attention text is `电脑上有 N 项需要你确认`; completed text is `你在手机上发起的会话已完成`; failed text is `你在手机上发起的会话没有完成`. The Host cannot supply alert text. APNs JSON contains only fixed `aps.alert`, the default sound, and optional top-level target. It contains no project names, conversation titles, prompts, or tool parameters. The configured bundleId becomes `apns-topic`; requests use `apns-push-type:alert`, priority 10, and collapse ID. Production uses `https://api.push.apple.com`; development uses `https://api.sandbox.push.apple.com`. TestFlight uses production. ES256 JWTs are cached for 50 minutes.

Each registered room defaults to 60 pushes per minute, configurable from 1 through 600. Host reconnection does not reset its current-minute count. At most 32 requests run concurrently, each with an absolute 10-second deadline. Relay neither queues nor retries. Saturation returns existing `error LIMIT_EXCEEDED`; disabled push returns `error UNAVAILABLE`. Healthy Host connections remain usable. APNs `410 Unregistered` returns `{"type":"pushResult","token":"…","status":"unregistered"}` to the current Host. Other delivery outcomes only enter sanitized logs. Logs contain only time, random route ID, kind, and status, without token, target, raw request, or APNs error body. Shutdown closes all APNs sessions.

Run `npm test` in `services/remote-relay` for temporary generated keys, local TLS HTTP/2, real WebSocket, and CLI-enrollment coverage. Actual APNs delivery and iOS lockscreen behavior require separate acceptance.

## C13. Browser trust and storage

Use explicitly selected Host/organization HTTPS origins, strict CSP/frame-ancestors/Referrer-Policy/permissions policy and no third-party runtime scripts. Verify browser Origin but do not treat it as a replacement for Noise identity. Hosts may omit Origin only with valid enrollment credentials; P0 browser clients must use an allowed origin.

Remember-device is explicit opt-in, storing identity in that origin's IndexedDB, not localStorage or URLs. Session-only mode keeps it in memory. This is not OS keychain protection: malicious same-origin code may access keys and content. Shared-device users should not opt in; cleared site data requires new pairing without automatic key import.

Service Worker caches only versioned static shell assets, not invitations, content, approvals, APIs or artifacts. Drafts default to the current browser session and never auto-send on reconnect. P0 requires neither push nor background permanence. Incompatible clients must update rather than weakening validation; avoid replacing their execution context midway through a user submission.

Remote DTOs are explicit presentation projections, not complete Core/Backend objects containing configuration. Optional read-only fields may be added without weakening authority or target binding.

Items retain id/type/phase and authorized content fragments, never opaque model internals. Oversized Items use preview/body-page references. session.history pages only history actually available from Core. Mark upstream limitations truncated/unavailable instead of claiming complete history or silently rebuilding a second store.

availableActions is the intersection of current DeviceGrant, implemented Core capabilities and object state. Advertise overview through the actual method directory and the atomic Task Run guard through `features.taskPauseRunGuard`, and guarded normal sends through `features.turnStartAdmissionGuard`. Missing capabilities produce explicit unavailable/upgrade states, not weaker calls. Builds without complete unopened-Thread overview cannot claim full P0.

Filtering automatically exposed configuration metadata is different from filtering authorized business content: messages, model output and effective tool arguments may contain user-supplied paths, code or secrets. Do not promise automatic elimination of all such content. Pairing must explain that the device can read authorized project conversations; logs and static builds must not collect those contents.

### Task pause

Source exposes `task.read` (observe) and `task.pause` (pauseTask). Reading `{taskId,runId?}` reuses bounded Task observation and returns current `revision/currentRunId`, original Run status, `workersSettled/settled` and `available`. Pause is unavailable before the first Run. The page reviews the original Task/Run and requires explicit confirmation to pause current work and future scheduling. Historical Runs never silently retarget the current Run. After a known accepted pause and a local Desktop resume of the same Run, a fresh available view and explicit confirmation are required to create a new commandId; pending/UNKNOWN still block new submission.

Pause accepts exactly `{taskId,expectedRunId,expectedRevision}` and requires Core's `taskPauseRunGuard` feature and `areal/task/pause` method. Native requestId is the existing journal operation UUID. Existing associations precede fresh admission checks; changing target or revision with the same commandId yields COMMAND_CONFLICT. Core atomically checks the last Run and revision; local callers omitting optional expectedRunId remain compatible.

Known native responses persist bounded `receipt:{taskId,runId,revision,paused:true}` before pending removal. There is no public Task receipt lookup: lost replies remain UNKNOWN. `command.read` never replays and may return independent `observedState` (source task.read, provesCommandAdmission false). Current observe and original pauseTask authorization remain required. Acceptance is only pause intent: settlement requires Task paused, the original Run paused or completed/failed/cancelled, and every worker settled. Paused is not terminal. Startup serverRestarted pause is observed without resume or replay. Remote offers no resume/cancel/schedule editing. Unavailable observations or missing pause/settlement fields render unknown, never unpaused or settled by inference. Source and DOM checks do not establish native T30/T31 acceptance.

## Current GUI reuse entry

The project/Session list uses `project.list` / `work.list`, not fixtures or GUI-opened history. Detail reuses GUI Messages and Composer without attachments. Model/permission configuration, goal create/pause/resume/clear, running follow-up queue and steering use real Core. Full goal editing and model catalog/credential settings remain on desktop.

Strict fields exclude paths, native method names, endpoints, and credentials. Task-owned Sessions reject these ordinary controls.
