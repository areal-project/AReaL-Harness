# Shared Host protocol

The protocol includes implemented interfaces and later target contracts. Host provides authenticated project management, stop receipts, subscriptions, legacy service migration, and the H2 source-import, legacy-secret retirement, submission-journal, fixed credential-slot, and Remote-state interfaces. `hello` advertises `projects`, `stopOperations`, `subscriptions`, `legacyMigration`, `guiImport`, `submissionJournal`, `credentialVault`, and `remoteState`. `updates` is unavailable. Ordinary GUI project connections, journals, credentials, and Remote state use Host. Complete quit behavior, connection-resource withdrawal, Remote execution migration, and service-manager delivery remain in progress. These definitions do not establish runtime or package acceptance. See the [implementation spec](../development/shared-host-spec.en.md), [ownership decision](../adr/0016-shared-host.en.md), and [per-project service contract](local-service.en.md).

## Transport and authentication

One Host owns the exclusive `host.lock` in the canonical service home. H1 resolves `AREAL_HARNESS_SERVICE_HOME`, then `AREAL_HARNESS_HOME`, then `~/.areal`. The home is mode 0700. Its descriptor publishes `version`, stable `hostId`, fresh boot `generation`, `socketPath`, `authFile`, `pid`, and executable version. PID is diagnostic, never authority for signaling or takeover. Socket paths reuse the existing short private `control.sock` derivation when the Unix path limit would be exceeded. Socket and auth file are mode 0600, owned by the same UID, and must not resolve through untrusted symlinks.

The local transport is a Unix domain socket with newline-delimited UTF-8 JSON, one request per frame. Maximum frame size is 1 MiB. Before dispatch, the server verifies peer UID against its UID and verifies the current auth file secret supplied in `hello.params.authToken`. Authentication failure closes the connection. Tokens never enter arguments, URLs, logs, status events, or Remote responses. `hello` is the only pre-authentication method. Reconnect requires a new handshake. The auth token rotates with the Host generation. The contract grants trusted local-user access, not isolation between processes of that user.


Normal stop removes the current generation’s `host/host.json` discovery descriptor and socket before releasing `host.lock`. Stable `host/identity.json` and original operation receipts remain.

## Envelope and common types

Requests use a dedicated envelope, separate from the existing service control protocol. Struct fields use camelCase; tagged enum values use their literal wire strings. Rust serde can represent requests as an envelope plus a method-tagged payload. Version 1 rejects unknown fields and invalid combinations. Optional fields are omitted rather than serialized as null unless stated below.

```json
{"version":1,"id":"rpc-1","method":"hello","params":{"protocolVersions":[1],"capabilities":["projects"],"authToken":"<read from private authFile>"}}
{"version":1,"id":"rpc-1","result":{"version":1,"hostId":"host-uuid","generation":"boot-uuid","capabilities":["projects","stopOperations"],"executableVersion":"build-id"}}
{"version":1,"id":"rpc-2","error":{"code":"projectAmbiguous","message":"Select a projectId","details":{"projectIds":["p1","p2"]}}}
```

`id` is a nonempty string that correlates one transport response. It is not an idempotency key. Mutations with effects require a separate `requestId`, a nonempty UUID persisted before effects. IDs cannot be reused for different method parameters. `expectedGeneration` always refers to the Host boot except `serviceGeneration`, which refers to a project's Core service. A stale Host boot returns `generationMismatch` before new effects. A receipt query remains possible after a new boot.

`ProjectRegistration` is durable, independent of live service descriptors. Its fields are `projectId`, canonical absolute `workspace`, canonical absolute `dataDir`, `source`, and `defaultBinding`. `source` is `{kind:"cli"}` or `{kind:"gui",profile,legacyProjectId}`. `defaultBinding` is a boolean selecting the default registration for its workspace. `projectId` is stable and opaque; a workspace path is not a project ID. A service descriptor retains the existing service-v1 fields and adds a Host owner only in the negotiated Host-aware contract.

Ordinary GUI registration requires a `profile` with exactly one committed source and a 24-character lowercase hexadecimal `legacyProjectId`. A new GUI project's `dataDir` must be `<coreHome>/<legacyProjectId>/state` within that source. Original import bindings retain their Store paths. A source alias cannot bind to another Host project. Host stores new aliases in existing project registration files without changing the original import manifest. Unknown and ambiguous sources return `sourceNotFound` and `sourceConflict`, respectively.

`ProjectStatus` contains `registration`, `state`, optional `service`, and optional `migration`. States are `stopped`, `starting`, `ready`, `stopping`, `unavailable`, or `legacyPending`. Migration records carry the original `serviceId`, `generation`, owner if present, source profile, and phase. `legacyPending` never carries a fabricated Host owner or grants a descriptor as Host-supervised. Clients can continue their existing legacy connections while migration waits.

The supervision owner is `{kind:"host",hostId,generation}`. It identifies the process that holds the service-host lifetime pipe. It is distinct from Remote Noise peer identity and device authorization. H1 and H2 retain runtime support for `{kind:"gui",appRunId,profile}` until GUI lifecycle migration completes; afterward it remains only for legacy identity detection. An old GUI cannot claim a new Host-owned service. Do not silently change strict service-v1 decoding for old clients. Negotiate Host-aware descriptors or return a capability error.

`LaunchInputs` contains required absolute `workspace`, `cwd`, and `configHome`, optional absolute `homedir`, `configPath`, and `deploymentPath`, a non-secret string map `environment`, `credentialNames:string[]`, and required `options:LocalArgs`. Outer fields use camelCase. `options` retains the snake_case fields of `core/local-service/src/spec.rs`; optional option values may be null. It carries model selection, permissions, sandbox and Runtime limits, workspace/data/configuration paths, `read_only_path`, `task_credential_command`, and `no_deployment_mcp`. CLI flags use hyphens. The CLI configures run-scoped MCP servers through Core after connection; Host launch inputs carry their credential names, not a `mcpConfigPath`. Skill roots are deployment entries rather than a separate `skillsPaths` field.

The client resolves paths and launch context before sending. The Host validates registration agreement, absolute paths, allowed environment names, and configuration before launch. Secrets travel in the separate `project.ensure.credentials` string map over the authenticated connection. `credentialNames` identifies required entries, including generated MCP secret references. Credential values are excluded from Debug output, logs, status, and durable operation parameters. H1 keeps them in project-private memory for the current Host generation. Missing required values return `credentialsRequired`. Secret-store persistence belongs to H2.

Before readiness, the Host snapshots the deployment JSON and its referenced Skill trees under `<home>/host/launch/<project-id-digest>/`, preserving nested resources and executable bits. It saves rewritten paths in `inputs.json`; deployment and Skill paths include content digests. Core preserves the explicit deployment root for the same Skill `id/revision`; discovery and refresh do not replace the snapshot. Other revisions follow existing discovery rules. A CLI can then remove its temporary deployment directory. Ordinary TOML files retain their original paths and existing configuration watch behavior. Configuration compatibility and safe-restart rules still apply. Each child uses the submitted cwd and environment; the Host never changes its process-wide cwd or environment. `configHome` preserves the client configuration, plugin, and Hook root independently of the Host registry home. The Host directs only `AREAL_HARNESS_SERVICE_HOME` to its registry.

`noAutoRestart` defaults to false. When true, ensure does not automatically restart an existing incompatible service. It remains an explicit activation and can start a stopped project. Automatic reconnect uses only `host.status`; applying configuration changes requires an explicit reopen or restart.

`projects.register` can update `defaultBinding` while project identity, workspace, data directory, and source stay unchanged. Ordinary registration changes only the Host project directory and can register a busy legacy service. `bindExisting` defaults to false. The compatibility command `areal service bind` sets it to true so Host verifies that the service is stopped and the Store belongs to the workspace before committing the legacy workspace mapping and default registration. Failures retain the original operation receipt.

This query never starts or resumes a stop operation.

Status events have `{version:1,method:"host.statusChanged",params:{subscriptionId,generation,sequence,status}}`, without an RPC `id`. Sequence increases strictly within a subscription. Every event is a full status snapshot. A generation change, sequence gap, or disconnect requires a fresh handshake and subscription; there is no durable event replay or automatic mutation retry.

A saved ready result does not establish current liveness; verify live identity before connecting. Receipts never include credential values.

## Scheduled project activation and preparation

`scheduledPreparation` means Host registers as the Core schedule host through a persistent authenticated connection and handles `areal/task/prepare`. Ordinary GUI tool and schedule connections may differ but must share the authenticated principal. Source conversations and execution anchors retain connection and directory-ownership validation. Core owns Tasks, Runs, preparation results, and triggering. Host does not advertise browser, computer, or JavaScript tools on behalf of an absent Main.

An online GUI publishes its current Browser/Computer bundles through Core `areal/task/tools/ready`. Run scheduling lifetime binds to Host; desktop tools bind to the actual GUI connection. GUI exit does not terminate plain-model execution, and old tool calls are not forwarded to a later connection. Registration is connection-scoped state, not a persistent Host task record.

The `scheduledActivation` capability identifies Host-owned scheduled project activation. GUI reads `scheduleActivationSuppressed:boolean` and optional `scheduleActivationError:string` from `host.status.projects`. Errors contain domain codes, not child-process stderr or secrets.

Host scans published task catalogs at startup and after registration, migration, or launch-input changes. It requests activation only when the catalog proves an enabled task exists and saved launch inputs are available. Core owns due-time triggering, misfire, and overlap admission. A `requiresCore` or inconclusive catalog produces an error rather than activation. Scans use two workers; failures back off from 5 to 300 seconds. Unknown admission is reconciled using the original request ID.

Explicit `project.stop` durably records scheduling suppression within its original lifecycle operation. Maintenance shutdown passes `suppressScheduling:false` to avoid adding suppression while retaining existing user intent; the field defaults to true. Host restart, status reads, and ordinary `project.ensure` do not clear it. Explicit resume uses `resumeScheduling:true` under the same project lock and receipt as activation. `host.stop` preserves global stop intent without independently suppressing every project. Legacy GUI lifecycle target suppression is imported once through source and project bindings; Host owns subsequent changes.

GUI `LaunchInputs.schedulePreparation` explicitly selects `managed` or `external`. `managed` supplies absolute `resourceStatePath`, `userManagedSkillsRoot`, and `projectManagedSkillsRoot` paths, plus `projectResourceScope` and `defaultProfile:{id,revision}`. Host materializes the deployment using existing user/project precedence and enabled preferences while retaining historical Skill revisions. Skill revisions use the same directory, name, and description digest as GUI; changing only the body or supporting files does not create a new revision, and the same `id/revision` retains its saved snapshot. `external` carries only an optional `defaultProfile` and uses the original deployment and Core defaults. CLI may omit this field; missing GUI preparation inputs do not permit inferring resource provenance.

Start preparation validates the current Task, Run, source thread, legacy exclusive-directory reservation, and workspace-author records. When the resource profile changes, Host saves the original restart request ID, MCP connections, and trusted plugin connections, checks `restartSafe`, then drains and performs a controlled restart. It reconciles original receipts and restores exact connections before registering the schedule host again. The old Core callback never receives a new-generation profile; `resume` retains frozen execution configuration. Subsequent GUI launches also merge Host-retained managed Skill revisions to preserve historical profile references.

## Global activity

`host.activity` includes every registered project, including projects started by CLI or TUI that GUI has not connected to. `ProjectActivity` is one of these results:

- `{projectId,state:"observed",activeTasks,activeTurns,activeGoals,pendingQueueItems,idleAllowed}`. Counts come from authenticated Core `areal/server/status`. `idleAllowed` uses Core `lifecycle.ifIdle.allowed`, not the task count alone.
- `{projectId,state:"unavailable"}`. Migration, startup, identity mismatch, unverifiable locks or cleanup receipts, and failed status reads remain unavailable rather than reporting zero.

A project that has never started reports idle with zero counts only when it has no service record, uncertain lifetime, or held lock. A stopped project also requires cleanup evidence for its original generation and released service and Store locks. Queries create no lock files, Stores, or service records and do not clear stop intent.

`complete` is true only when every project is observed. `totalActiveTasks` sums only observed `activeTasks`, without adding turns, goals, or queued items. An incomplete result reports only the known task count. Projects are observed individually rather than in an atomic cross-project snapshot. This result cannot authorize a later stop. `host.stop` still checks its conditions when executed.

## Stop receipts and partial settlement

`StopReceipt` has `version:1`, `requestId`, `projectId`, `serviceId`, `serviceGeneration`, `strategy`, `state`, and optional `message` and `lifecycle`. Its states preserve the existing service stop semantics: `acceptedPending`, `blocked`, `admissionUnknown`, `settlementIncomplete`, and `completed`.

`HostStopReceipt` has `version:1`, `requestId`, `hostId`, `generation`, `strategy`, `state`, and `projects:StopTarget[]`. `StopTarget` contains `projectId`, `serviceId`, `serviceGeneration`, child `requestId`, `dispatch:"notStarted"|"started"`, and optional `receipt:StopReceipt`. `notStarted` means only that the Host has not dispatched the request; it never claims Core admission. The Host persists `started` before sending. After a crash, a missing downstream receipt requires UNKNOWN reconciliation, not an assumption that nothing was sent. Aggregate state is `acceptedPending`, `blocked`, `partial`, `admissionUnknown`, `settlementIncomplete`, or `completed`. `partial` means at least one target completed and at least one did not; every target retains its precise state. `completed` requires all targets completed and the Host exit handoff durably recorded. A known busy rejection is `blocked`, never UNKNOWN. `admissionUnknown` means that acceptance cannot yet be determined. UNKNOWN is queried under the original ID, never replayed or converted into a new automatic request.

The Host saves and fsyncs the aggregate target set and each suboperation identity before draining. It records stop intent to block new activation during stop. Core drain still performs the authoritative idle check, cancellation, and settlement. The Host freezes project admission while taking the target set; it does not claim atomic drain across Cores. A project may settle before another becomes blocked. The Host stays available to report partial results. A rejected idle stop can clear its activation fence only after every accepted target has reconciled. A successful explicit Host stop keeps durable stop intent so the service manager does not relaunch it. A later explicit local start clears that intent.

Completion requires the existing Runtime cleanup proof and service/Store lock release, or a verified successor generation under those locks. PID exit and socket disappearance are insufficient. Receipts live outside generation cleanup in the private home. New operations may follow a known rejection or settled incomplete operation with explicit fresh intent; they cannot resolve an unknown previous admission by resending it.

`UpdateReceipt` has `version:1`, `requestId`, `hostId`, `generation`, `targetVersion`, `action`, `state`, optional `stopRequestId`, and optional `message`. States are `prepared`, `acceptedPending`, `blocked`, `partial`, `admissionUnknown`, `settlementIncomplete`, or `completed`. Apply uses the same per-project stop receipts and proof requirements. The new Host retains stable `hostId`, changes `generation`, and exposes the original update receipt. Running Turns never switch binaries in place.

## Registration and migration

CLI workspace lookup uses an explicit `projectId` when supplied. Otherwise it resolves the canonical workspace and explicit `dataDir`, then an unambiguous default binding. Multiple candidates without one default return `projectAmbiguous` with candidate IDs. Never select by display name, directory order, or first registry entry. Registration preserves separate projects for the same workspace with different data directories. The same canonical data directory cannot acquire a second writer. Equivalent repeated imports use the saved source mapping; incompatible bindings return `dataDirConflict`.

GUI import persists `(profile,legacyProjectId) -> projectId` mappings with worktree bindings, authorization scopes, receipt locators, and source/default bindings. Existing GUI project IDs are retained when conflict-free. On collision, a new ID is allocated and the full mapping is committed before activation. Remote grants and old request locators are resolved using that mapping; authorization cannot broaden through ID reuse.

The GUI-root `<projectId>-pending.json` and `<projectId>-outcomes.json` submission journal are outside Core Store. Preserve native Core request IDs, semantic digests, admitted outcomes, UNKNOWN locators, original service identities, and all remote command correlations. Stop admission in the old writer, flush and snapshot its journal, import under the Host lock, and fsync a migration receipt binding source identity and journal digest. Switch the writer only after that receipt is durable; then reopen admission through the new owner. Recovery resumes from the receipt phase and never creates a second writer. Core Stores and data directories remain in place. The old accepted response-lost case must resolve against its original receipt after upgrade with exactly one side effect.

A legacy ownerless service remains `legacyPending` while active. Existing connections continue. Migration performs an idle drain or an explicitly authorized cancel, queries durable stop receipts, verifies cleanup and locks, and starts a fresh Host-owned generation. Editing registry metadata cannot transfer a pipe or process ownership. Legacy GUI-owned services also require their old lifecycle owner to drain and settle before replacement.

Only one legacy GUI profile with a compatible Remote identity can migrate automatically. The stable Host supervision ID and Remote Noise key are independent. Preserve the profile's Noise key, paired-device pins, grants, revocations, and journal association. A second profile with a distinct Noise identity returns `migrationConflict`, retains its original state, and requires an explicit identity-selection or separate-home decision. Never overwrite, combine, or silently regenerate Noise identities. Credential migration covers API keys, OAuth refresh/access tokens, and provider subscription transport sessions. A successful secret-store write receipt precedes retirement of the old encrypted value.

Import first saves a fixed manifest and original-byte backups, then secrets and receipts, and verifies old service cleanup evidence and locks. Host installs non-JSON source startup and per-project journal sentinels before publishing a committed marker. Projects reserved by unpublished imports cannot activate or access journals, including reused CLI registrations. Import preserves original Store and scratch paths and `(profile,legacyProjectId)` aliases. Original registries and non-secret backups remain. The original import receipt's `retirement:"pending"` records the state at import commit. Query the separate retirement interface for subsequent results.

`gui.source` queries the complete canonical `GuiSource` and returns only committed sources. If a profile has multiple committed sources, it returns `sourceConflict` rather than mixing newly registered aliases. It does not acquire a source guard, start an import, read credentials, or create directories. `bindings` retains imported aliases for reused CLI projects and adds new GUI registrations for this profile. New bindings use scratch path `<coreHome>/<legacyProjectId>/scratch`. Host rebuilds the result from original import receipts and current project registrations after restart.

GUI initialization and Host reconnection attach read-only observers to ready foreign projects and load their conversation catalogs. Discovery does not start stopped Cores or overwrite CLI configuration. Rediscovery of the same generation preserves an in-flight observer. History configuration decoding accepts Core's `automaticSessionName` field without expanding the fields accepted by GUI creation commands.

`credentials` contains non-secret migration metadata only. `references` combines imported provider references with later vault slots owned by the source, including revoked references; `vault.read` remains authoritative for values. `migratedConfigPaths` retains original configuration migration markers. `legacyProviders` removes ciphertext and adds `apiKeyEnv` only for entries with secrets in the original providers manifest. Reads verify original backup digests or retirement-plan derivative digests and never read the fenced credential source file.

### Legacy secret retirement

Host stores a separate plan and receipt in `retirement.json`. It does not alter the original manifest, credential-import receipts, or committed marker. The Electron adapter holds the original Desktop singleton and replaces source files and their backups according to the plan. Retirement removes only manifest-covered provider ciphertext, subscription-account ciphertext, Remote ciphertext, and the plaintext subscription-transport token. Non-secret configuration and unknown fields remain. Duplicate JSON keys or unsupported source shapes block retirement and retain unprocessed files. The provider startup sentinel, journal sentinels, original journal backups, Store, and `cloud.json` are outside the replacement list.

Progress is `{requestId,migrationId,planId,state,next}`, with `state` equal to `applying` or `completed`. Only prepare returns a next target `{site,relativeName,backupId,beforeDigest,afterDigest,byteLength}`. `site` is `source` or `backup`. Status, confirm, and operation receipts always return `next:null` and never return file contents. Host saves derivative content in the fixed private file `host/imports/<migrationId>/retirement/<planId>/<backupId>.bytes`, so large files do not exceed the control-frame limit. The adapter verifies file ownership, permissions, type, length, and digest. It replaces the target through a temporary file, file fsync, rename, and directory fsync. Backup paths remain `host/imports/<migrationId>/backups/<backupId>.bytes`.

Prepare requires a committed import, a valid source guard, and completed receipts with readable original vault entries for every manifest secret. Missing or locked entries block further replacements. Retirement never seeds old values from the current credential revision, so a later revocation cannot restore an old account. Call prepare before each file replacement and confirm afterward. Host independently reads the targets and accepts only the original or planned derivative digest. It also verifies the original startup and journal sentinels before completion.

Recovery reads the original plan and derivative files without parsing retired ciphertext again. If rename succeeds before confirm, Host records progress from the derivative digest. After disconnect, attach the source again and use the original requestId returned by status. A different requestId cannot recreate the same plan. Status and offline operation queries neither access secure storage nor advance retirement. Original manifest digests still describe historical bytes. A retired backup is a derivative recorded in the separate plan. Old backups outside the current committed manifest are outside this plan.

Without an imported or newly created Remote configuration, remote.read returns {revision:0,sourceId:null,config:null} without accessing secure storage. A published source can create its first configuration with expectedRevision:0. Once a Noise identity exists, replacements cannot change it. A pending first write also reserves its source against another import. Grant scopes use original source aliases, new GUI registrations, and stable local aliases for other Host projects. GUI Gateway uses a separate lease connection; losing it closes the endpoints, including a late Direct listener.

### Rust Gateway handoff

The native Gateway reuses the same Noise identity, grants, Remote revision, and Host journal. The old executor closes its endpoints, drains accepted work, and releases its lease before handoff. The existing Host state owner atomically checks the source, revision, and absence of a lease and saves the original receipt. After durable handoff, `remote.acquire` and generic `remote.replace` return `nativeGatewayOwned`; settings writes go through the native owner. Native startup failure reports unavailability without restoring the JS executor. Clients select the native GUI facade through capability `remoteGatewayV1`, never a version-number inference.

| Method | Parameters | Result |
| --- | --- | --- |
| `remote.gateway.handoff` | `{requestId,expectedGeneration,sourceId,expectedRevision,assetRoot?}` | A `completed` handoff receipt containing the original `hostId`, `generation`, `sourceId`, and `revision`. |
| `remote.gateway.status` | `{}` | Native-owner connection and availability state without secrets. |
| `remote.gateway.state` | `{sourceId}` | The existing GUI `RemoteStatus` projection, without private keys, Relay capability, or push tokens. |
| `remote.gateway.subscribe` | `{sourceId}` | `{subscriptionId,generation,sequence:0,state:RemoteStatus}`; subscribes to source state on the same authenticated connection. |
| `remote.gateway.control` | `{requestId,expectedGeneration,sourceId,request,assetRoot?}` | The existing local `RemoteRequest` and response shapes; GUI Main generates pairing QR images. |
| `remote.gateway.replace` | `{requestId,expectedGeneration,expectedRevision,sourceId,config}` | The existing durable `remote.replace` receipt and CAS semantics. |

`remote.gateway.subscribe` requires `remoteGatewayV1`. The initial snapshot and subscription are established on one connection. Subsequent `remote.gateway.stateChanged` notifications use `{version:1,method,params:{subscriptionId,generation,sequence,state}}` and report actual state changes. Clients replace the projection after checking the original subscription ID, Host generation, and consecutive sequence. A gap or identity change closes the original connection and requires a fresh snapshot. Disconnecting revokes the subscription; the old view cannot consume events from a new connection. Pairing requests and connection state update the GUI through this channel. Notifications contain no secrets.

The trusted local producer supplies `assetRoot`, pointing to the source Renderer build or packaged `areal-gui` directory. It is neither a phone request field nor a new user setting. Direct serves only the Remote closure described by `remote-assets.json` with matching checksums, retaining the existing Host, Origin, CSP, worker, and cache rules. Migration resolves the selected source's original GUI aliases; other Host projects use stable Host aliases. Reusing an old ID in another profile cannot broaden authorization.

Control requests reuse the existing Remote receipt directory and bind the original settings request through `controlDigest`. It uses the existing Host-generation auth token as an HMAC key, separates method, source, and requestId domains, and binds canonical request bytes. The auth key stays in Host and authenticated local Main clients, outside Renderer and without another key store. Temporary pairing receipts have `ephemeral:true` and the original Host identity and exclude invitation secrets; lookup never recreates an invitation after restart, consumption, or cancellation. GUI persists unresolved request references and queries only the original ID. `null` never permits replay. The native `requestId` for Remote `interaction.respond` is the interaction domain identifier; its journal UUID neither replaces that ID nor creates a separate `areal/request/read` admission proof. An uncertain response retains journal UNKNOWN. Current interaction state remains a separate observation and cannot establish this command's admission. Other submission methods with native request receipts still query their original IDs.

`enable` retains the original Relay origin, one-time `code`, and `confirmed` inputs. Invalid origins, invalid codes, or missing required enrollment data return `invalid-origin`, `invalid-code`, or `enrollment-required` before admission. Before the single HTTPS `/enroll` POST, Host durably records the original `remote.gateway.control` as `outcomeUnknown`, binding source, Host identity, generation, previous revision, and HMAC without storing the code. Client retries and redirects are disabled. Only authoritative 403/429 enrollment denials settle the original receipt as `blocked`; disconnects, timeouts, unexpected statuses, or unparseable success responses remain UNKNOWN. After definite success, only the current in-memory continuation can move the same original ID into the existing Remote CAS/Vault commit chain. An UNKNOWN lookup never starts another enrollment. GUI queries the original ID to settle a confirmed rejection and retains the original reference for an unknown result.

### Journal and operation receipts

A journal snapshot is `{version:1,pending:object[],outcomes:object}` and preserves unknown fields within entries. Fixed file slots carry snapshots larger than 1 MiB; control frames retain the transport limit. Prepare and commit CAS conflicts use `result.state:"blocked"` and `result.error.code:"revisionConflict"`, not a top-level RPC error. Only that explicit conflict permits rereading and recomputing a change. Disconnect, timeout, or an unresolved commit permits only querying the original requestId, not rerunning the mutation closure or dispatching to Core again.

On the first `journal.read` or `journal.prepare` for a published ordinary project, Host creates an empty revision-0 snapshot only if the record is absent. This includes projects first registered by CLI. Existing imported data, revisions, and operation receipts remain. Corrupt records are never replaced with empty snapshots. Unknown projects and projects reserved by uncommitted imports are rejected before initialization. Offline receipt queries never initialize journals.

Both online `host.operation` and offline `areal host operation <request-id>` query lifecycle, source-import, secret-write, secret-retirement, journal, vault, and Remote replacement receipts. Retirement receipts use method `gui.retirementPrepare` and state `acceptedPending` until completion. Offline queries do not start Host, access Keychain, or write or repair state files. A missing home does not create directories.

`ClientStateReceipt` is the union of these H2 domain receipts. Each contains the original `requestId`, `method`, and `state`, plus its interface-specific result fields. `gui.import` and `gui.importSecret` wrap their domain result in `result`. Receipts do not contain secret values.

Offline queries prefer durable commit evidence, including final receipts embedded in atomic journal, vault-slot, and Remote-state records. Existing final evidence can return completed even when the separate receipt file is missing or still pending. An operation that stored a secret entry but did not commit its state remains acceptedPending for the online owner to reconcile. An uncommitted journal slot remains prepared; offline lookup does not expire it. `null` always means missing evidence, not proof of non-admission or permission to replay. Online Remote recovery still reconciles the original stable vault entry and revision without a new requestId.

## Fixed credential slots

`credentialVault` serves published GUI sources only. Slots are `{kind:"providerCredential",sourceId,reference}`, `{kind:"subscriptionAccount",sourceId,providerId}`, or `{kind:"subscriptionTransport",sourceId}`. `reference` retains the original `AREAL_CREDENTIAL_*` name. Identical references from different sources remain separate. Remote identity still belongs to `remote.read/replace`; vault access to `remoteIdentity` returns `remoteStateRequired`.

| Method          | Request params                                               | result                                                                                                                                            |
| --------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vault.read`    | `{slot}`                                                     | `{revision,value}`. An unset slot in a published source returns revision 0 and null.                                                              |
| `vault.replace` | `{requestId,expectedGeneration,slot,expectedRevision,value}` | The original write receipt, containing `requestId`, `method`, `slot`, `previousRevision`, `entryId`, and `state`, plus `revision` when completed. |

Provider values are nonempty strings or null; subscription values are complete record objects or null. Null is a durable revocation and increments the revision. Original import receipts initialize absent slots only; they never overwrite later replacements or revocations. A stale expectedRevision returns a top-level `revisionConflict` error before writing. Clients must not repeat a remote OAuth refresh.

A write first saves a non-secret acceptedPending receipt, then stores and verifies a stable vault entry, and finally atomically commits the slot version and completed receipt. Recovery reconciles the original entry and revision. Locked system storage still returns `storageLocked`, not evidence of absence. A confirmed missing entry can settle as `blocked/storageWriteNotApplied`. Operation receipts contain neither secret values nor ordinary hashes of secrets. A lost response permits querying the original requestId only.

On each activation of an imported project or a new GUI project from a committed source, Host reads fixed provider references from that source's current vault. Revocation removes the old Host cache value; stale client values cannot override the vault. Missing or ambiguous GUI sources fail without falling back to stale client values. Ordinary CLI projects and non-fixed references retain the existing launch-input credential behavior. GUI settings and subscription consumers read and write through these slots. The reserved `AREAL_CREDENTIAL_areal_openai` reference resolves to the source subscriptionTransport token. Other environment credentials travel separately in `project.ensure.credentials`, not the saved launch environment. Revocation does not automatically remove credentials already injected into a running Core.

## Native subscription source owner

`subscriptionOwnerV1` isolates accounts, OAuth, refresh, and local streaming transport by published GUI source. Core remains authoritative for model execution; GUI consumes safe state and login URLs. `accountEpoch` identifies account lifetime independently of vault revision. Normal token rotation or saving a new inactive account does not cancel the active account's stream. Selection and logout revoke the old epoch; late refresh or callback results cannot restore the old account.

| Method | Parameters | Result |
| --- | --- | --- |
| `subscription.read` | `{sourceId}` | Source owner, safe account state, directory, model catalog, and transport endpoint, without OAuth or loopback Bearer tokens. |
| `subscription.handoff` | `{requestId,expectedGeneration,sourceId,migrationId,expectedAccountRevision,expectedTransportRevision,network}` | The original handoff receipt. Durable takeover follows verification of the exact committed and retired source, both slot revisions, and binding the original port. |
| `subscription.command` | `{requestId,expectedGeneration,sourceId,expectedAccountEpoch,action}` | The original command receipt; query the original ID for background completion. |

`subscription.read.owner` is `legacy` or `nativeV1`, with `sourceId`, `generation`, `accountRevision`, and `transportRevision` always present. Native state adds `accountEpoch`, existing account status, `accounts`, `catalog`, and `endpoint`. Login state `{loginId,authUrl}` lets the local UI open authorization. `applied` records `{accountEpoch,serviceId,generation,connectionId,providerRevision}` by Host projectId. Source readiness does not establish that every Core has applied it.

Actions are `begin` (`target:{kind:"current"|"newAccount"|"saved",accountId?}`), `cancel` (`loginId`), `select` (`accountId`), `logout`, `forget`, `refreshCatalog` (`force?`), `probe` (`model`), and `configureNetwork` (`network,expectedTransportRevision`). A new authorization can be saved inactive while Core is busy, preserving the original stream. Selection and logout retain live idle checks against each original Core without promising an atomic reservation across Cores.

`network` is `{proxies,extraCaPem,proxyUnavailable}`. `proxies` accepts only `HTTP_PROXY`, `http_proxy`, `HTTPS_PROXY`, `https_proxy`, `ALL_PROXY`, `all_proxy`, `NO_PROXY`, `no_proxy`, and `AREAL_CHATGPT_SYSTEM_PROXY`. These source network inputs reside only in the encrypted transport slot, outside status and ordinary operation logs. Subscription intents use the same domain-separated HMAC with the current Host auth key; operation files do not retain ordinary SHA digests of inputs containing secrets such as proxy passwords. OAuth and catalog calls have request deadlines. Inference SSE follows Core, source, and account-epoch cancellation, without a short global deadline covering the whole inference.

Before handoff, drain old-source active streams, refresh, and original slot writes. Host retains the original token and port for existing Core transport references. Host resolves new Cores' reserved credential references from the exact source; GUI does not return stale secrets. After takeover, generic `vault.replace` returns `subscriptionOwnerRequired` for the source account and transport slots, but accepted original receipts are returned before the fence. Native private CAS retains the existing vault revision, immutable entry, and request ID without another credential ledger.

Handoff and command receipts have method `subscription.handoff` or `subscription.command` and state `acceptedPending`, `completed`, or `blocked`. Terminal receipts carry `result` or `error:{code,message}`. A lost response permits only an original `host.operation` lookup, never another OAuth exchange, inference POST, or uncertain Core submission.

Restart recovery confirms a handoff when its original marker request ID matches and the source restores successfully. Before accepting handoff, Host durably associates `migrationId`, the original transport CAS request ID, and the original port CAS request ID. Without a marker, Host continues only the same original handoff's local steps after verifying the original Vault receipts, exact slot revisions and immutable entries, old-source retirement, and binding the original port. An initially zero port also requires the original port-write chain; recovery never repeats OAuth exchange or inference POST. Older records without sufficient evidence retain an unknown outcome and an unavailable, read-only source projection.

A command whose background task was lost becomes `blocked/outcomeUnknown`, preserving its original `acceptedPending` receipt, identity, and recovery evidence. This means its historical effect is unknown, not that it did not execute. GUI retains the original request and shows the uncertainty while connection and account reads remain available. Current state cannot establish the old action's admission or effect. Unresolved requests prevent automatic handoff, network configuration, or new source commands. Refresh queries the original operations again; proven terminal outcomes can release their corresponding restrictions. That refresh reads source state only, without catalog refresh, network configuration, or old-action submission.

## Exit and service-manager contract

`areal host run` holds `host.lock` for its entire lifetime. A losing concurrent process exits 0 on macOS and 73 on Linux; systemd uses `RestartPreventExitStatus=73`. Normal requested stop exits 0. Unexpected failure exits nonzero and consumes the bounded restart budget. macOS uses `KeepAlive.SuccessfulExit=false`. Durable explicit stop intent suppresses automatic restart, but a fresh explicit local start may clear it. At most five automatic restarts occur within five minutes, with delays of 1, 2, 4, 8, and 16 seconds; exhaustion records `crashLoopStopped`.

Host crash closes its owned lifetime pipes. The existing service-host, launcher, Core, and Runtime cleanup chain remains authoritative. A successor waits for cleanup proofs and old locks. These guarantees apply only to Host-owned generations, not `legacyPending` instances. Logout, shutdown, and sleep do not promise reachability. This contract does not establish package, launchd, systemd, or real-device acceptance without their separate evidence.
