# Desktop API: areal.core.v1

This contract extends [Core WebSocket](core.en.md), separately from Runtime JSONL and [CLI stdio](claude-cli.en.md). Full requests, responses, notifications and persistent types are in [areal-core-v1.json](../../schemas/areal-core-v1.json). Typed AReaL requests reject unknown fields; Codex compatibility methods retain their pinned wire contracts.

`make desktop-schemas` exports package and hook DTOs from their Rust types and includes the [pinned Codex 0.162.1 plugin contracts](../../upstream/schemas/codex-plugins-0.162.1/methods.json), whose [provenance](../../upstream/schemas/codex-plugins-0.162.1/provenance.json) identifies the source of each contract. Generation requires paired request/response schemas and every advertised notification. The example client additionally verifies coverage against the running Core's capabilities. Each method and named type schema can be extracted and compiled independently. The generator retains recursive definitions and binds local `$ref` pointers to their original scope within that export. Generation rejects unresolved local references.

Web/PWA Remote uses a separate restricted [areal.remote.v2 contract](remote-control.en.md), mediated by the desktop background adapter with current device authorization checks. It exposes neither a generic entry to this API nor local Bearer tokens; Remote design and implemented scope are identified separately.

Thread snapshots and Item notifications accept the optional `agentMessage.phase` field; see [Core message phases](core.en.md#agent-message-phase) for lifecycle, examples and legacy compatibility. This additive response field keeps `areal.core.v1` unchanged.

## Desktop host task catalog compatibility

The desktop backend supports `tasks.preview` and `tasks.observe` with `requestId` and `viewEpoch` when `service.commandContract` is `areal.desktop-commands.v3`. `preview` reads published snapshots only. `observe` reads live catalogs for connected owners and snapshots for cold owners without starting project Core services. An older backend may stay connected and continue existing work, but Main rejects these queries with `SERVICE_COMMAND_UNSUPPORTED` when the command contract is absent or different. It does not substitute `list`, which may start a project.

When the command contract is incompatible, the task manager retains loaded tasks and directs users to safely update through Settings > Background service. It neither retries each project nor claims that no tasks exist. Updating remains explicit and uses the existing lifecycle resource inspection and settlement flow; running work is not stopped automatically. Deployment identity includes the `desktop-contract` entry and protocol file contents in its split directory, so split protocol changes also mark a retained backend for update.

## Desktop host worktree contract

The Desktop host `connect` command accepts an optional `threadId` hint to prioritize selected-conversation observation. The service snapshot advertises `selectedThreadObservation=true`. Main omits the hint for older v3 backends that do not advertise support and retains the existing restoration request. It does not change project execution readiness. Navigation summaries refresh in the background. Desktop snapshots may include a public `subscription` status with the existing `chatgpt.status` account and model fields, plus `availability: "checking" | "available" | "unavailable"` and `refreshing`. Model catalog entries may also carry `availability`. Discovery does not imply invalidity, and the cache does not replace Core submission validation. Older consumers may ignore the added response fields. Older backends continue to receive the original v3 requests. This adds no Rust RPC.

This section describes the authenticated desktop host `command` contract in `clients/gui`. It does not add a Rust `areal.core.v1` RPC. The host uses existing Core methods for each execution directory. Core retains ownership of threads and execution history. Shared desktop types and validation are in `clients/gui/packages/workbench/client/desktop-contract.cjs`.

`create` accepts the logical `projectId`, stable `requestId`, existing model and configuration fields, and optional `worktree: {sourceRoot?,ref?,worktreeRoot?,branch?,branchPrefix?,mode?,environmentId?,environmentRevision?}`. `mode` is `source` or `worktree`. `environmentRevision` is a nonnegative integer. Other fields are strings. Ordinary creation uses the current project directory, branch, and Core. Only `mode: "worktree"` creates a separate checkout. Omitting `worktree` or `mode`, or selecting `source`, keeps that directory even when other conversations exist. Success returns `{threadId,requestId}` without changing the logical project. Isolated creation pins the source SHA, confirms an independent Core/Runtime and empty-thread binding, and completes selected setup before readiness.

`workspace` provides these host operations through the existing narrow command boundary. Project ownership is validated.

| operation | Additional request fields | Result and behavior |
|---|---|---|
| `worktreeOptions` | `sourceRoot?` | Returns same-repository sources, branches, settings, defaultRoot, project environments, and environmentRevision. |
| `worktreeSettings` | `worktreeRoot,branchPrefix,fetchBeforeCreate?,autoCleanup?,keepCount?,expectedRevision?` | Saves global future-creation policy without moving existing directories. An empty root uses `.areal/worktrees` under user home, grouped by project. |
| `worktreeList` | None | Returns `{settings,defaultRoot,revision,projects,worktrees}` from host registrations without starting every Core. |
| `worktreeEnvironmentSave` | `environment,expectedRevision` | Saves an environment for the logical project with revision conflict detection. |
| `worktreeEnvironmentDelete` | `environmentId,expectedRevision` | Deletes configuration without changing frozen creation environments. |
| `worktreeRead` | `requestId` | Reads the original creation and binding record, or `missing`. It does not recreate a checkout or rerun unknown scripts. |
| `worktreeCancel` | `requestId` | Requests cancellation and returns the current record. `cancelling` does not confirm termination. Only `cancelled` allows a new explicit source request. |
| `worktreeAction` | `requestId,worktreeRequestId,actionId` | Runs a frozen environment action in its managed checkout with an independent receipt and bounded output. |
| `worktreeDelete` | `requestId,worktreeRequestId` | Checks the managed checkout, cleanup, and service-stop receipts before non-force removal. Branches, history, and ownership tombstones remain. Failure or uncertainty preserves the directory. |
| `worktreeCreate` | `requestId,source?,sourceRoot?,ref?,worktreeRoot?,branch?,branchPrefix?` | Retained explicit checkout entry using the original Git lifecycle. The `working-tree` source is rejected. |
| `worktreeOpen` | `requestId` | Recovers or completes binding for a confirmed checkout and returns the original logical project and thread. |

An environment is `{id,name,setup,cleanup,actions}`. Setup, cleanup, and each action's script use `{default,macos?,linux?}`. A nonempty platform script replaces Default. Actions are `{id,name,script}` entries. Creation freezes the environment. Later edits do not affect existing checkouts. Scripts use existing Core managed processes at the actual project execution root and receive `AREAL_WORKTREE_PATH`, `AREAL_PROJECT_PATH`, and `AREAL_WORKTREE_BRANCH`.

Host states include `creating`, `created`, `binding`, `settingUp`, `cancelled`, `ready`, `failed`, and `unknown`. Cancellation retains the original stage with `intent: "cancel"`; the UI shows cancelling. Binding an empty thread does not permit ordinary execution before environment readiness. Project snapshots expose the journal through `worktreeOperations`. Thread `worktree`, `worktreeEvents`, and `executionProjectId` describe the actual checkout and host. Events are not Core messages. Changed parameters under one request identity are rejected. Unknown writes are not replayed. Partial success never falls back to the source. Removal preserves ownership so reconnect cannot create an empty replacement or redirect execution.

Ordinary conversations and Forks can share the current directory without a permanent exclusive Session author. Desktop still verifies thread identity, read-only Side restrictions, and scheduled tasks in the same checkout. Reserved schedule directories admit only the original task family. Legacy ordinary-author records remain but cannot trigger automatic worktrees or block a second ordinary conversation.

Subsequent requests retain the logical `projectId`. The host resolves execution ownership from `threadId`, `sourceThreadId`, `parentThreadId`, task ownership, or the original request receipt. One request cannot mix targets from different execution hosts. A durable task index records the actual host and optional Core thread anchor. Without an indexed owner, the host queries hosts within the same logical project. Offline, timed-out, or conflicting results cannot be treated as task absence or trigger a source-checkout fallback. The host injects the trusted thread anchor and rejects a conflicting caller-supplied `threadId`. Unconfirmed ownership returns `TASK_WORKSPACE_UNAVAILABLE`. `taskRunNow`, `taskResumeRun`, `taskReply`, and `taskResume` also refuse dispatch without an anchor.

Desktop `manage.taskCreate` in `scheduled` mode and `manage.taskDraftConfirm` use dedicated schedule admission. A task family must reserve an automatically allocated projectless directory that was not pre-existing, using the same directory-author registry. Reservation precedes execution-anchor and task creation or verification, followed by original-receipt binding. Read-only planning and autosave confirmation remain available. The host checks Task, run, anchor, and actual cwd in `areal/task/prepare` callbacks for both `start` and `resume` before allowing execution. Schedules created by Core tools in ordinary conversations use derived shared admission: after verifying the desktop owner, source Thread, execution anchor, and matching actual cwd, they may execute in the current project or a selected Worktree. One source may have multiple schedules. This does not create or migrate exclusive reservations. Legacy arrangements with neither a verifiable ordinary source nor an original reservation cannot activate; they return `SCHEDULE_WORKSPACE_REQUIRED` or the applicable author error. Pause and cancellation remain available. Foreground/background operations with trusted anchors retain ordinary admission. Native Core scheduling and already prepared legacy autonomous work do not gain a retroactive guarantee. Every directory-author admission reads the authoritative paginated Task catalog for the same checkout. An uncancelled legacy exclusive scheduled task retains future execution eligibility even while paused or sleeping; only its original reservation token, bound Task, and anchor match that family. Ordinary-source schedules must pass current Core identity checks before sharing a directory with other conversations. Failed or incomplete reads prevent dispatch.

`ScheduleAdmission.authorForSession` verifies the current task family only for `respond` and `continue`, requiring a unique active Run, exact goal/Turn/cwd, registered workers, and a bounded parent chain. `respond` also requires an exact unexpired pending interaction: thread, Turn, requestId, and answer kind. Foreign Sessions, stale requests, cancelled Runs, and paused Runs do not map. Sends, edits, and ordinary manage operations cannot use the schedule-family author mapping. Native Task Agent research and tool restrictions remain unchanged and do not allow recursive delegation.

| Run or interaction state | Desktop behavior |
|---|---|
| Current active Run waiting for a valid question or approval | `respond` verifies the exact interaction; Core automatically continues. |
| Goal-owned scheduled thread | Ordinary Core Continue remains unsupported; host mapping does not expand the Core contract. |
| Paused or blocked Run | Use `taskResumeRun` to retain the Run and thread with a fresh Turn. |
| Host disconnect while pending | Run pauses as hostUnavailable; old requestId is rejected. Answer the new question after resume. |
| Cancelled, completed, wrong Session/anchor, or expired interaction | Reject without consuming another valid pending interaction. |

From the repository root, `node clients/gui/scripts/worktree-schedule-interactions.mjs` verifies the real Core protocol with a deterministic local model and no Electron. Its manifest separates protocol validation from Runtime payload results. A protocol pass cannot establish verified writes when native file execution did not succeed. See the [worktree guide](../guides/worktrees.en.md) for directory and branch rules, old snapshot compatibility, concurrency, and isolation limits.

## Authentication and connection

Product servers listen on loopback and authenticate WebSocket/Blob requests. Trusted Main reads its Bearer token from authFile in ready metadata; Renderer receives neither that file nor model credentials. Built-in Web uses a separate HttpOnly, SameSite=Strict session cookie and validates Origin; see automatic local login below.

The auth file `{version:1,principals:[{id,token,permissions,threadIds?}]}` requires mode 0600. Permissions are observe/interact/manage/tools; explicit threadIds limit observation and interaction. Client names and Thread IDs are not authentication.

Use initialize → initialized → areal/capabilities (optional apiVersion). Request IDs are independent in each direction; item/tool/call is a server request requiring a response. Replace the baseline through thread/resume. See [Core](core.en.md) for subscriptions, queues and backpressure.

<a id="browser-auth"></a>
### Browser login

- `POST /areal/auth/bootstrap`: a trusted local client supplies `Authorization: Bearer <local token>` without Origin; success returns `200 {code,expiresIn:60}`. Cookies cannot mint codes; requests with Origin receive 403.
- `POST /areal/auth/bootstrap/exchange`: the page sends JSON `{code}` with an Origin exactly matching the service. Bodies are limited to 1 KiB and unknown fields are rejected. Success returns 204 with a session cookie. Invalid, expired, consumed or other-instance codes return 401; missing or mismatched Origin returns 403.
- `POST /areal/auth/session`: manual Bearer login remains available, returning 204 with an independent session cookie. Existing cookies cannot renew a session. Any supplied Origin must match the service.

Codes have 244 bits of random entropy, expire after 60 seconds and are consumed atomically once. The CLI opens `/ui#bootstrap=<code>`; fragments never enter HTTP request targets. The page uses `history.replaceState` to remove the fragment from the current history entry before exchanging it through POST, without localStorage/sessionStorage. Failed automatic login prompts another `areal web` invocation or manual login. Authentication responses use `Cache-Control: no-store`; clients disable proxies and redirects. Long-lived launcher tokens never enter URLs, service descriptors, logs or cookies.

Cookies are named `areal_session_<origin digest>`, omit Domain and use `HttpOnly; SameSite=Strict; Path=/; Max-Age=3600`. Transport is restricted to HTTP loopback, so the HTTPS-dependent Secure attribute is omitted. Names distinguish local ports; cookies are not an isolation boundary against untrusted processes on the same host. Independent sessions inherit the original permissions and threadIds. The server stores SHA-256 digests of codes and session IDs and enforces a one-hour absolute lifetime: HTTP/new WebSocket authentication is rejected and existing browser connections close, without cancelling background tasks. Restart invalidates all codes and browser sessions. Each service retains at most 64 valid codes and 1024 valid sessions; capacity returns 429 without evicting existing sessions.

Compatibility: Bearer clients and the authentication file format are unchanged. Legacy `areal_session=<long-lived token>` cookies are rejected; run `areal web` again or sign in manually after upgrading. `areal web --json` preserves its descriptor and neither opens a browser nor mints a code. Request/response types are browserBootstrap / browserBootstrapExchange in [local-service-v1.json](../../schemas/local-service-v1.json).

### Chat permissions

`features.permissionPresets` advertises `options.permissionPreset: "ask" | "autoReview" | "fullAccess"`. `areal/thread/start` accepts optional `options` and atomically saves the initial configuration; `areal/thread/configure` retains revision and idle checks. Missing presets in old configurations retain their previous semantics. Clients must not silently ignore a new selection when the capability is absent.

Core returns optional `EffectiveConfig.permissions: {resources:"workspace"|"deployment",reviewer:"human"|"model"|"none",fullAccessAvailable:boolean}`. `features.permissionFullAccess` supplies deployment availability before creation. Ask and AutoReview use the workspace and task scratch with command networking denied. FullAccess uses the range allowed by deployment. Read-only, Profile, parent constraints and explicit rules still apply. Queues retain the full admitted configuration.

`run_command` accepts `permissionRequest:{readRoots:string[],writeRoots:string[],network:boolean,justification:string}` to request additional access for one operation. Approval binds final arguments and creates only that operation's scope. It does not widen subsequent commands or replay a previously failed command. Automatic review uses a separate model request without tools and binds the verdict to the request digest. Refusal prevents execution; failed or uncertain review uses human approval. Review records remain in tool execution history.

Managed-command permissions do not imply whole-host isolation for Core, plugins, MCP or the browser. Browser access retains separate page control and exact plan validation. See [permission architecture](../design/permissions.en.md).

## Submissions, configuration and recovery

Desktop `reconcile` accepts `{projectId, requestId?}`. When the original `requestId` is provided, existing request ownership routing selects the execution host before checking its receipts. Omitting it retains project-level reconciliation. Checking never resubmits creation or sends a draft. Independent creation requests from old Worktrees remain in the unconfirmed creation records under Settings → Background service instead of appearing as operations of a new draft. The current draft owns its creation warning. Missing receipts preserve the original request and resources without assuming success or failure.

requestId is a durable business key; RPC id only correlates responses. Identical identity, method, key and normalized parameters return the original result; changed parameters conflict. Each Thread permits 1024 receipts; management logs permit 4096. Exhaustion rejects instead of forgetting keys. Accepted management records without results become UNKNOWN after restart and are not reexecuted.

`features.taskRequestReceipts` extends `areal/request/read` across the current principal's Thread, management, and Task receipts while preserving legacy fields. Each record adds `operation:{method,requestId,target}` and `status:admitted|completed|failed|unconfirmed`, with the original `result` or `error` when available. Task methods use canonical public RPC names, and creation results retain the original Task ID. Lookup also enforces visibility of the Task and every Run's Thread. A supplied `threadId` restricts Thread and Task receipts and preserves the legacy same-identity, same-key deployment management records. Scoped principals still receive only records for visible Threads. `retention:threadAndDeploymentLifetime` and `capacities:{thread:1024,management:4096,task:8192}` describe retention and per-store limits. Recovery matches method, identity, target, and the existing digest. Empty results remain unconfirmed. Archived Threads retain access to their receipts.

### Conversation creation admission journal and negative proof

`features.threadCreationJournal = {version:1,binding:{identity,journalEpoch,coreInstanceId}}` covers only `areal/thread/start`. `identity` binds the authenticated principal; `journalEpoch` identifies a continuously retained Store journal; `coreInstanceId` identifies this Engine boot. These values are not inferred from Runtime epochs, service IDs, PIDs, or timestamps. Before dispatch, clients persist `creationAdmission:binding`, the original request ID, and a creation timestamp in pending, then send the binding unchanged. The creation entry checks it. A late request bound to a retired instance is explicitly rejected; clients must not rebind or automatically resend it.

Core reuses `desktop/submissions.json`. Before creating a Thread, running SessionStart, or starting a Profile Workflow, it atomically replaces the admission journal and syncs the file and directory. Thread creation and its receipt retain their existing atomic snapshot boundary. The completion journal stores the original Thread ID without copying history. Receipt reads prefer the original Thread creation receipt and never complete a Workflow, Hook, or creation by executing it again. Errors and interruptions after admission remain admitted with completion unknown.

`areal/request/read` optionally accepts the original `creationAdmission`, without threadId or taskId. It returns the original identity-scoped `data` plus `creationAdmission:{method:"areal/thread/start",requestId,identity,journalEpoch,coreInstanceId,status}`. Principals restricted to Thread scopes receive no project-wide proof. The method remains read-only:

| Evidence for the original request | Status and recovery |
| --- | --- |
| No record in the current instance; a request may still be queued | `unconfirmed`; retain UNKNOWN |
| No admission or creation receipt, and a missing binding, different identity/coverage, or a recreated journal | Legacy reads retain empty results; bound reads return `unconfirmed`, never inferred rejection |
| Matching identity and coverage, retired original instance, and no admission or Thread receipt | `notAdmitted`; the old binding cannot execute in the current instance |
| Admission exists without a complete creation receipt | `admitted`; reboot changes accepted to unknown without executing it |
| Uncertain publication of an admission write | `unconfirmed`; reconcile the retained image after restart without retrying creation |
| Thread creation snapshot and receipt exist but completion logging or the reply was lost | `data` returns the original Thread as `completed`, without a second creation |

Desktop accepts negative proof only when it matches the original request ID, method, identity, coverage, and instance; current capabilities confirm that the original instance has retired; and the original read contains no other receipts. It persists `accepted:false, admissionState:"notAdmitted"` before removing ordinary pending; Remote keeps its existing rejected terminal state. The draft remains and is never automatically created or sent. Timestamps are informational; neither timeouts nor record age establish rejection. Legacy pending records without bindings remain UNKNOWN across upgrades, scans, and elapsed time.

The journal shares 4096 keys and an 8 MiB budget between management writes and conversation creation, exposed as `capacities.submissionJournal`; `management:4096` remains for compatibility. Capacity or response reservation exhaustion rejects before side effects without evicting old keys. The existing 1024 Thread receipts and 8192 Task receipts retain their lifetime rules; archive does not release deduplication keys. The journal envelope is `{version:1,epoch,entries}`. Opening migrates legacy management entries without dropping keys. Corruption, an unknown version, or failure to persist coverage prevents startup. Older Core versions may not read this format; rollback requires a complete pre-upgrade backup. Proof depends on exclusive Store ownership and continuous journal durability. External replacement or rollback of a live journal is unsupported; recreated coverage after journal loss does not prove rejection of old pending requests.

`features.atomicConfigureReceipt` enables an optional `requestId` on `areal/thread/configure`. Core checks the principal, method, key, and request digest before revision CAS. An identical request returns the original configuration; changed parameters conflict. Configuration and receipt commit in the same Thread snapshot. The receipt exposes the original configuration result, request digest, `expectedRevision`, `resultingRevision`, and `configurationHash`. Legacy callers without `requestId` retain the existing CAS behavior. Configure requests recorded in the management journal before upgrade are checked first using the original identity, method, key, and digest of raw parameters with `requestId` removed. Completed records return the original configuration; unknown records return admitted without replay. Only requests without an old record use the Thread receipt store.

Desktop allocates the original `requestId` for recoverable writes before outer command dispatch. Composite command and suboperation `read|subscription|mutation` effects are declared in `desktop-contract`; Core RPC effects and receipt families come from Core `methodSemantics`. The existing pending journal retains an immutable operation reference. Outcomes retain identity, admission and completion state, without copying ordinary conversation history. `status:failed` can still have `accepted:true`, meaning execution failed after admission rather than proving non-execution. Creation returns the original `threadId` and `requestId`; local journal or view refresh failure cannot invalidate a confirmed Core result. Configuration and all Task writes retain their original keys. Legacy `localOnly` configuration entries are observed without inventing keys or writing revision barriers.

Each project/client connection generation has one read-only receipt worker. It queries original `areal/request/read` receipts at 0.5, 1, 2, 4 and 8 second intervals within a 30 second pass. Disconnect, lifecycle operations and close stop it; reconnect, new pending entries and relevant notifications can rearm it. It does not settle entries while the original response is in flight. Missing receipts, individual lookup failures and view refresh failures neither delete pending entries nor block unrelated receipt settlement. Unknown writes are never replayed. Settlement requires matching method, request key and known target; creation binds the newly returned resource under the same method and key.

`openThread` exclusively owns bounded observation retries, including timeouts on a healthy connection. The same Thread/connection shares one restoration. Deterministic permission, authentication, size and cursor failures are not retried. `observationErrors[threadId]` carries an independent occurrence `id`, project/Thread/connection ownership, `reason`, `recovery` and `refreshPending`. It clears only when its observation restores; admission and view failures remain separate projections. `pnpm --dir clients/gui run test:recovery` exercises real Core creation refresh failure, late receipts, healthy-connection timeout, local journal persistence failure, and configuration/Task receipt recovery.

`areal/turn/submit` atomically admits ordinary conversation input using `{requestId,threadId,expectedConfigRevision,intent}`. The tagged intent is `{type:"message",input}`, `{type:"continue",expectedTurnId}`, or `{type:"edit",expectedTurnId,itemId,input}`. Continue accepts no text. Support requires both `features.ordinaryTurnSubmit=true` and the advertised method. Under the lifecycle, Thread, and ordinary ownership locks, Core reads receipts before checking configuration, ownership, archival, compaction, cancellation settlement, and UNKNOWN. Task, Goal, legacy read-only Side, and task management conversations retain their existing entry points. Executable Side v2 messages use ordinary submission; editing and continuation remain subject to their own contracts.

Edit requires `features.editLastMessage=true`. It accepts only the last user message in an idle ordinary conversation with no pending/running queue items. `expectedTurnId` must match the latest Turn, including any continuation; `itemId` must match the last non-continuation user message. Core hydrates archived history, removes that message and all subsequent items/Turns, invalidates the context checkpoint, and prepares a replacement Turn. Validation and persistence complete before activation, in one snapshot with the receipt; rejection preserves history. Earlier items in a steered Turn remain. File and external effects remain. After commit, `areal/thread/edited {threadId,thread}` explicitly replaces the client history baseline before `turn/started`; ordinary partial Turn events still merge items. Lost replies use the original request receipt, never a separate rewind or automatic resend.

Message preserves the submitted input. A normally active Turn queues it at the tail. An idle Thread without pending input starts a Turn directly. With pending input, Message appends at the tail and resumes the queue; Continue resumes the existing queue. Both respect the authoritative FIFO order. Continue without pending input creates a new Turn in the same Thread, records `continuedFromTurnId`, and uses a visible continuation instruction with history and the current workspace. Its anchor must be the latest `interrupted` Turn, or a `failed` Turn with an explicit interruption fact or Core recovery UNKNOWN evidence. Ordinary model failure and completed Turns do not qualify. Uninspected tool, Hook, or plugin UNKNOWN and unresolved resource cleanup still block execution.

Direct execution returns `{turn}`. Queued admission returns `{queueItemId,queueRevision,configRevision}`. Continue has a null `queueItemId`; Message identifies only the newly submitted item. Core persists the Turn, queue, and receipt in one snapshot before activation or scheduler notification. `areal/request/read {threadId,requestId}` reads the receipt for this method. A lost response or failed client journal cleanup retains the original key and never replays with a new key. Basic `turn/start` and durable `areal/turn/start` cannot bypass retained pending or running items.

turn/start/enqueue take `{requestId,threadId,input,expectedConfigRevision?,interactionMode?}`. Queues retain at most 128 historical items with frozen configuration. Only success advances automatically. Stop/failure/UNKNOWN/restart/drain pauses the queue until explicit resume. After timeout, query request/read or authoritative state rather than assuming no side effects.

Optional `turn/start.admissionGuard: {configRevision,ordinarySession:true}` checks the configuration revision and current ordinary-session ownership atomically before freezing configuration and persisting the Turn. Managed children, active or settling Goals, queued/running/waiting Task Runs and unsettled workers reject admission. Fully settled history or a future schedule alone does not reserve the Thread. Archived sessions, paused or nonsettled queues and existing busy/UNKNOWN/tool-host checks remain barriers. Core retains the Task reservation lock through durable activation. This guard is unavailable on enqueue; `ordinarySession:false` is invalid. Support is declared by `features.turnStartAdmissionGuard`.

Optional `thread/start.admissionGuard: {ordinarySession:true}` checks the resolved explicit/default Profile before creating the Thread or starting a Workflow. Workflow-bound Profiles return argument error `-32602` with `UNSUPPORTED_PROFILE:` in the message. Accepted guarded creation replays return the original Thread without attempting Workflow startup. Support is declared by `features.threadStartAdmissionGuard`. Omitting either guard preserves existing local behavior; omitted fields preserve existing receipt digests. Receipt lookup precedes new guard checks, so an identical accepted request returns its recorded result rather than re-evaluating changed state.

`areal/thread/observe` returns `ownership: {kind: "ordinary" | "task", taskId?, runId?}` beside `thread`. `features.atomicObserveOwnership=true` guarantees ownership, snapshot and subscription are captured under the same Thread → Tasks locks. The predicate matches ordinary admission: active/settling Goals, managed/child Threads, queued/running/waiting Runs and unsettled workers are Task-owned; settled paused/blocked Runs, history and future schedules alone are not. Task/Run IDs require the existing Task and coordinator visibility rules; hidden or unbound ownership remains `kind: "task"` without IDs. If several Runs reserve the Thread, IDs identify only a unique Run bound to the current active/settling Goal; without such a Goal, only a sole eligible Run can supply IDs. Ambiguous ownership stays `kind: "task"` without IDs. This projection is not persisted in Thread.

Known parameter, configuration, capacity, or input-capability refusals before atomic Turn start/enqueue/submit admission return `outcome.kind=rejected` and `recovery.kind=none`, without creating an admission receipt. Known Fork/Side source, anchor, target-profile, and request-key refusals retain their original `reason` and declare rejection. Storage failures, admitted failures, and transport uncertainty are never inferred to be unadmitted from a numeric error code; clients continue observing the original request without automatic replay.

Turn stops, synchronous interaction responses and Task question replies also declare `rejected` for explicit validation failures under the owner lock. Capacity and storage failures in these controls remain uncertain: cancellation or a partial durable write may already have occurred, so neither non-admission nor permission to replay can be inferred.

`areal/queue/steer` accepts `{requestId,threadId,expectedRevision,queueItemId,expectedTurnId}` to atomically transfer a pending entry to the specified active Turn. Under one Thread lock, Core reserves steering capacity, validates the Turn and input, and persists the message, `steered` queue status and receipt together before notifying the executor. The same identity, request key and parameters return the recorded result; different parameters conflict. Query its receipt with `areal/request/read` and threadId. Saving updates the original position and attachment references while retaining the queued model/mode; save or cancel restores the original draft. The previous unpaused state is restored only while the revision and pause reason still belong to that edit. Existing unsent File drafts survive navigation within the current GUI process; no disk attachment cache is added. `pnpm --dir clients/gui run test:queue` checks the queue paths with isolated Electron/Core/Runtime and a deterministic HTTP/SSE model.

Explicit Provider selections retain their model and Provider snapshots. The model archive belongs to the data directory and contains no environment credential values.

Optional `modelName` and `resolvedParameters` in `thread/inspect` project the implicit model's safe name and effective parameters from the existing archive. thread/configure requires expectedRevision and an idle, non-compacting Thread. resetModel=true clears the session model override to Profile/service defaults and cannot accompany a nonempty model. ### Bounded history display

Desktop synchronously installs conversation content, `thread.desktop.configuration`, queue, and interactions from one observation result. Explicit models do not require three additional metadata reads. Historical implicit defaults still resolve their stored revision for display names and effective parameters. Latest-turn hydration collects pages, then merges them into the current live model and publishes content while preserving concurrent deltas. The loading placeholder retains message and bottom Composer layout. Submission and preference notices do not change the message viewport height.

After negotiating `boundedObservation` and `boundedHistory`, the GUI uses `areal/thread/observe {mode:"bounded",maxBytes:262144}` for ordinary, Side and archived conversation baselines. A specific `HISTORY_BUDGET_TOO_SMALL` response permits one retry at 1 MiB; a second failure remains a scoped conversation read error. `CoreClient` independently enforces the same complete-response byte budget before installing the baseline in synchronous `onResult`. Browser host recovery also requires `boundedResume`; tool attachment does not replace host binding. Older Core versions retain the full-history compatibility path without a pagination capacity guarantee.

The read-only Desktop `history` command accepts `{projectId,threadId,viewId,operation:"acquire"|"loadOlder"|"loadItem"|"release",itemId?}`. Only `loadItem` accepts `itemId`; Desktop owns cursors, budgets and Core identity. Messages acquires and releases a distinct `viewId` for each main, Side or child conversation reading view. Older pages merge by Turn/Item ID into the current projection without overwriting events received during the read. Fork inherited history and Side reference snapshots retain their existing provenance contracts.

The display cache retains at most eight conversation windows, each with its latest baseline and four loaded older pages. Deeper paging releases older pages nearest the latest baseline and marks the omitted interval in the timeline. Releasing the final reading view drops old pages and explicitly expanded content; another GUI viewing the same conversation retains its content. This neither cancels Core execution nor deletes durable history. Materialized and currently assembling entries share a 128 MiB serialized-byte budget. Opening a conversation never eagerly expands large `historyDeferred` items. After an explicit Load full content action, Desktop validates UTF-8 offsets, total length and version across responses of at most 1 MiB, then replaces the original placeholder. Explicit expansion increases visible-item memory; this is not a process peak-memory guarantee.

A stale older-page cursor rebuilds only that conversation baseline. Changed item versions discard partial bytes and allow at most one restart from Core's `restartCursor`. Loading retains the actual placeholder and progress, and errors never become invented Agent messages. Automatic file-change summaries inspect only loaded display content; deferred tool records ask for explicit expansion instead of bypassing the budget through a full `thread/read`. History reads never replay submissions.

Desktop `workspace.turnReview` builds historical comparisons from immutable filesystem tool receipts and before-images. If formatting or another external edit breaks one file’s version chain, only that file is listed in `unavailableFiles: [{path,reason}]`; other verified files retain their Diff and line counts. Summaries label partial counts, unverified files never imply zero changes, and the review panel explicitly lists exclusions. Individual tool comparisons remain strict. Current disk contents never fill gaps in history, and intervening external edits are never attributed to tool writes.

Desktop owns reading views per authenticated socket and releases all of that client's references on disconnect. A late acquire cannot revive a closed view or release another client's same-named view. A rebuilt baseline makes Renderer re-register the view without releasing it first. A rebuild on the same connection that is not invalidated keeps the displayed boundary items of the previous turn and reports the previous display boundary until the new baseline finishes hydrating, so no restore notice reappears above content already shown; pages loaded through "load older" are still released by the rebuild. Thread content and `displayHistory` are published together. If completed history exceeds 1 MiB, Desktop fetches a bounded baseline and releases old pages and explicit expansions, which remain available for another explicit read. An expanded item cannot exempt later completed history from the retention bound.

Desktop → Main retains its 256 MiB frame limit. Each connection has at most one in-flight frame, one coalesced pending state, and an ordered ordinary-response queue bounded to 32 MiB of serialized bytes. Projection encoding happens only when a frame is sent. A large item state waits for its send callback before the next frame, so its following command reply does not falsely trigger slow-consumer termination. Send error, deadline or queue overflow closes the connection and releases retained buffers; existing request timeouts remain effective.

### Guarded recovery after a Core crash

Desktop first checks status and attempts to reconnect to the same generation. Guarded recovery requires positive Host cleanup proof from `status --recovery`, the same applicationOwner, a live client lifetime and freshly read matching configuration. A lost reply is reconciled through the recorded successor of the original generation, without an `ensure` fallback. Each original generation allows at most two guarded CLI query/recovery calls; each project allows at most two crash candidates per five minutes. Waiting for `cleanupUnconfirmed` is bounded to 30 seconds. Lifecycle, project, client and closing state are rechecked before dispatch and adoption. Recovery connect/reconcile uses `observeOnly`; Core startup retains UNKNOWN outcomes without replaying submissions. See [local shared service](local-service.en.md) for authoritative proof and recovery interfaces.

## Model configuration hot apply

Shared services provide two narrow methods. Discover support from the current connection's `areal/capabilities.methods`. Only an authenticated `desktop-owner` with `manage`, `tools` and no Thread scope may call them. Observers, ordinary model clients and standalone Engines without a configuration controller do not have this capability. Requests cannot select a file path, supply Provider metadata or change arbitrary process environment variables.

| Method | Request | Purpose |
| --- | --- | --- |
| `areal/server/modelConfiguration/read` | `{requestId?,expectedGeneration?}` | Read the actual applied version or inspect the original request. |
| `areal/server/modelConfiguration/apply` | `{requestId,expectedGeneration,expectedApplied:{revision,sequence},targetRevision,credentials}` | Read authoritative configuration and apply it under Core's admission gate. |

`credentials` is a bounded mapping from `AREAL_CREDENTIAL_` names referenced by the target file to secret values. References are immutable additions; a different value for an existing reference is rejected. Old references remain available to existing tasks. Secrets exist only in trusted requests and execution memory, never in configuration, history, digests, logs or receipts. This endpoint cannot update ordinary startup environment variables.

The response contains `{serviceId,generation,applied:{revision,sequence},modelRevision,credentialStates,operation?}`. `applied.revision` identifies the committed whole configuration file; `sequence` increments after successful application within that generation. These differ from the default model's `modelRevision`. Startup assembly begins at sequence 0. Core checks the revision and configuration from one controlled file snapshot. It rejects stale targets, non-model deployment changes, active work and credential conflicts, without draining or restarting Core or Runtime. Existing Thread, Turn and queue configurations retain their original credential references.

`operation` identifies the original `requestId` and has state `running`, `applied`, `rejected` or `unknown`, with an optional redacted terminal `result` or `error`. Core owns accepted operations; disconnecting does not cancel a commit. Duplicate requests return their original result without publishing again. Inspect the original request after losing a response. In-memory receipts are bounded; a generation change or unavailable record does not prove failure and cannot authorize automatic replay. Clients may verify a new instance's current readiness without treating it as the old request's receipt.

Each Core applies and confirms independently. The GUI provider Save action uses the existing persistence command and completes after file CAS succeeds. Running tasks do not block saving, and an application failure does not undo a successful save. The desktop service attempts application after task completion or reconnection and checks every two seconds while busy. Definitive nonbusy failures stop automatic retries; unknown outcomes only inspect the original request. The page distinguishes persistence from application and preserves the original CAS revision of any new draft. Fallback-default changes and provider removal retain strict coordination. Known partial failures may trigger file CAS compensation followed by application of the actual restored revision. Do not roll back while an earlier request remains unknown. External writes or newly admitted work may prevent compensation; retain actual applied versions and pending state. File watching and explicit application share the applied baseline. Non-model settings retain the safe-restart boundary.

## Interactions and media

Approvals bind Thread/Turn/callId, Host generation, effective argument digest and permissions. allowOnce/deny are supported; effectivePermissions.rememberAllowed=true additionally permits allowSession/allowProject without expanding Runtime Scopes. Questions allow 8 questions/8 options each, 4096-byte answers and 256 historical interactions. Waiting holds no model permit; Stop wins, and late/cross-Turn responses fail.

`permissions/read {threadId}` returns configuration (mode/allow/ask/deny), source, sandbox, workspace, session/project grants and projectFile. `permissions/forget {threadId,project}` clears session or project memory and requires an idle target Thread. Project approval requires manage without a threadIds restriction. See [permission configuration](../guides/configuration.en.md#permissions) for memory and rule precedence. Old snapshots without permissionGrants read as empty. thread/start/resume add permissionMode; full-access Runtime projects as dangerFullAccess.

POST `/areal/blobs?threadId=...` uploads raw bytes with Content-Type matching signatures. Tool uploads also supply callId/hostGeneration and require tools permission. Limits are 16 MiB/file, 128 registered uploads/64 MiB per Thread; no global cumulative Blob quota. Supported types are PNG/JPEG/GIF/WebP, WAV/MP3, PDF and UTF-8 text. GET requires authentication, threadId and reference ownership; a digest is not an access token.

Text and source uploads require strict UTF-8 and reject NUL, binary control characters, and known container signatures. Empty MIME or `application/octet-stream` first recognizes existing media signatures, then validates text. Common text, JSON, YAML, CSV, Markdown, and source MIME types normalize to `text/plain`. Empty files remain rejected. Authoritative `Input::File` retains the filename, Blob URI, and original bytes. Core uses registered upload MIME and bytes to project a filename-labelled text block, without trusting client `mime_type`. Chat Completions and Responses share this projection. New submissions, steer, enqueue, and queue edits enforce the existing 1 MiB aggregate text budget and model capabilities against projected body and labels. Overflow is rejected without truncation. History replay and forks use the same text projection and effective input capabilities. Existing Blobs retain the 16 MiB limit, while normal model budgets govern historical context. Accepted request receipts return before new validation.

contentItems preserve inputText/arealMedia order and deliver actual bytes to models. Authenticated RPC rejects host localImage/localAudio paths; use uploaded areal://blob URIs. Unsupported modalities fail explicitly.

The optional `DynamicToolCall.execution.fileBefore` is a `MediaRef` containing the complete bytes before a conditional write to a `workspace://repo/` file. After hooks and file-version aliases resolve, Core reads through Runtime in pages of at most 64 KiB. Core verifies each page's full-file SHA-256, size, contiguous offset, and the final content digest. The preimage contains at most 8 MiB with MIME `application/octet-stream`; empty files and binary bytes are valid. Core saves the Blob and its tool-record reference before submitting the original CAS write. Capture failures return `FILE_BEFORE_CAPTURE_FAILED` with `dispatch:"not_sent"` and the original cause. Cancellation during capture does not make the file write outcome unknown. UNKNOWN after submission still prohibits automatic replay.

Clients read the preimage through the existing Thread-authorized Blob GET. Archive, fork, and GC retain its direct history reference; fork validates the digest, byte count, and MIME. Only confirmed successful file writes can use this evidence to reconstruct a historical Diff, whose postimage must still match the successful receipt's digest and size. File creation needs no preimage. Older records without this field retain the verified full historical-read fallback. Missing evidence makes the historical version unavailable; current disk contents cannot substitute for history.

## Processes and retention

process/start defaults to lifetime=turn. Thread lifetime needs Profile allowThreadProcesses; writable services also need deployment allow-concurrent-writes. Managed services in a root Thread use the desktop process duration already granted by Runtime, while ordinary Turn processes retain the command duration limit. The two durations are separated only when the trusted command Scope matches the Runtime root's permissions and other budgets. Child tasks, hook task Scopes, and additionally narrowed Scopes retain their original ancestry; the service interface cannot widen their authority. GUI terminals and manually started GUI processes inherit parent Runtime limits by default. An explicit `timeoutMs` can only narrow the corresponding parent limit. Known excess is rejected before durable acceptance without creating an unknown-start receipt. UNKNOWN after acceptance still requires inspecting the original record and prohibits automatic replay. Input is attributed to authenticated identity. Output cursors and cleanup reuse Runtime facts. PTY resize uses actual ioctl; pipe EOF closes the FD, canonical PTY uses VEOF, and raw mode is unsupported.

The GUI terminal uses the account's executable login shell, with `SHELL` as a fallback and `/bin/sh` as the final fallback. The desktop adapter submits concrete argv for an interactive login session and supplies `SHELL`, `USER`, `LOGNAME` and `TERM=xterm-256color` through literal `/usr/bin/env` arguments. Login and interactive startup files establish the user's toolchain environment. Runtime retains its existing environment filtering and permissions. Recovery reads the original managed argv. A running terminal hides routine cleanup diagnostics; exited or uncertain processes retain their exit and cleanup facts.

The model-facing `development_service_inspect` lists only the current Thread's managed records, or returns one record with current Runtime state and at most 16 KiB of output. `development_service_start` submits a thread-lifetime process through the same durable process/start owner with a request identity derived from the trusted Core Thread, Turn and tool call IDs. Omitting `timeoutMs` inherits the authorized service parent limit instead of requesting a fixed 24 hours. Core approval, Profile permission and Runtime write-serialization checks still apply. An unknown start is inspected through the original record and is never automatically replayed. These tools do not provide a second process executor or infer a listening port.

With an explicitly longer `--desktop-process-timeout-ms`, Profile-authorized root Thread services use the deployment lifetime Scope, while ordinary commands retain the narrower `--command-timeout-ms` Scope. An omitted service `timeoutMs` inherits its parent Scope ceiling; an explicit value may only narrow it. Child Thread services must inherit a confirmed parent Turn Scope and are rejected when that boundary is unavailable. Command and service hook participation Scopes retain separate identities and UNKNOWN receipts, and Thread closure cleans up all of them.

Old-epoch handles return STALE_HANDLE without process restoration. Unconfirmed Thread process cleanup, active groups, and compaction prevent restartSafe. Historical tool or hook UNKNOWN alone does not prevent stopping the service; it still requires inspection before continuing its Thread. Archiving requires idle, settled queues/resources and releases hot history while retaining disk snapshots and deduplication keys. GC after drain scans hot/cold references and cannot collect referenced Blobs.

Events use areal/ prefixes, including thread/configured/archived, plan/updated, queue/updated, goal/updated/cleared, interaction/requested/resolved, process/updated and server/draining. Their revisions are not output cursors. Unknown model windows/usage remain null or absent rather than guessed. See [direct protocol examples](../examples/desktop-api.en.md).

features.goals=true advertises Goal support without a separate configuration toggle. Goal events follow the same authorization and atomic subscription boundaries. drain closes automatic continuation admission and pauses Goals; archiving and explicit compaction require stopping the Goal and awaiting resource settlement.

Local service discovery, window-independent lifecycle and Desktop Main integration use the [local service contract](local-service.en.md). `server/status` and `server/drain` additionally return `activeGoals` (Thread IDs) and `pendingQueueItems` (pending/running queue count). These are additive response fields; restartSafe still describes execution cleanup rather than absence of scheduled work.

Shared services expose `server/status.configuration` as `{modelRevision,applied,appliedRevision,applySequence,currentFileRevision,credentialStates,pendingApply,restartRequired,error}`; other deployments return null. `applied={revision,sequence}` identifies the file revision confirmed by Core. GUI model settings use the explicit hot apply interface above. Missing environment credentials during ordinary CLI model reload may report both `restartRequired=true` and `error`, indicating that a local client with valid credentials must perform a safe restart; other reload errors do not trigger automatic restart. `areal/server/configurationChanged` publishes `{threadId,configuration}` to subscribed threads. `server/drain` also accepts `strategy="ifIdle"`: check idle state and close admission under one gate; busy rejection keeps work running. See [configuration reload](../guides/configuration.en.md).

`server/status` and `server/drain` also return `lifecycle={version:1,admission:"open"|"draining"|"closed",ifIdle:{allowed,reasons},settled:{allowed,reasons},executionOutcomes:{uninspectedUnknown}}`. The outcome summary is an additive version 1 field. Its count covers historical tool calls or hook invocations requiring inspection, independently of physical resource settlement. `unresolvedTools` retains the original inspection entries. `restartSafe` equals `settled.allowed`.

`reasons` contains `{code,count}` entries with codes `activeTurn`, `resource`, `compaction`, `workgroup`, `activeGoal`, `queuedMessage`, or `activeTask`. Core shares observation policy with the operation check under its admission lock; observation does not authorize stopping. `ifIdle` requires no work and settled execution; `settled` is the execution/resource postcondition for cancel. Cancel retains paused Queue input without requiring zero pending messages again. Historical uninspected outcomes remain in the journal and keep the original Thread's continuation gate closed, but do not block service exit. Hook task scope uncertainty, unavailable Runtime observation, live Runtime processes, and unconfirmed cleanup remain resource barriers. A timeout can return draining, and RPC success does not prove process exit. Unknown versions, reasons, or missing permission fields cannot imply permission.

### Desktop adapter lifecycle

This GUI adapter protocol is separate from `areal.core.v1`. Authenticated snapshots advertise `service.lifecycle={version:2,desktopGeneration,capabilities:{request,read,reconcile,kinds},activeRequestId}` with stopDesktop, updateDesktop, stopProject, updateProject and interruptTurn.

`lifecycleRequest` carries `{protocol,requestId,kind,mode,expectedDesktopGeneration,expectedTargets,threadId?,turnId?}`. Mode is ifIdle or cancel; each target binds projectId/serviceId/generation. interruptTurn requires the original threadId/turnId. `lifecycleRead` and `lifecycleReconcile` accept protocol/requestId; reconciliation only reads the original Host or Turn, never ensure, drain or cancel.

For a worktree chat, Main resolves the selected logical project and thread to the current execution project and Core instance before preparing interruptTurn. The durable Main reference retains the original logical project for retry identity and UI guards; the request targets retain the actual Core generation. Reusing a request ID for another project is rejected.

Before effects, the Desktop owner saves a durable receipt with per-target Host request IDs and states. Overall phase is acceptedPending, blocked, partial, admissionUnconfirmed, settlementIncomplete or completed. When Desktop targets settle it records only desktopExit=requested; Main verifies original Desktop exit before displaying completion. Main durably saves request references before writes without becoming another execution authority. Lost responses and generation changes read original receipts; completed targets are not repeated. Uncertain targets restrict their projects while other projects remain usable.

Application quit observes resources with `purpose="quit"`. Desktop retains every owned target and shares a five-second budget across status reads without reconnecting unavailable targets. Disconnected or timed-out targets return `observation="unavailable"`, without idle state or empty task lists. They require native confirmation before the original generation receives a cancel request. Confirmation rechecks target identity, generation, and impact. A change in observation availability also invalidates confirmation. Registry, ownership, explicit Core RPC errors, and malformed result structures still block the operation. A closed connection only means observation is unavailable. The Host independently verifies the original identity and cleanup receipts. Updates and resource management retain strict observation.

After every Host target completes, Desktop waits for library and configuration writes and saves `desktopExit=requested` before closing connections. Desktop `before-quit`, SIGTERM, SIGINT, and completed lifecycle requests share one five-second finalization deadline covering connection closure and connection metadata cleanup. A timeout records its cause and stage, closes owned lifetime pipes, and exits with a nonzero status without rewriting Host cleanup receipts. External exit and owner loss trigger existing supervision cleanup. They do not prove resource settlement.

Ordinary startup only attaches. GUI Main serviceLifecycle accepts only `{operation:update|stop|check}`; check does not change execution. Explicit update settles original targets and confirms Desktop exit before launching a replacement, retaining references on failure. Older adapters without these capabilities remain observable, without write probes or cross-layer cancellation fallback.

## Task Mode integration

The GUI read-only `tasks` command accepts `operation: list | inbox`, optional `projectId`, `limit` (1 to 1024), a UUID `requestId`, and a nonnegative integer `viewEpoch`. Omitting `projectId` still aggregates all saved owners. A scoped response echoes its identity and an `owners` outcome. A GUI receiving an older response without that identity requires a safe backend update rather than interpreting global rows as one owner's result. Each owner has a five-second deadline covering startup and every page. The deadline ends only the catalog read. Existing lifecycle code retains startup ownership. Unfinished reads are shared across retries. Expired work cannot fetch later pages or publish projections, and failures retain the previous complete rows. Each page checks a fixed client and connection generation. Repeated cursors fail the read. `[operation]` logs contain requestId, viewEpoch, projectId, stage, duration, page and row counts, and terminal outcome. Renderer `[task-catalog]` logs record receipt, commit, or abandonment without task content or credentials. A taskWatch receipt independently gates task management.

`task/create/list/read/pause/resume/cancel/subscribe/unsubscribe`, `channel/read/reply` and `inbox/list` form task control and communication APIs independent of Threads; see the [Task contract](tasks.en.md). task/updated carries a Task projection and channelSequence; clients retrieve Channel messages through pagination. server/status and drain report activeTasks for work that needs settling: scheduled tasks count only Runs that are queued, running, waiting for input or waiting for agents, including live Runs whose future schedule has been paused. An idle schedule awaiting its next trigger permits safe restart and retains its timing, enabled state and history. GUI/TUI/WebUI can share this Inbox; existing conversation interaction panels still handle synchronous questions and approvals.

Optional `parameters.contextWindowTokens` (1–2000000) sets the user working budget. Provider model metadata retains the service-reported window; the effective window is the smaller of the report and user budget. Context budget contains `windowTokens`, `outputReserveTokens`, `inputLimitTokens`, `windowSource`, and optional `reportedWindowTokens`, `reportedWindowSource`, and `userBudgetTokens`. Effective sources are `account/provider/user/modelDefault/fallback`; report sources are `account/provider`. A lower user budget retains the original report source. Accounts without a report use the system fallback, never public API model-name defaults. Older records can omit the new fields. If model configuration or credentials are unavailable, context inspection still works and returns budget=null. These values control local preflight and do not expand provider capabilities.

## Turn Fork

`areal/capabilities` advertises `conversationDerivationV1` by default with `preview:false` and all six derivation methods. Fork supports `before` and `after` anchors at persisted Turns in a main conversation or Fork, with `sharedCurrent` workspace mode. Creation, listing, recovery, history and evidence reads retain identity, role and admission checks; clients enable actions from the current connection’s advertised methods and capabilities.

`areal/thread/fork` accepts `{requestId,sourceThreadId,anchor:{turnId,boundary:"before"|"after"},workspaceMode:"sharedCurrent",target?}`. Optional `target` selects an ordinary configuration with `agentProfile?`, `model?`, and `parameters?`; `{}` selects the deployment default, while omission freezes the configuration at the final inherited Turn. `before` excludes the anchor Turn; `after` requires a terminal anchor. Tools, hooks and plugin operations in the prefix must be settled; UNKNOWN requires source inspection. Core reads the anchor prefix from a committed source record and fixed cold segments; when the source is itself a Fork, its inherited snapshot is flattened first. Core persists a target-owned snapshot, per-Turn source IDs and creation receipt, then publishes an idle independent Thread and Session. Its local `turns` start empty; source Goals, queues, approvals and execution hosts are not inherited. Creation starts no model or tool and does not change workspace files. Creation and same-key replay return a Thread summary with empty `turns`; read or observe the target to recover its current history. The same business key and parameters return the same target; conflicting parameters return `REQUEST_CONFLICT` in `error.data.reason`. `conversation.kind=fork`, `origin` and `historySeed` describe content provenance, not a `parentThreadId` delegation.

`areal/conversation/history {threadId,view:"inherited"|"reference",cursor?,maxBytes?}` authorizes against the target and pages Fork inherited history or a Side reference snapshot, with a 64 KiB default and 256 KiB maximum covering the serialized result. Cursors bind the target, snapshot, view and position; reuse across targets or views is rejected. An absent history layer returns empty data, snapshotId=null and complete=true. Oversized items are split at UTF-8 boundaries: fragment.text contains consecutive portions of the complete entry JSON with offsetUtf8, nextOffsetUtf8 and totalBytes. Clients concatenate and parse these fragments without creating execution events. Each complete entry includes `turn` presentation metadata for the original status, error, timing and Goal, without items. The GUI groups entries into Turns and renders them in the main message timeline without an inherited-history disclosure. Fork and Turn menus appear with the copy action only after the response ends. `areal/context/read` and subsequent target model requests build logical history from the persisted snapshot and local Turns without reading the live source. The snapshot limit is the smaller of the configured history limit and 64 MiB. Tool batches, settled results, media and raw-result references remain historical facts; they are not registered as new target executions or usage. The target may read only Blobs referenced by its snapshot. The target model must support inherited modalities and native Provider context format; creation otherwise returns `MODEL_MODALITY_INCOMPATIBLE` or `MODEL_CONTEXT_INCOMPATIBLE`. Automated Workflow Profiles return `PROFILE_NOT_SUPPORTED`. Old records without `conversation` remain ordinary main conversations; unknown kinds or unsupported versions fail recovery.

## Side Chat

### Executable auxiliary conversations

Clients enable the new entry only when `features.sideExecutableV2=true` and both `areal/side/create` and `areal/side/close` are advertised.

The new GUI creates auxiliary conversations through `areal/side/create {requestId,sourceThreadId,firstInput?}`. `firstInput` is an optional ordinary input array. Omitting it creates an empty session without a user Turn or model request. When provided, Core persists the child, frozen history, first Turn, and original request receipt together before execution. The same identity, request key, and parameters return the same child and optional first Turn. Unknown outcomes query the original receipt without recreating the child or resending. The Desktop `side` command uses `operation:"create"` and maps text arguments from `firstInput:{text}`.

New sessions persist `conversation.kind=side`, `version=2`, and `policy.kind=sideExecutableV2`. Core inherits the source's effective model, mode, and permission configuration and creates independent queues, interactions, execution state, and receipts. The model receives complete stable source history, while the timeline displays only child messages. During an active parent Turn, inheritance ends at the committed user input and excludes later unfinished assistant and tool increments. Parent progress neither changes the snapshot nor advances the child. Goals, active tools, approvals, and background work are not copied. Later inputs, attachments, tools, permission interactions, and compaction reuse ordinary session paths and limits. Goal, edit/retry, and fork remain unavailable. Existing read-only Side sessions do not gain execution authority.

Each child has an independent transient tab. Selection appends only to the active auxiliary tab belonging to that source. An active resource tab causes a new child. Main and child Composers share structured references, deduplicated by source and text. Limits are 8,000 JavaScript characters per reference, eight references per draft, and 16,000 total characters. Rejection preserves text and attachments. Sending includes only a `{text}` array in a `userselect` code block after `# userselect:`. Source identifiers stay in the unsent UI. Bare `/side` and `/btw` create empty tabs. Pure text arguments create and submit the first child input. Attachments or structured context keep the existing main submission path. Child Composers omit recursive auxiliary-conversation commands.

`areal/side/close {requestId,threadId}` closes an executable child. Before stopping, Core durably fences further admission, cancels that child's work, and waits for settlement and resource cleanup. Closure remains associated with the original receipt. Unknown cleanup is not success and never triggers automatic replay. Single, other, and all-tab close use this operation. Hiding the panel or switching the parent preserves live children. Restart restores neither their transient tabs nor drafts. Core retains history and receipts. Escape stops the conversation owning the keyboard event. With the panel open, outside Escape stops neither conversation. With it closed, main receives the default stop entry. Dialogs, input suggestions, and consumed Escape retain priority.

### Legacy read-only Side

The following `areal/side/start`, `sideReadOnlyV1`, selection anchors, and restricted limits describe legacy records and compatibility entry points.

The `areal/side/start` request is `{requestId,sourceThreadId,anchor?,selection?,workspaceAccess:"none"|"readOnly",input:[{type:"text",text}]}`. The anchor may be `latestCommitted` or `{kind:"turn",turnId,boundary:"before"|"after"}`; omission selects the last committed Turn when the first question is accepted. `selection` may be `{kind:"itemRange",turnId,itemId,startUtf8,endUtf8,textSha256}`: Core verifies the UTF-8 byte range and SHA-256 digest against one text Item in the frozen prefix, so repeated text remains position-specific. An invalid boundary, range or digest returns `STALE_SELECTION` without submitting the first question. For uncommitted or unmappable text, use `{kind:"userQuote",text,claimedTurnId?,claimedItemId?}`; it persists as an unverified user quote, and the claimed IDs do not prove provenance. `turn/after` accepts completed, failed and interrupted Turns, and rejects an active Turn with `TURN_NOT_TERMINAL`. Opening an empty pane creates no Thread. The first question commits an independent Session, immutable reference snapshot, first Turn and request receipt together, then starts the model. Repeating the same key returns the same target and original first Turn even after archive, cold-history eviction or restart, without executing or unarchiving. Creation and same-key replay return summaries with `thread.turns=[]` and `turn.items=[]`, retaining target and first-Turn identity, status and configuration; recover full history through the target read/observe routes. After a lost response, query `areal/request/read {requestId}` instead of retrying under another key. A committed but unfinished Turn is marked interrupted on restart and is not resubmitted.

Side's `conversation.kind=side` and `policy.kind=sideReadOnlyV1` are durable roles; `none` permits the fixed Core `side_context_read` tool and, when enabled by the deployment, the protected answer publisher `gen_ui_publish`; `readOnly` intersects the source's current tool allowlist at creation, identity authorization, deployment permissions and the trusted native Runtime `fs_read`, `fs_list`, `fs_stat` and `search_files` tools against current workspace files. Historical anchor configuration cannot widen this authority; the frozen tool subset survives model configuration, archive and restart. `areal/capabilities.features.conversationDerivationV1.sideWorkspaceAccess` advertises `readOnly` only when the native path sandbox, file helper and search capability are verified and no command hook is configured. Otherwise creation returns `WORKSPACE_READ_UNAVAILABLE`, and users may explicitly select `none`. The Side Runtime scope has the workspace read root only when its frozen subset contains file tools; otherwise read roots are also empty. Write roots are empty and network access is denied; commands, MCP, plugins, dynamic tools, Goals, automated Workflows and delegation cannot execute. File reads report `source:"currentWorkspace"`, the observed SHA-256 and range; another read of the same path in the Turn reports `changedSincePreviousPage:true` when the SHA differs. Directory and search results are also current-workspace observations, without an atomic cross-page snapshot. Historical instructions and tool output are reference data. Model context includes bounded recent excerpts, evidence references and an omission count; follow-ups use the original snapshot. `areal/side/context/read {threadId,evidenceRef?,cursor?,maxBytes?}` pages through frozen evidence under target authorization, with a default budget of 8192 bytes and a maximum of 16 KiB. `evidenceRef` and `cursor` are mutually exclusive. The GUI labels evidence with its snapshot and verification status and does not claim it is current when the source advances or its current state is unknown. Legacy execution routes cannot change the Side role or widen access, and the default `thread/list` task list excludes Side. `turn/start` and `areal/turn/start` accept text follow-ups only; `turn/interrupt` stops only the current Side Turn. Closing the GUI pane sends no interrupt.

GUI selections from a completed Turn default to that Turn's `after` anchor; streaming user quotes use the latest persisted observation at first-question acceptance. If rich rendered text cannot map directly to canonical text, the GUI marks it as an unverified `userQuote` even when the reply is complete. A selection over 16 KiB in original bytes, or one that cannot fit the initial context after escaping, returns `SELECTION_TOO_LARGE`. The initial model package is limited to 32 KiB of serialized UTF-8; `maxBytes` for evidence pages includes the whole serialized result and rejects a budget too small for one page. Selecting from an existing Side opens a new draft and leaves its old snapshot intact.

The GUI can bring selected text or an explicitly chosen whole Side answer into an editable preview with the Side and source snapshot identified. Confirmation checks the captured service instance, project, source conversation, and Side owner, then appends to the latest local main draft with a local insertionId dedupe; existing attachments and model choice remain intact. If the source advances, the preview labels the older snapshot. If the source is archived or the target changes, the preview remains available for copying. This operation changes only the local draft: it neither sends, queues, steers, nor unarchives a conversation.

`areal/conversation/list {view?,sourceThreadId?,includeArchived?,limit?,cursor?}` classifies conversations as `main` (default), `side`, or `all`. Archived conversations are excluded by default; `limit` is 1–100 (default 30). `main` includes ordinary main conversations and Forks but excludes delegated Workers and Side. `sourceThreadId` applies only to `side`/`all`. Results use stable `createdAt,id` ordering, and cursors are bound to identity and filters; cross-filter reuse is rejected. The old `thread/list` contract remains unchanged. The GUI uses the new list for main navigation, explicitly including archives for its archive view, and pages related discussions by source. Manual refresh discovers Side conversations created by other clients.

On authenticated connections, observe permission alone cannot create a Side. A principal with `threadIds` cannot create a derived conversation even with source read and interact permissions: the response carries `error.data.reason=SCOPED_PRINCIPAL_UNSUPPORTED` and does not extend visibility. List, read, evidence, Blob and request-key receipt access authorize the target Thread independently; seeing a target does not grant access to its source or another Side. Request media retained in a Side snapshot with that Side's `threadId`; guessing a digest does not authorize another conversation's Blob. While idle, a Side accepts `areal/thread/configure` only for `model` or `parameters` with `expectedRevision`, preserving its read-only role and tool scope; options, Profiles, Skills and resetModel are rejected. `areal/tool/acknowledge` can save an explicit inspection note on Side-owned UNKNOWN tool records while preserving their UNKNOWN outcome and preventing replay; it cannot acknowledge source or reference-snapshot tools. Other legacy execution routes enforce the durable Side role against writes or privilege changes. The GUI Core client preserves `data.reason` and `data.requestId` from errors.

An idle Side can be durably archived with `areal/thread/archive {threadId}`; an active turn rejects archive. `areal/conversation/unarchive {requestId,threadId}` idempotently restores an archived Side and its full history without starting a model turn. Replaying the original Side creation key returns its original first Turn from durable history, including after restart, without executing or restoring it. Reading or subscribing to an archived Side does not restore it, and sending while archived remains blocked. Stopping or archiving the source does not stop or delete the Side; closing the related-discussion pane only hides it. Core restores sent content after GUI or Core restart. Unsent drafts have no cross-process persistence guarantee.
First questions and follow-ups share active Side capacity: two per source and eight per deployment by default. Exhaustion returns `SIDE_SOURCE_CAPACITY_REACHED` or `SIDE_DEPLOYMENT_CAPACITY_REACHED`. Each Side Turn defaults to at most eight model rounds, 16 tool calls and 300 seconds; global limits can tighten these. Side skips automatic and manual model compaction to avoid requests outside this allowance, and reports context overflow. When a model permit is unavailable, `areal/side/capacity` emits `waiting`/`available`; `thread/read` and subscription snapshots from `areal/thread/observe` / `thread/resume` project the current state as `desktop.sideCapacityStatus` for an active Side. Snapshots clear this waiting state after the Side stops. Stopping affects that Side only. Side requests count toward their own Session and real deployment usage, without inheriting the source Goal budget.

## Side model and cleanup recovery

`areal/side/start` without `model` or `resetModel` inherits the anchor model. `resetModel: true` explicitly selects the deployment default; `model` selects an explicit model. Combining them is invalid. Existing clients retain inheritance semantics; an older Core must reject unsupported resetModel instead of silently inheriting. First and subsequent questions share the persisted configuration.

Side restore has idle/loading/ready/error states per owner and connection generation. A definite error waits for explicit retry; a new target or connection can read again. Old results cannot update new targets. Unknown submissions only reconcile their original receipts and never replay the first question.

MCP cleanup failure remains cleanupFailed with persistent cleanupUnconfirmed. Repeating disconnect without a live connection is no cleanup evidence and cannot clear the state or start another host. Directory rollback also propagates unconfirmed cleanup. Restart does not clear the marker. There is currently no remote RPC to claim successful cleanup; an operator must independently verify the task-owned host exit before repairing the record through maintenance. This state alone does not prove a process leak.

### Component support reports

Portable `extensions.org.areal.hostRequirements` accepts the strict object `{"version":1,"tools":["browser_v1"]}`. Unknown fields, versions, and invalid tool names are rejected. Requirements are projected as `PluginDetail.requiredTools` and each `InstalledSkill.requiredTools`, defaulting to an empty list for old records. They restrict Skill admission and reads in actual conversations; they never register or grant tools. The static report's `declaredHostTools` means actual deployment still needs checking. Desktop read-only readiness checks use the installed identity and current deployed tools, without certifying OS permission.

`PluginDetail.componentSupport` describes the candidate `admissionDigest ?? sourceDigest`. `installedComponentSupport` describes the exact `installedDigest`. Each nullable report contains `digest`, `manifestFormat`, `components`, `compatibility`, and `validation`. An unresolved or unavailable candidate has no report. A validated package with no declarations has an empty component list. Core recomputes reports missing from old installed State using the integrity-checked installation cache. Candidate changes never replace the installed report.

Each component row contains `kind`, package-relative `sourceField`, `status`, `reasonCodes`, nullable `supportedSchema`, `required`, and `activationRequirements`. Kinds are `skills`, `mcp`, `hooks`, `apps`, `commands`, `agents`, and `uiSurfaces`. Status is `supported`, `partial`, or `unsupported`. Commands, agents, and UI surfaces retain individual declaration rows without exporting command, prompt, environment, or credential values. Declaration keys are limited to 256 bytes, implicit paths to 1024 bytes, and reports to 4096 rows. Inputs exceeding these limits reject the candidate rather than omit declarations.

`supportedSchema` names the validated parser contract. MCP and Hook envelope support does not certify runtime configuration, host policy, authentication, platform behavior, or a distribution package. `validation.scope` is `staticParserContract`; provider, platform, and distribution remain `unverified`. Requirements name existing installation, enablement, target-Thread Profile, digest trust, connection, authentication, connector mapping, and Hook consent boundaries. They do not grant those permissions. Read current facts through `areal/plugin/mcp/list` and `areal/plugin/hooks/list`, matching both `pluginId` and `installedDigest`. Reading a report does not resolve remote sources, start code or connections, authenticate, trust, or call a model. The pinned Codex adapter retains its existing response shape.

Only recognized portable 1.0.0 manifests can declare `extensions.org.areal.componentRequirements`. Its strict shape is `{"version":1,"requiredKinds":["skills"]}`. Both members are required. Unknown members, versions, kinds, duplicates, wrong types, and more than seven kinds reject parsing. Legacy lookalike fields, MCP `required`, and Skill dependencies have no package-wide requirement meaning. Every required kind must have a declaration and every row of that kind must be `supported`. Missing, partial, or unsupported required kinds produce `compatibility.state=blocked` with `requiredKindMissing:<kind>` or `requiredKindUnsupported:<kind>`. Otherwise the state is `allowed`.

Installation retains blocked packages for inspection and `enabled` remains configured scope intent. The existing Store effective selection excludes blocked packages from Skills, components, revision publication, and execution checks. A historical Skill requires both current package eligibility and compatibility of its own immutable package digest. An allowed replacement cannot admit a blocked old revision. Compatible historical references remain usable after an update, while disable, uninstall, or a blocked current package revokes eligibility. Optional unsupported declarations do not block supported Skills. Dynamic trust or connection requirements remain separate from this static gate.

Hook reports reuse runtime declaration selection and typed document parsing. `mcp_tool` is the recognized MCP handler type. Invalid declarations retain partial rows, alongside any default document selected by the existing fallback rules. The Hook `supportedSchema` covers document and handler field shapes, not matcher behavior, platform commands, trust, or execution results. Apps reports first load manifest path arrays through the component loader, then recognize a single object with a string `id`, id-keyed maps, and declaration arrays inside documents. A static connector declaration does not establish mapping, authentication, or connection.

## Generated interactive answers

`areal/mcp/apps/list {threadId?}` returns complete tool metadata. App `open/request/close` routes bind thread/server/instance/generation; tool requests also bind requestId. Extension-call kinds are settingsRead/settingsUpdate/settingsAction/mentionsSearch. Forms list/respond/preview validate complete pending requests and originating servers. `areal/mcp/tool/result {threadId,callId}` reads persisted raw MCP results; models receive recursively stripped projections.

`areal/mcp/app/openFromResult {threadId,turnId,itemId,requestId}` accepts exact Core record identity and requires unrestricted manage authorization. The `requestEpoch` from `areal/mcp/apps/list` forms `result-v1.<requestEpoch>.<UUID>`. Replies are `{status:"open",instance}`, `{status:"closed"}`, or `{status:"unavailable",reason}`; Main maps open to an opaque `app` page descriptor. Renderer supplies no HTML, resource URI, arguments, or source proof.

Core resolves turnId then itemId, requires a successfully completed MCP record, verifies raw snapshot length and SHA, and uses saved effective arguments and the raw MCP result. The original MCP call captures plugin digest, connection generation, Thread, cwd, and Apps process epoch. Publication rechecks the enabled source and original connection. Preparing a page only reads its declared resource: it neither repeats the business tool nor creates a tool Turn. Follow-up page calls retain existing App visibility and authorization checks.

Result receipts and instances share a versioned `mcp-apps.json` and one atomic commit. Limits are 1024 receipts per process epoch, 1 KiB per receipt, and 8 MiB per file, without eviction. Existing retries, close, and revocation remain available at capacity. A request with different source arguments conflicts; concurrent requests for one source share an instance. Close atomically terminates every alias, so old requests return closed. A new UUID expresses explicit reopening. Old epochs always expire. UNKNOWN retains the original request; an uncertain close immediately revokes the page token and preserves the original close intent until reconciliation.

Only trusted Main grants host files. Authenticated non-desktop-owner principals cannot supply fileResource or private ui/host-file, which the App bridge does not expose. File-write receipts use areal/mcp/app/file/write and existing areal/request/read without threadId. New notifications preserve instance/generation through the shared desktop service: areal/mcp/app/notification, areal/mcp/tool/result and areal/mcp/form/requested.

Native Main uses areal/mcp/form/resource/prepare {threadId,requestId,fieldName}, stage {selectionToken,requestId,paths} and release {threadId,requestId,fieldName,uri}. Prepare/stage require authenticated desktop-owner and are denied through generic Renderer commands. Stage is UUID/payload-bound in the existing management ledger; UNKNOWN only reads its original receipt. Paths/tokens stay in Main/Core; Renderer receives opaque URIs. Modern discovery negotiates MRTR; requests preserve original arguments and keep requestState private.

Pinned Codex0.162.1 plugin/list/installed/read/install/uninstall/reconcile/search and marketplace/add/remove/upgrade share the package owner. Only search requires experimentalApi opt-in. Unconfigured hosted share/catalog services return -32004 capability errors, never fake empty success. marketplace/add accepts source/refName?/sparsePaths? with persisted sparse cone paths. Full hooks and other limits remain in the [acceptance matrix](../development/codex-plugins-p1-p3-acceptance.en.md).

### Finite page tools

`areal/mcp/app/tools/register`, `revoke`, `claim`, and `resolve` require unrestricted `manage` and `tools` authorization. `core/protocol` types generate request and response schemas. Page tools cannot reach these routes through generic Renderer management forwarding.

Registration attests that the original page completed SDK initialization in trusted Main. The declaration contains only `version:1`, `documentId`, and unique `getSelection` or `applyPatch` kinds. It accepts no custom names, schemas, descriptions, or executable code. Core generates names under the registration namespace and a schemaDigest, then freezes them at ordinary Turn admission. Tools enter only their original Thread's effective inventory and use ordinary approval, hooks, result budgets, and ToolCall history. Read-only Side, research tasks, and unauthorized restricted workers do not inherit them. A readOnly declaration grants no permission.

| Operation | Input identity | Result |
| --- | --- | --- |
| `register` | `threadId,instanceId,generation,ownerId,declaration` | `registrationId,documentId,tools`, each with kind, name, and schemaDigest |
| `revoke` | `threadId,instanceId,generation,registrationId,ownerId` | `revoked:true`; removes publication and new claims before draining calls |
| `claim` | `threadId,turnId,callId,registrationId,ownerId,schemaDigest` | `granted` with claimId, kind, documentId, and effective arguments, or `notGranted` with reason |
| `resolve` | The same call identity, optional claimId, and reply | `accepted` after durable commit |

A reply is `completed` with the fixed result, `noEffect` with a `cancelled`, `closed`, or `unavailable` reason, or `unknown`. `getSelection` returns document revision, anchor, head, bounded selectedText, truncated, and dirty. `applyPatch` accepts `expectedDocumentRevision` and `{from,to,insert}`. Applied evidence includes both revisions, the original range, inserted length, and dirty. Conflict and rejection explicitly report no edit. Offsets and lengths use UTF-16 units, with one unit per LF. CR insertion and offsets that split surrogate pairs are rejected.

Core binds the original actual ToolHost, App epoch, Thread, instance, MCP generation, plugin digest, registration, and schema. Desktop binds the opening Main socket before returning the open response. ownerId is only a service-generated handle. A matching principal or known IDs cannot transfer ownership. Main also checks the original window, token, epoch, and initialized mount. Directed `pending` and `cancelled` notices contain correlation identity only and grant no execution permission.

Core saves ordinary intent and runs approval and hooks before publishing the pending call. Claim persistence precedes the single execution grant. One invocation serializes claim and settlement; endpoints do not independently write history. Repeating identical terminal data reads its receipt. Different terminal data conflicts. Later hook errors, feedback, or generic finalization cannot replace accepted terminal evidence or its result snapshot.

Cancellation before claim proves no execution. After claim, only validated completion or authenticated `noEffect` evidence settles definitively. Timeout, abort, or connection loss does not prove that no edit occurred. Without evidence after the one-second drain, Core saves UNKNOWN. Restart and reopening never replay. Replacing either original connection revokes execution while retaining the unsaved page. An installed package digest change also removes old page-tool publication and new claim authority. The old instance cannot register again; retaining its page does not restore execution authority. Only an explicitly opened new instance can register again. Valid hidden pages remain callable.

Desktop retains revoked ownership for 32 seconds so claimed calls can settle. Confirmed revocation or close releases the record. Unconfirmed retirement retains only an identity marker without connection references. Ownership records are capped at 128; reaching the cap rejects new bindings. Registration cannot exceed the existing 128-tool effective Thread inventory limit. Terminal resolve, revoke, and close use reserved control capacity.

v1 permits one registration per instance, eight per Main, 32 per Core Host, and 128 per runtime. Limits are two active calls per page, sixteen per Host, and 128 KiB combined arguments per Host. Declarations are at most 1 KiB, documentId at most 64 bytes, and each input and output at most 32 KiB. Documents contain at most 65,536 UTF-16 units. Replacement and returned selection text contain at most 4,096 units, with explicit truncation. Claim timeout is ten seconds, execution timeout thirty seconds, and cancellation drain one second. Existing page request budgets and the 2 MiB resource limit remain. This capability adds no sampling, cross-device editing, or arbitrary page execution platform.

## Plugin hooks

These management methods require an unrestricted manage identity and use the deployment submission journal.

| Method | Parameters | Result |
|---|---|---|
| `areal/plugin/hooks/list` | `{}` | Per-source installedDigest, definitionDigest, definitions, diagnostics and trust; configuration sources also expose sourceKind/origin/enabled |
| `areal/plugin/hooks/configure` | `requestId,id,expectedDigest,definitionDigest,enabled,trusted,allowReadOnlyCommands?` | Review current installation/source and complete plan digest before persisting independent definition trust; mismatch rejects; revoke/disable cancels admitted calls |
| `areal/hook/acknowledge` | `requestId,threadId,invocationId,inspection` | Bounded inspection of an idle target's own UNKNOWN; preserves UNKNOWN without replay |

An explicit `AgentProfile` may declare `allowPluginSkills:true`; omission or false retains the existing exclusion. This lets ordinary sessions with that Profile participate in plugin Skills/MCP/hooks, subject to separate current-package and definition trust. Children must also inherit the parent plugin boundary and cannot restore authority disabled by the parent. Read-only command hooks still require separate `allowReadOnlyCommands` consent; Side, research and nativeTaskAgent remain excluded. Hook `agent_type` uses the admitted Profile id; absent roles and the internal discovered-skills Profile use `default`. SubagentStart/Stop matchers and inputs share this identity, and child Pre/PostCompact inputs also include `agent_id`/`agent_type`.

`allowReadOnlyCommands` defaults to false when omitted, including existing trust metadata. It independently authorizes command handlers only in ordinary read-only child Sessions, bound to the same current package/source and definition digests. Each listed definition exposes `readOnlyCommandTrusted`; MCP handlers report false. Side, research, nativeTaskAgent, read-only root Sessions and Profiles disabling plugin Skills remain excluded. Core filters inherited plans and rechecks live authority. Restricted hooks require Runtime `restrictedScopeIsolation`: workspace/package reads, private child scratch and own package data writes only, network denied and no inherited provider secrets. Redirected data parents/leaves are rejected; authorization retains the fixed path identity. Configuration hooks receive no package data/root grants. Omitting or clearing the option removes this capability and conservatively cancels all pending invocations of that package/source, including writable hooks; revoke/disable removes both consents and cancels admitted calls.

`desktop.hookRuns` retains invocation package/definition digests, event, turnId/toolUseId, Runtime operationId, outcome, asynchronous, delivered, output and inspection. `areal/hook/completed` only signals refresh; Thread snapshots remain authoritative. Uninspected UNKNOWN prevents new Turns; closing Sessions reject execution.

`turn/steer` accepts optional `requestId`; with it, hooks and results share the durable deduplication boundary used by `areal/queue/steer`. Matching identity/method/key/parameters wait for the original execution or return its stored response; changed parameters reject. `areal/request/read {requestId}` reads deployment receipts; thread-scoped reads also append that identity's same-key deployment records. Legacy callers may omit the key but cannot guarantee a single execution after response loss. Parallel management operations queue by key. The 8 MiB journal reserves up to 256 KiB plus record margin per accepted response; insufficient capacity rejects before execution without truncating old receipts. `make desktop-schemas` generates the method/projection schema.

Feedback commands run in the trusted desktop backend. The renderer cannot choose the receiver, owner, or context. See [user feedback](../guides/user-feedback.en.md).

## Desktop trajectory switch

The GUI service's narrow `trajectory` command accepts `{operation:"status"}`, `{operation:"retry"}`, or `{operation:"setEnabled",enabled:boolean,expectedRevision:string}`. Toggling requires the current file's 64-character lowercase SHA-256 and accepts no path, destination, or credential override. The desktop adapter fixes the same configuration and credential environment as Core. Status reads neither decrypt credentials nor count as admitted work. Toggling immediately applies upload control. Capture assembly reuses safe application's `ifIdle` drain and restart only when Core is idle, no queued work remains, and unrelated settings are unchanged. Optional `capture_apply_pending` and `capture_apply_error` response fields indicate deferred application or an application problem; clients must not present them as ready enablement. The switch does not establish remote analysis or archival success.

## Desktop provider connection diagnostics

The desktop `providers` command returns a fixed `error.code` and actionable guidance when network initialization or a `discover` or `probe` request fails.

| `error.code` | Diagnosis |
| --- | --- |
| `PROVIDER_NETWORK_DNS` | DNS resolution failed |
| `PROVIDER_NETWORK_REFUSED` | The service or proxy refused the connection |
| `PROVIDER_NETWORK_TLS` | TLS certificate validation failed |
| `PROVIDER_NETWORK_TIMEOUT` | The request timed out or was cancelled |
| `PROVIDER_NETWORK_PROXY` | Proxy setup is unavailable |
| `PROVIDER_NETWORK_REDIRECT` | The service returned a prohibited redirect |
| `PROVIDER_NETWORK_UNAVAILABLE` | Another network or initialization failure |

Diagnostics omit raw exceptions, upstream text, URL queries, and credentials. HTTP 401/403 retain authentication guidance. Other HTTP errors retain their status code. Invalid streams retain model and protocol guidance. Responses probes still send `input`, `store:false`, and `stream:true` to the saved endpoint and require valid text with a successful terminal event.

Model settings show a fixed mask from `credentialStates` by default. The eye requests `providers {operation:"revealKey",id,expectedRevision}` through the authenticated local desktop entry. The backend validates the provider and current configuration revision and returns only its `{apiKey}`; credential references and paths are not accepted. Remote control cannot call this operation. The revealed value is local to the current form and clears on hide, provider or revision changes, and unmount; late responses cannot restore it. Viewing creates no draft or write. Save includes only a replacement entered by the user and clears it after success. Catalogs, state broadcasts and durable receipts exclude the revealed value; read failures return fixed guidance. A blank input preserves existing credentials; a new value replaces them. After saving, feedback distinguishes saved, pending and confirmed application from the actual receipt. A separate probe confirms connection success.

The `providers` `discover` operation accepts an unsaved `connection:{protocol,baseUrl,credential}`. The credential is `{kind:"none"}`, `{kind:"draft",value}` or `{kind:"saved",providerId,expectedRevision}`. Saved credentials resolve against the provider and current file revision. Draft keys are used only for that request. Discovery writes neither configuration nor credentials. The existing provider-ID discovery entry remains supported.

The provider catalog returns aggregate and per-project `application` states. Their `kind` is `saved`, `applied`, `deferred`, `unknown` or `failed`, with the target `revision`. A deferred `reason` is `busy` or `disconnected`; a failed `message` is redacted. `pendingApply` still indicates that a project has not confirmed the current saved revision. A definitive failure is retained for its target revision and service generation. Explicit retry, a new revision or a new service generation can reopen application.

## Desktop background command compatibility

The authenticated `areal.desktop-service.v1` snapshot adds `service.commandContract: "areal.desktop-commands.v2"`. This declaration belongs to the resident Desktop code and is independent of Rust Core capabilities. Main projects an exact match as `desktopCapabilities.currentCommands` at the snapshot root and on each project. It does not trust the same projection supplied by an older snapshot.

A missing or unknown command declaration does not prevent observation; stopping additionally requires independent lifecycle version 2 capabilities. Before dispatch, Main returns `SERVICE_COMMAND_UNSUPPORTED` for operations requiring current semantics. These include `send`, `continue`, `prepareCreator`, `feedback`, steer/queue updates carrying MCP content, new plugin management operations, `providers.defaultAndApply`, and `trajectory.setEnabled`. This is a known rejection without an unknown-submission flag or invented request ID. Compatible queue operations retain their original business request keys. No alternate write is attempted. Feedback draft reads, preferences, and MCP Apps/forms polling degrade according to this availability while preserving local drafts.

Version 2 also requires the original caller identity and normalized admission/execution outcomes for create, configure and Task writes. Main rejects these writes against version 1 before allocating a business request ID; existing observation and legacy queue/steer inspection remain available.

## External CUA client results

The Core `externalCua` capability advertises original CUA results and turn cleanup. A trusted tool host may provide optional `rawMcpResult` in a dynamic tool response, containing the original MCP CallToolResult. Core reuses its MCP projector and media materialization, and retains the original envelope as `mcpResult` in the durable result. Original `structuredContent` remains the output-schema validation target. These results use the MCP 8 MiB durable receive budget instead of the generic mixed-client 16 KiB budget. Projection, media, or persistence failures remain UNKNOWN and never authorize replay.

`ClientOptions.externalCua` defaults to false. The GUI sets it only for manually created LCU chats. Core uses this marker to add trusted identity and turn cleanup to js/js_reset. Ordinary dynamic hosts using the same tool names retain their existing behavior.

## Cloud configuration and session lifecycle

Cloud settings accept only `status` and `save`; resource-allocating `check` is removed. The fixed service path is `/openapi/v1/app-server/`. The trusted desktop adapter derives each workspace endpoint from its persisted Cloud session UUID. Opening a new Cloud chat only edits a local draft. The first send submits `cloudSession/create`, establishes the native thread, and projects its actual connection state; queries use that connection directly. Creation request IDs must use the UUID 8-4-4-4-12 hexadecimal layout, validated before persistence or workspace derivation. Disconnects after server reclamation do not reconnect automatically. The next user message or explicit Reconnect action restores the same endpoint, thread, and UPFS. An explicit reconnect refreshes authoritative history even when a disconnected conversation still shows a running turn, so stale state cannot block further input. Turns with unknown submission outcomes are never replayed. Existing conversations retain their bound endpoints when service configuration changes.
