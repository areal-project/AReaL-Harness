# Testing

Dual-product comparisons reuse the contract's [six baseline journeys](conversation-reading-acceptance.en.md#dual-product-baseline) and shared material generator. Reports distinguish fresh runs, reused evidence, source inference, and unverified cases; a listening dev server does not pass a user journey.

Desktop conversation and Composer follow the [experience acceptance contract](conversation-reading-acceptance.en.md). Define input intent, context recovery, submission facts, completeness, readable time, and position standards first, design transition and final-state cases, then compare designs, implement, and validate together. Complete final content in one conversation does not replace loading-transition and interaction checks.

Recorded smoke journeys request normal `app.quit()` before awaiting Playwright `close()`, allowing product shutdown and recording settlement to proceed together while still awaiting completion of `close()`. Playwright otherwise drains recording before requesting quit, consuming the same 20-second deadline serially. A controlled recording gate verifies this ordering; incomplete shutdown still fails at the original deadline. Draft confirmation, failure reporting and recording evidence remain required.

The Side Chat Escape fallback test waits for the outer task-resources popup to leave layout before checking that the main turn stops. Hiding its inner `Activity` precedes the closing animation of the `keepMounted` popup; that animation must continue protecting the main turn. The test explicitly slows this animation and records popup state for both main/Side start orders, without a fixed sleep or repeated Escape presses to hide the race.

Model-usage observer non-interference tests await the `drained` settlement signal while disk writes remain blocked, then inspect the in-memory ledger under the observer lock. Receiving HTTP EOF does not establish that the server's `finally` block has completed; longer sleeps or releasing the blocked disk first cannot substitute for that ordering.


The release smoke fixture handles auxiliary session titles separately from solve requests. Main-task exit may cancel an unfinished title request; BrokenPipe/ConnectionReset while replying to that title must not turn successful read/write acceptance into failure. Interrupted solve responses, tools on naming requests and other protocol errors still fail. `scripts/fixture_session_title.py` is a local fixture helper and does not change production retries, timeouts or model usage.

Install dependencies using the [development guide](README.en.md). Regular tests use temporary directories, dynamic loopback ports and deterministic models without real model credentials.

Model-selection smoke uses the efforts explicitly configured by its fixtures. Four-option, two-option and empty lists cover choices, slider bounds, keyboard/drag input, correction of invalid historical values and service default. Fast request and cold-reopen assertions use the same restricted options. Reading the provider catalog can settle pending configuration, so seed saves check idle status after that read.

Browser terminal results, Worktree and scheduled-task contracts use the existing `history.loadItem` operation to read deferred successful-tool records before checking execution results and files written in the owning directory. A conversation summary without the full record does not prove that a tool failed to run; a summary alone also does not prove success. Migration smoke opens results through the current tool summary control and retains child-conversation and main-draft isolation assertions.

Tool-fact acceptance uses `scripts/support/tool-history.mjs`: acquire/loadItem only for deferred tool records in the target Turn, reread the snapshot by its original Turn/item identity, then release the temporary view. Inline records retain the full-history compatibility path; original failed, interrupted and UNKNOWN assertions remain active. Read failures or changed identity fail directly without retries or skips. Presentation acceptance still exercises the visible summary disclosure; RPC acceptance checks formal responses, error categories, notifications, threads and request receipts directly. When both Profile and provider references are missing, Profile resolution errors take precedence, keeping model configuration from masking the resource-reference contract.

When a new history view acquires an already invalidated window, it rebuilds the baseline once before bounded hydration; registering the same view again does not trigger recovery loops. The original connection identity and generation are fixed before waiting for recovery; the same connection may produce a new window, but a replacement connection cannot take over the old request. A further window change, invalidation, or release of the requesting view fails explicitly even when another view remains alive. Concurrent readers share hydration; closing one reader rejects its own acquire without cancelling another live view.

The GUI `workflow_dispatch` input `smoke_parallel` explicitly compares the scheduling candidates 4/5. The default and ordinary PR/main runs stay at 4; shared resource usage is not raised automatically. Only the smoke matrix limit changes: tests, gates, timeouts and real artifact dependencies remain intact. After cache population for one successful ref/SHA, run both values serially with the same `comparison_base` and `qualification=none`, recording actual cache hits, concurrent workflows, first failure feedback, total feedback and accumulated runner time. Do not compare an observation overlapping queued/running main work as an isolated result. Gaps in matrix/shared execution do not turn created-to-started time into proof of insufficient capacity; ordering and five-way parallelism remain falsifiable candidates, not established remedies for long waits.

PR workflows cancel superseded runs by PR number; Verify/GUI main and manual runs use separate run IDs so pending main commits cannot replace each other in a shared concurrency group. Documentation-only changes retain lightweight formatting, contract, and link gates without Cargo dependency fetching, Rust build-cache restoration, or dependency auditing. Product inputs such as built-in Skill Markdown still receive code validation. Workflows do not use paths filters that would leave required checks pending; final gates retain explicit applicability validation. Linux GUI installation uses setup-node's pnpm store cache, while Relay keeps its separate Node runtime and npm lockfile cache. Dependency auditing downloads the pinned official cargo-audit binary and verifies its SHA-256.

The GUI artifact job publishes its matching build inputs after the required builds and RPC check. Core contracts are partitioned deterministically into two manifest-derived shards; independent native/design checks reuse preparation in the second shard, with separate steps and result directories that still run after contract failures. Each lane consumes the same run/attempt dependency report and publishes unique results. The existing `macOS Core contracts` check name remains a strict aggregate. Desktop and snapshot modules are frozen alongside Core, renderer, and the native helper, so consumers no longer repeat `build:desktop`. Final gates still reject missing, duplicate, failed, wrong-platform, stale-source, stale-plan, or wrong-run/attempt results and incomplete child-test sets.

Container builds use the pinned, checksum-verified official cargo-chef binary to derive a dependency recipe from manifests and the lockfile. Dependencies compile before real source COPY instructions; source edits rebuild workspace code while target, manifest, and lockfile changes still invalidate the recipe. The runtime image exports only final-layer cache while the test image retains full build layers, avoiding duplicate complete dependency caches. The test target imports only its own complete cache graph as a candidate measure to isolate it from the final image’s min graph. A structural experiment using local OCI caching and the native snapshotter supports this choice; hosted GHA caching with overlayfs remains unverified, so neither the online cache-miss root cause nor a timing benefit is established. macOS native and GUI builds share the Rust dependency cache for the same environment key. The macOS private Bash cache contains only the current identity directory: lockfile, builder, architecture, compiler, SDK, OS, and runner image changes produce a new key. Restored binaries, corresponding sources, and license files are still checksum-verified; other identities and download directories are not cached. Test outcomes and failure reports never serve as cached passing evidence.

Use `python3 scripts/ci-timing.py --collect areal-project/AReaL-Harness --limit 50 --output target/ci/timing` to preserve gh data and generate per-job/step CSVs; use `--input <snapshot.json>` for offline replay. Collection retains every attempt of the latest 50 runs and fetches its matching jobs. Analysis starts each attempt at its own run_started_at, excluding the pre-rerun interval and earlier attempts’ runner minutes. Analysis retains cancelled/failed runs, attempts and runner metadata. Dependency waiting is estimated. `post_dependency_delay_estimate_s` measures from the later of job creation and estimated dependency completion to job start, including possible matrix throttling, orchestration, shared quota and provisioning. Public timestamps cannot isolate the actual runner queue; the legacy `runner_wait_lower_bound_s` remains null and does not establish a capacity shortage. `first_failure_feedback_s` uses an actual failed step’s completion time and records its preparation/validation/mixed phase; simulated failure records printed by unit tests do not count. Composite steps containing installation or compilation remain mixed rather than being counted entirely as testing. Without logs or child reports, cache temperature and exact test splits stay unknown. Compare successful runs with matching coverage and inspect both wall-clock critical path and accumulated runner minutes.

`scripts/ci-scope.py` owns the plan shared by local checks and CI. `check-changed` resolves merge-base once and unions staged, unstaged, and untracked paths, including both rename sides and changes cancelled by partial staging. The plan records commands, dependencies, capabilities, platforms, and manifest child-test sets, bound to base/source/head and input digests. Shared Rust, schema, lockfile, build, and CI changes broaden selection; unknown code selects conservatively. An unavailable comparison base cannot pass.

Focused checks run the plan’s `commit` phase plus previously unsuccessful checks and their dependencies; `ARGS=--phase=full` selects the complete plan. Commands read the `working-tree`, while the index affects selection and drift detection; this does not validate partially staged contents. Reports list unselected full checks as `pendingRequired` and other-platform checks as `remoteRequired`. `passed` covers only the selected checks. `blocked`, `invalidated`, and `failed` cannot count as passing.

Failure follow-ups automatically read `target/ci/{preflight,changed,failures}/*/report.json`. Only reports from HEAD’s ancestry after the comparison base (including HEAD) participate. For each check ID and platform, results from newer commits take precedence, ordered by completion time within a commit. Unsuccessful checks still required by the current plan are selected with their dependencies. Other branches and commits already included in the base are excluded; late passes from ancestor commits cannot clear failures on newer commits. Reports only guide selection: commands come from the current plan, and historical passes never count as current evidence. Download remote reports to `target/ci/failures/<attempt>/report.json`, or import one explicitly with `ARGS='--failure-report /path/to/report.json'`; explicit reports outside the branch are rejected. Other-platform checks remain required remotely; missing local capabilities block the selected check.

Read structured progress with `python3 scripts/ci-preflight.py --report target/ci/changed/<run-id>/report.json`. The adjacent `plan.json` must match the report identity. At initialization, command start, and check completion, the runner updates `progress` with counts and IDs for `passed`, `failed`, `blocked`, `pending`, `running`, `invalidated`, and `cancelled`. Unselected full checks and remote checks remain pending and are also listed as `pendingFull` and `remoteRequired`. Later independent passes cannot erase earlier failures. Top-level `status=passed` covers only selected local checks; `progress.status=pending` means the full plan still needs validation. The progress reader’s exit code indicates readability, not verification success.

Design documents are health-budget inputs: Markdown-only changes under `design/` or `clients/gui/design-system/` select the inexpensive `gui-health` check without triggering GUI builds or smoke. Ordinary `docs/` changes retain document-only selection.

Reports record the actual selection in `selectedRequired`. An interrupted local attempt carries selected local checks without results into the next focused check; never-selected `pendingRequired` and other-platform `remoteRequired` do not become a mandatory local full run. Legacy reports recover this set only from an adjacent identity-matching `plan.json`. History only guides reruns, never proves a new source/base/plan passed; `passed` still covers the current selection, while progress and remote requirements describe completeness. Missing or duplicate child-runner entries report a coverage error; failures within a complete set identify `failedScripts`. Identity mismatches still fail immediately.

The scheduled-task editor loads only after explicit editing; reading the list imports no editor and submits no task operation. Its dynamic chunk remains in the Remote offline asset closure. New chunks need bounded budgets without raising entry or aggregate limits. Pure-state tests verify loading, retries, and stale-generation invalidation; SSR checks establish only the absence of eager imports; first editing, loading failures, task changes, and stale responses after unmount still require interaction acceptance.

Human review of health baselines remains a code-review responsibility; the script cannot verify human authorization. It suppresses only the old-base transition diagnostic; actual overruns, other metrics, and source caps still fail. Once the base adopts the new value, this record no longer matches and may be removed. Later growth requires a fresh review, not a permanent `--allow-regression`.

## Local verification artifacts and startup diagnostics

After Cargo succeeds, `make build` / `make release` writes `target/<profile>/verification-build.json`, binding the existing Core `inputHash`, build revision and SHA-256 of the complete Core/Runtime set. GUI builds extend the existing bundle analysis plugin with `renderer/dist/verification-build.json`, recording GUI inputs and output hashes; source changes during a build fail it.

From the repository root, deploy matching artifacts into a separate fixed slot, then diagnose startup:

```sh
python3 scripts/verification.py deploy --source-dir "$PWD/target/debug" --bin-dir "$PWD/.local/dev-bin/verification" --evidence "$PWD/.scratch/verification/deployment.json"
make gui-build
python3 scripts/verification.py doctor --core "$PWD/.local/dev-bin/verification/areal" --report "$PWD/.scratch/verification/startup-1.json"
```

Deployment reuses existing process/open-file inspection and rejects occupied slots, missing components and artifacts changed since the build. Verification helpers hold the slot's `.verification-lock` for the entire run; deployment uses the same lock. Locks do not expire automatically. After interruption, inspect `owner.json` and confirm its processes and services have stopped before removing a leftover lock. Existing local fixed-path deployment and doctor entry points delegate to these versioned implementations. Isolating test directories does not establish build identity. Direct `cargo build` does not create the batch receipt; use `make build`.

On macOS, fixed artifacts also include `shells/bash`, `shells/sh`, build metadata, the GPL license, and corresponding source archive. The build receipt reuses release packaging validation for the private shell and records every file's SHA256. Deployment copies them under the same slot lock, and doctor checks their integrity. Missing or changed files fail verification; Runtime does not fall back to system Bash. Linux retains its existing Runtime and reaper closure.

Before Electron starts, doctor checks Core's embedded input identity, all component hashes, Renderer inputs and output hashes. Reports include each of the three programs' path, SHA, probe command, exit code or signal, and macOS signature check. A failed probe does not discard remaining diagnostics and produces a nonzero exit. Use a new report filename for each attempt; existing reports cannot be overwritten. The file helper's no-request probe checks startup without performing a file operation. Neither exit zero nor a valid signature proves manual authorization. `authorization` defaults to `unknown`; after actual human observation, record each component separately with options such as `--authorization-observation areal=allowed`. SIGKILL is recorded as a signal without attributing it to endpoint protection. Reports do not replace real Runtime, provider or packaged-app acceptance.

Doctor also accepts `bin/areal` in an installer version directory. It first reuses installer validation of the manifest and full inventory, then probes Runtime from the same bundle’s `libexec/areal` and checks the manifest, actual Core version, embedded inputs, current source and Renderer. It writes no fixed-slot receipt or lock into the bundle, preserving its original inventory. This supports controlled-update acceptance with source Electron; it does not replace signed-package or system-authorization acceptance.

## CI and contracts

Handle CI failures through evidence, operation identity and state ownership, a controlled counterexample, a repair, and verification of the same source version. When a failure class recurs or local checks pass while CI fails, revisit the whole causal path before another edit. Local patches and reruns without new evidence do not establish a diagnosis.

1. Collect failures from the same version and distinguish product defects, test defects, environment blockers, and contract issues. Retain the PR head, actual CI checkout/merge revision, artifact identity, tool versions, and first-run logs. Verify differences before attributing failure to the environment.
2. Identify the owners and completion signals for the current request's admission, receipt, projection, storage, and final UI state. Bind asynchronous assertions to the request ID, target, and execution Core generation; bind history views to view ID/revision. A previous Turn's completion, a send count, or a single RPC's zero pending count cannot establish completion of the current operation.
3. Use one-shot barriers to fix an observed concurrent order. Confirm the pause phase and original request identity before performing the competing action. Preserve the mounted instance and connection lifecycle; record added navigation, remounting, or a changed pause phase as a separate case. After release, wait for the corresponding response and Renderer projection. Failure cleanup must release barriers too.
4. Reuse the real state owner's subscription, registration, cancellation, and release logic in fixtures. Simplified transports still need explicit connection identity and coverage of reload, overlapping connections, and acquisition completing after close. Within each state owner, commit its state and storage changes before notifying synchronous consumers; acceptance checks both notification-time consistency and settled text, attachments, and UI.
5. For product defects, retain the same counterexample failing before and passing after the repair. For test defects, document evidence that a prerequisite or assertion conflicts with the contract. Assert user-observable outcomes: allow valid empty-value representations or coordinate changes after history prepends while continuing to reject resurrected content, settlement of the wrong target, and visible-anchor drift. If reproduction fails, record the uncertainty and add bounded observations; a passing rerun does not establish a repaired cause.

Each diagnostic run should distinguish a specific hypothesis. If candidate causes remain indistinguishable or patches spread across modules, review ownership and design before further repair. Reuse existing logs, state, and traces; a new unified diagnostic platform is not required. Inspect the owned diff, run affected tests and required gates, and verify remote status against the final source version. Passing local checks proves only their executed scope; report conditional skips separately.
